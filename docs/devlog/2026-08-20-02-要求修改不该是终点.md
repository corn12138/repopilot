# "要求修改"不该是终点

> 开发记录 · 2026-08-20 · RepoPilot

补丁审查页有三个按钮：接受、拒绝、要求修改。前两个是终点，第三个不该是 —— 它的意思是"再来一次，按我说的改"。
但原型里它是这么实现的：

```ts
} else {
  this.setStatus(record, 'BLOCKED', `用户要求修改：…（原型暂未实现新 Attempt）`, 'CHANGES_REQUESTED');
}
```

`attemptId` 全仓只有一个生成点（Run 创建时），加上 `setStatus` 的"终态不可逆"守卫 —— 点下去，这个 Run 永远停在那儿。
双审跑起来之后这会是最常用的按钮，所以这一刀切它。

## 一、新 Attempt 不是"接着跑"，是"重新来过但记着"

TD §11.1 早写好了形状：旧 Attempt 的事实全留，旧审批全废，**不续用旧 workspace/lease**，
预算是 Task 级聚合的。落到代码：

- 旧补丁 push 进 `record.priorPatches`，`record.patch = null`、`record.plan = null`、审批清空；
- `attemptId` 换新、`attemptNo + 1`、新 `AbortController`；
- 工作区从**同一个 immutable snapshot** 重新物化。这一条是结构性的而不是靠自觉：
  `MaterializedWorkspace.create` 以 runId 为目录键，会先删旧目录再从快照重建 —— 想"续用"都没有入口；
- 账本继续累加，墙钟带着已用时间起算（给 `PausableDeadline` 加了 `priorConsumedMs`）。
  否则每点一次"要求修改"就白送一份完整时长，预算就成了摆设；
- 发一条 `ATTEMPT_STARTED` 事件，把 `attemptNo`、上一版 digest、**起始账本**都写进去 ——
  "预算是接着用的"这件事要能在事件里被验证，而不是靠我在文档里说。

开不了的时候要说清是哪一种，而不是笼统一句"暂未实现"：预算耗尽（点名是哪一项预算）、
恢复态 Run 没有活的执行器（它能接受/拒绝，但开不了新尝试）、路由丢失、工作区重建失败。

## 二、不带上反馈，模型会把同样的改法再写一遍

工作区已经回到快照，上一版改动**不在**里面了。所以新一轮的任务简报里要塞两样东西：
用户的原话，和上一版的 diff（截断到 24k）。外加一句"这是同一个任务的第 N 次尝试，预算与上一次共用，没有重置"。

e2e 直接断言这件事：捕获两次发给实现方的请求体，第一次不含"要求修改"，第二次含用户原话、含上一版 diff 里的标记串、含"第 2 次尝试"。

## 三、否掉的那一版必须留得住

`PATCH_SEALED` 事件里只有 patchId / digest / 文件名，**没有 unifiedDiff 正文**。
所以历史补丁不能只活在事件流里 —— 它是"用户为什么不接受"的证据。
持久化 schema 升到 v3，加可选 `priorPatches`（v2 旧快照读回 undefined，按"没有历史"处理，v4 仍 fail-closed）；
`patch.get` 一并返回；审查页多一张默认折叠的"历史补丁"卡。没有历史时不渲染空壳。

## 四、踩了什么坑

**1. 测试互相喝对方的模型脚本。** 新 Attempt 是异步推进的：用例结束时它还在后台跑。
`fetch` 是全局 stub，于是上一条用例的后台 Run 会去消费**下一条**用例的脚本队列，
表现成"api.deepseek.com 的模型脚本已耗尽"——单独跑绿、一起跑红。
修法是 `afterEach` 里 `authority.shutdown('test-teardown')`。这类"绿在单跑"的失败这个月已经第三次了
（08-13 的数据根、08-19 的 cleanup、这次的后台 Run）；它们的共同点都是**测试之间共享了一个进程级资源**。

**2. 第一版补丁得能过验证。** 我最初让第一版故意改错，想着"用户当然会要求修改"。结果它走的是
`VERIFICATION_FAILED` 分支，根本到不了 `AWAITING_PATCH_REVIEW`。REQUEST_CHANGES 的真实场景是
**机器说通过了、但人不满意实现方式** —— 夹具得照着这个来。写测试之前先想清楚被测的那条路径怎么才走得到。

**3. 一个 stub 没跟上契约。** `patch.get` 多返回一个 `priorPatches`，App 测试里的假 Core 还只回 `{ patch: null }`，
`[...undefined]` 直接把整个详情加载炸掉，5 条用例红。选择是改 stub 而不是给生产代码加 `?? []` ——
stub 是在扮演 Core，契约变了就该跟着变；给生产加兜底等于让真实的契约违约悄悄过关。

**4. 为了一条断言差点在产品里开后门。** "预算耗尽时不开新 Attempt"需要把账本推到上限，而任务预算在创建时写死、没有对外入口。
我先写了个 `__setLedgerForTest`，然后删掉了：与其在产品里留一个绕过口，不如在测试里明说自己在戳私有状态
（一行 cast + 注释）。被测的仍然是产品逻辑本身。

## 五、数字

`persistence.ts` v3、`domain.ts` 加 `ATTEMPT_STARTED`、`authority.ts` 新增 `startChangeRequestAttempt`
（含四条拒绝路径）、`PausableDeadline` 加 `priorConsumedMs`、`agent.ts` 的 `changeRequest` 简报、
`patch.get` 返回 `priorPatches`、RunDetail 历史补丁卡与恢复态禁用、Transcript 的 Attempt 分隔。
测试 891 → 901（attempt e2e 4、persistence +1、RunDetail +4、Transcript +1）；typecheck 与 selftest 均过。

## 六、可复用的结论

- **"要求修改"是循环的一部分，不是终点**；把它做成终态，等于把最常用的那个按钮做成了死路。
- **续期要带着账本走**：新一轮共用同一份预算，否则"再来一次"就是无限续杯。
- **不续用旧工作区这件事，用目录键做成结构性的**，比写一条注释叮嘱靠谱。
- **证据要能脱离事件流活着**：事件里没有 diff 正文，那就得有一份快照存着。
- 又一次：**进程级共享资源是测试互相污染的根源**；异步后台任务在用例结束时要被显式停掉。
