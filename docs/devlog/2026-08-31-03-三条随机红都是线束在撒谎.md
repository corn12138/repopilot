# 三条随机红，都是线束在某个维度上撒谎

一天里修了三条"全量跑偶尔红、单跑必过"的用例。分开看是三件事，
放一起看是同一件：**测试线束在某个维度上对真实系统撒了谎，而红的样子
指向错误的方向。**

三条都不是"等久一点"能解决的，也都不该用重试掩盖。

## 一、三条各自是什么

| # | 用例 | 线束撒的谎 | 红的样子 |
|---|---|---|---|
| 1 | 外部 CLI 隔离负向断言 | 证据载荷**无界**（把整份 env 含 PATH 带回来） | `expected 'FAILED' to be 'SEALED'` —— 像隔离坏了 |
| 2 | 时间线跟随 | mock 回源返回**比推送更旧**的事实 + 卷入一个无关异步源 | 按钮从未出现 / `expected 800 to be 1100` |
| 3 | （同 2 的另一半） | 同上 | 同上 |

第 1 条的机制：平台对 stdout 预览有 4000 字节上限，超了整份判为不可解析。
宿主 PATH 在开发机上就有 ~2996 字节。**于是用例的成败取决于"仓库检出到多深
的目录"** —— 实测同一份代码，深一层路径下 PATH 涨到 3451 就必红。

第 2 条的机制：fixture 是 `AWAITING_PLAN_APPROVAL` 且 `plan.get` 回 null，
正好命中 App 里"状态推进到需要新数据时补拉一次"的 effect，于是每次挂载都发
**第二次** `run.events`（加计数实测：同一条用例里两次）。那次补拉把 runDetail
置 loading，`selectedRunDetail` 暂时为 null，itemCount 归 0；机器不忙时它在
`act()` 内就 settle 了，忙起来就没有 —— 断言撞在空窗上。

## 二、我在第 1 条上猜错了两次，值得记下来

**猜测一：flake。** 不是。同一份代码在深路径 worktree 里 **3/3 必红**、
主树 **3/3 必绿**，是确定性的。

**猜测二：`.chat-scroll` 被 React 换掉，stub 落在脱离节点上。** 也不是。
它是 `<main>` 的固定第三个子节点，兄弟条件翻转不会让它重挂。

**第三次才对：加计数。** 一行 `console.log` 打出 `run.events fetch # 2`，
真相就出来了。

教训与 08-28 那三次是同一条：**先量，别猜。** 而且这次更具体 ——
"猜是 flake"是最贵的一种猜，因为它让人停止查错。

坐实"不是 flake"的手法值得复用：**把最终提交检出到同样深的路径跑同一条**。
同一份代码、不同路径深度、不同结果 → 才能断定是环境不是提交。

## 三、共性：线束撒的谎有三种形状

1. **无界**：证据载荷随宿主环境增长（PATH）。
   → 改成只带判据（键的清单）+ 逐项对值检查，两者都有界。
2. **回退**：静态 mock 让"回源"返回比推送更旧的事实。真实 Core 持有全部事件，
   重拉一定是超集。
   → 让 mock 累积。
3. **多了一个异步源**：fixture 的状态恰好触发了一条与被测行为无关的补拉。
   → 把那个状态换掉，而不是给断言加等待。

## 四、一条反向教训：修法本身也可能撒谎

第 1 条我第一版的修法是"把 PATH 的值抹掉"。用例绿了，但我按"去掉就红"的
规矩验了一次：注入 `Object.assign(..., process.env)` 模拟真泄漏 ——
**它确实红了，但红的理由是"输出被截断"，没有一个字提到泄漏。**

也就是说：修完之后，真泄漏时用例仍然会指向错误的方向。而我正在修的就是
"红的样子指向错误方向"这件事。

第二版才对：让 CLI 自己算判据（键的清单 + 逐项 grep），失败信息直接命名
漏了什么。验证：

| | 报错信息 |
|---|---|
| 修之前 | `输出被平台截断（仅保留末 4000 字节）后无法解析` |
| 第一版 | 同上（绿了，但泄漏时仍误导） |
| 第二版 | `expected 'KEYS=_,__CF_USER_TEXT_ENCODING,…' to contain '\|LEAKS=\|'` |

## 五、刻意没做的

三条都**没有**加 `waitFor`、没有加重试、没有调 timeout（第 2 条那里作者早先
已经加过 5s 显式超时，仍然拦不住 —— 因为它不是"慢"）。

红会因为等久一点而消失，但消失的理由是"等久了"，不是"这里本来就不该有
第二个异步源 / 载荷本来就不该无界"。前者会把问题推到下一个更忙的机器上。

唯一放宽的一处是 `testSetup.ts` 里 testing-library 的 `asyncUtilTimeout`
（1s → 10s），那修的是另一类：App 级用例要等一整轮 bootstrap 四个并发请求，
默认 1s 在全量跑时不够。**放宽等待窗口不会让真正的失败变绿** ——
断言不成立时 waitFor 仍会在窗口结束时报错，只是慢一点。

## 落点

- 全量连跑 3 次 1232/1232（这个会话里第一次做到）
- 一条可复用的判别手法：怀疑 flake 时，**把同一份代码放到不同环境跑**，
  而不是重跑同一个环境
- 一条可复用的验收标准：修完之后要问的不是"绿了吗"，是
  **"它下次真出问题时，会指向正确的方向吗"**
