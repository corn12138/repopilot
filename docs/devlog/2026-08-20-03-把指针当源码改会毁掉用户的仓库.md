# 把指针当源码改，会毁掉用户的仓库

> 开发记录 · 2026-08-20 · RepoPilot

`grep -rniE 'submodule|lfs|sparse|case collision' prototype/src` → **零命中**。
四种真实的仓库形态在导入时全是 fail-open，而且失败方式都不可见。其中一条会**破坏用户的真实仓库**：

Git LFS 的文件在磁盘上是一段一百来字节的指针文本。`git ls-files` 照样列出它，`copyFileSync` 照样收进快照，
模型看到的"文件内容"是 `version https://git-lfs.github.com/spec/v1`。它可能对这段文本生成补丁；
用户点「应用到仓库」，`git apply --check` **会通过** —— 于是宿主上真正的指针被覆盖成模型写的内容，
大文件与仓库的关联就此断掉。整条路径没有一处会报错。

## 一、四种形态，四种归因，四种下一步

之前它们的表现是：LFS **完全静默**（连排除清单都没有）；子模块是个目录 → lstat 之后记成 `UNREADABLE`；
sparse checkout 的路径磁盘上没有 → 也记成 `UNREADABLE`；大小写重名则两条都收进来。

「读取失败」这四个字把三件完全不同的事说成了一件。用户看到它会去查权限，而真正该做的分别是
`git lfs pull`、`git submodule update`、`git sparse-checkout disable`、改名消歧。所以先把归因拆开：

| 形态 | 判据 | 处理 |
|---|---|---|
| `LFS_POINTER` | **内容**以 `version https://git-lfs.github.com/spec/v1` 开头（且 < 1KB） | 排除 |
| `SUBMODULE` | `git ls-files -s` 的 mode 是 `160000`（gitlink） | 排除 |
| `NOT_CHECKED_OUT` | lstat 抛 `ENOENT`（与其他 errno 分开） | 排除 |
| `CASE_COLLISION` | 仅大小写不同的一组，**全部能解析且指向同一个 inode** | 整组排除 |

两处判据值得说：

**LFS 用内容判，不用 `.gitattributes`。** smudge filter 跑过的仓库里，同一批路径拿到的是真内容 ——
那时它就是普通文件，不该被排除。判据只能是"磁盘上现在是什么"。

**大小写碰撞用 inode 判，不用 `process.platform === 'darwin'`。** 猜平台会在大小写敏感的 APFS 卷或 Linux 上
误伤两个真正不同的文件。而且只有"全部能解析且同 inode"才算碰撞：如果其中一条 ENOENT，在不敏感的文件系统上
根本不会出现（查找会命中同一个文件），所以它意味着那条路径是真的没检出 —— 该记 `NOT_CHECKED_OUT`，
在这里判成"大小写碰撞"就是又一次归因错误。

## 二、归因顺序也会盖住事实

第一版跑测试，`assets/logo.png` 里的指针没被认出来 —— 因为 `.png` 先被判成了 `BINARY`。

"二进制，跳过了"这句话本身不假，但它恰好盖住了最该说的：**这个仓库用了 LFS，真内容不在本地**。
两句话导向的用户动作完全不同。所以顺序改成：路径类排除（依赖目录、构建产物、疑似 secret）保持原判，
而 `BINARY` 和"没有理由排除"都要再让 LFS 判一次。测试里留了一对对照：同一目录下，指针归 `LFS_POINTER`、
真二进制归 `BINARY`。

## 三、两道闸，不是一道

导入排除是第一道：模型看不见，就不可能改。但万一模型在同一路径上**新建**一个文件呢？
第二道在 `git apply --check`：宿主上那个文件已存在，check 失败，整笔拒绝。
`apply.test.ts` 里直接手写了那条"恶意"补丁验证这件事 —— 断言只有一条真正重要：
**宿主上的指针逐字节不变，`git status` 干净**。

## 四、缺席要对人也对模型说

排除清单里多了四种原因还不够。`summarizeShapes()` 把它们聚合成"形态"级事实，三处消费：

- 导入页每种一条横幅（LFS 用错误色，附 `git lfs install && git lfs pull`）；
- 任务创建时每种发一条 NOTE，进事件流；
- **模型简报**里点名："这些不在快照里，你看不到它们，也不要假设它们存在"。

最后一条和 untracked 那条是同一个道理：模型的世界就是这份快照，不说清楚它会去"修"一个它看不见的文件，
然后把失败归因到别处。

## 五、踩了什么坑

**测试装上了本机有没有 git-lfs 的依赖。** 我写了个 `.gitattributes` 里带 `filter=lfs` 的用例，想表达
"LFS 仓库里 smudge 过的真内容照收"。结果 `git add` 直接失败：`git-lfs filter-process: git-lfs: command not found`
（这台机器的全局 gitconfig 引用了一个已经不在的二进制）。那条用例于是变成了"这台机器装没装 git-lfs"的函数。
而它要断言的本来就与 `.gitattributes` 无关 —— 判据只看内容。改成同一目录下"指针 vs 真内容"两个文件，
断言不变、依赖消失，顺带把测试输出里那两行 `fatal: the remote end hung up unexpectedly` 也清掉了。
**测试输出里的噪音不是无害的**：下次真有一行 fatal，它会被当成老噪音略过。

## 六、数字

`domain.ts` 加四个排除原因；`repo.ts` 加 `isLfsPointer` / `ls-files -s` 的 mode 解析 / errno 分流 / inode 碰撞判定 /
`summarizeShapes`；`agent.ts` 简报、`authority.ts` NOTE、`App.tsx` 四条横幅。
测试 901 → 912（repo +9、apply +2）；typecheck 与 selftest 均过。

## 七、可复用的结论

- **归因错误和静默丢弃一样有害**："读取失败"把三件事说成一件，用户会照着错的方向去修。
- **归因有优先级**：先判出来的那个原因如果盖住了更重要的事实，顺序就是错的。
- **判据要用事实，不要用配置或平台**：LFS 看内容不看 `.gitattributes`，大小写碰撞看 inode 不看 `platform`。
- **能毁掉用户数据的路径要两道闸**：看不见（不进快照）+ 写不进（apply --check 整笔拒绝）。
- **别让测试依赖本机装了什么**，也别容忍测试输出里的噪音。
