用户丢来一张别家产品的计划表截图：「继续接入 Kimi Code、zcode、OpenCode 等
Coding Agent Provider —— 在不改变 Work/Run 生命周期的情况下接入更广泛的 Agent 生态」，
问：我们能做这种想法吗？

量完两边（我方接入面的代码 + 三家 CLI 的官方文档）之后，答案分成三句：

1. **这个想法在我们这里不是新需求 —— 接入面已经存在，且已有两家在表里。**
   「不改变 Work/Run 生命周期」正是 TD-DEC-016 的 candidate→canonical 边界，
   e2e 钉着。
2. **三家候选的判定各不相同**：Kimi 能接（一处平台小改）、OpenCode 能接但先要
   做一个 vendor 设计决定、zcode 按现行合同接不了（桌面 ADE，无 CLI 入口）——
   但它背后的目标（接 GLM）**已经达成**，zhipuai 是内置 API provider。
3. **接入不解锁真正的瓶颈。** 卡住 SPK-010 的是 0 个 API key，多接一家 CLI
   不改变这件事；反而先配两家异构 key 能同时解锁实验和现有 CLI 连接器。

## 一、材料定性

输入是一张**别家计划表的截图**——与 08-28-01 那次同级：无 URL、无采集记录、
真伪未核验。所以它不能支撑任何关于那家产品的事实陈述，只能当**问题清单**：
「这三个名字，我们自己接得了吗？」后面所有结论的证据来自两处：

- **我方代码**（读的是 `prototype/src/core/external/` 全部三个模块 + P1 合同）；
- **三家官方文档**（2026-08-31 当日 Web 核对，来源见文末 —— 会漂，标注为快照）。

## 二、现状：接入面早已存在，模板就是 Claude/Codex

`connector.ts` 的 `DESCRIPTORS` 表是唯一事实源，注释原话：
「**加第三家 CLI = 在表里加一个条目**，不需要再去别处扩枚举」。
表刻意留在代码里（不做配置文件）：argv 形态是安全评审对象。

已有两个条目的证据分级（这决定了后来者能继承什么）：

| 层 | 证据 | 等级 |
|---|---|---|
| 探测层 | ChatGPT.app 内打包 codex 被真实发现（`BUNDLED_CLI` 就是为它加的）；Claude.app 实测不打包 CLI | **真机验证** |
| 隔离与生命周期层 | synthetic HOME、单凭据注入、tree diff、归一化、双审闭环 —— 全部 e2e，**真子进程** | 验证过，但 CLI 本体是 `#!/bin/sh` 假 codex |
| 真实端到端 | 无 | **没跑过 —— 0 个 API key**（与 SPK-010 同一瓶颈） |

已接受的残余（devlog 08-19-05）：argv 随 CLI 版本漂移 → 表现是
FAILED/TIMED_OUT，**不会假绿**；identityDigest（路径+版本）变化会作废旧同意。

## 三、接入契约（从现有两家提炼，六条硬要求）

| # | 要求 | 依据 |
|---|---|---|
| 1 | 非交互入口，prompt 走 **stdin**，退出码即状态来源 | 合同 :18 只认「可验证的非交互 CLI」；argv 载 prompt 会进程可见 |
| 2 | 纯 API key 认证，**单一环境变量**注入 | synthetic HOME 整份替换环境，登录态一概不可见（设计如此） |
| 3 | `--version` 在隔离环境下可跑 | identityDigest 是探测与同意作废的基石 |
| 4 | 作者模式：只写 cwd、编辑无需交互批准、最好自带沙箱 | candidate 目录 + tree diff→MutationPlan 双保险 |
| 5 | vendor 可判定 | 异构审核是硬不变式（`SAME_VENDOR_REVIEW_DENIED`） |
| 6 | 逐家准入评审（terms/版本/网络行为） | 合同 :18「能运行某个命令 ≠ 已准入」 |

## 四、逐家判定

### Kimi Code CLI —— ✅ 能接，三家里最顺

当日核对到的事实：

- `kimi --print` 非交互模式，prompt 走 `--prompt` 或 stdin —— 与 `claude -p` 同形；
- `KIMI_API_KEY` 环境变量可覆盖配置文件里的密钥；
- provider/model 选择**要求 `~/.kimi/config.toml`**，纯环境变量不够。

vendor = `MOONSHOT`（枚举已有），`moonshot-cn` 已是内置 API provider
（`MOONSHOT_API_KEY`）—— 凭据 audience 直接复用。

**需要的平台改动（一处，小）**：描述符形状加一个「向 synthetic HOME 播种
最小配置文件」的钩子。synthetic HOME 是我们造的一次性目录，播我们自己的
`config.toml`（provider/model 钉死、key 引环境变量）不破坏隔离语义 ——
隔离挡的是**用户的**真实配置与登录态，不是平台自己的注入。声明式为宜
（`seedFiles: [{relPath, content}]`），不给任意函数：保持「表可被安全评审」。

**实测项（接作者角色前必须回答）**：`--print` 下文件编辑的批准语义 ——
有没有等价于 `acceptEdits` 的非交互放行，文档没写。**审核方角色（只读、
空 cwd）没有这个问题，可先行。**

估算：描述符条目 + 播种钩子 + 照 `connector.test.ts` 模式补负向测试 ≈ 1 天。

### OpenCode —— ⚠️ 能接，但先要做一个真设计决定

当日核对到的事实：

- `opencode run` 非交互；`--format json` 出事件流；`--model provider/model`；
- `--auto`：自动批准未被明确拒绝的权限（可与播种的权限配置组合成
  「编辑放行、Bash 拒绝」）；
- 密钥支持环境变量与 `.env`；凭据文件在 XDG data 目录（synthetic HOME 隔离覆盖）。

**设计决定（阻塞项）**：OpenCode 是 provider 无关的，而 `DESCRIPTORS`
**每个连接器固定一个 vendor** —— 异构不变式与出站披露都建立在这上面。两个方案：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 一模型一条目 | `opencode-deepseek`、`opencode-glm` 各占一行，model 钉死在 argv 里 | 零形状改动、审计面不变；条目会随想接的模型线性膨胀 |
| B. 描述符带路由参数 | 形状加 `routeParam`，vendor 从 `provider/model` 推导 | 一个条目吃所有模型；但「vendor 由运行时输入决定」动了异构判定的地基，且 argv 不再是纯字面量 —— 安全评审面变大 |

**倾向 A**：与「表是唯一事实源、argv 不做运行时拼接」的既有纪律一致；
膨胀问题等真的要接第三个模型时再说（今天一个都还没接）。
但这是设计决定，落地前应过一遍人的判断。

**实测项**：① stdin 收 prompt（文档只演示 argv 形态，contract 要求 stdin）；
② `--auto` + 播种权限配置能否精确到「编辑放行、Bash 拒绝」；
③ 启动时拉取 models.dev 的网络行为（进准入评审清单——首启需网、离线行为、
是否自更新）。

估算：设计决定 0.5 天 + 实现与测试 1–2 天，且 ① 若不成立需重新评审入口形态。

### zcode —— ❌ 按现行合同接不了；但目标其实已达成

当日核对到的事实：ZCode 3.0 是**桌面 ADE**（Mac/Windows GUI），官方文档
无 CLI 入口、无 headless 模式、无终端用法。

这正是我们已经处理过的 Claude.app 情形：探测如实报
`PRESENT_NOT_AUTOMATABLE`，remediation 指向 API。GUI 自动化被合同 :18/:149
明令禁止 —— 不是「披露一下就能做」。

**但接 zcode 的目的是接 GLM 生态，而那已经完成**：`zhipuai` 是内置 API
provider（`ZHIPU_API_KEY`，vendor=ZHIPU），今天就能当实现方或交叉审核方，
零行代码。计划表上这一项对我们的正确措辞是「GLM：已支持（API）；
zcode CLI：等它存在」。

不建议的灰区路径：Claude Code CLI 指向 Z.ai 的 Anthropic 兼容端点 ——
claude 二进制 + 智谱凭据，vendor 归属进 UNVERIFIABLE（devlog 08-21-03：
推不出厂商不该被写成已异构）。真要做也是单独的设计决定，不是顺手活。

## 五、优先级：先配 key，再接 CLI

按「动手前先量」的纪律倒一次序：接 CLI 不解锁任何被卡住的问题 ——
SPK-010 要的是**两家异构 API key**，而 key 一到位，现有的 Claude/Codex
连接器和 A/B 实验**同时**解锁。所以：

1. **P0：配两家异构 API key**（如 DeepSeek + Moonshot/智谱任一）——
   解锁 SPK-010 + 现有连接器真实端到端；
2. P1：Kimi 审核方角色（含播种钩子）—— 顺路验证 Moonshot 生态；
3. P1.5：Kimi 作者角色（先实测 `--print` 编辑批准语义）；
4. P2：OpenCode（先过方案 A/B 决定 + 三个实测项）;
5. 观察：zcode 出 CLI 再加条目 —— 探测架构是动态的，成本是一个表条目。
