# 一个门禁设计，我改了三次

> 开发记录 · 2026-08-07 · RepoPilot

这篇不讲技术，讲一个「安全设计」怎么从正确变成难用、又怎么改回来。
过程有点丢人，但可能是这个项目里最有参考价值的一段。

## 版本一：硬墙

产品文档里写着（PRD-PROJ-002）：

> 导入只接受固定 commit 的 tracked-only immutable snapshot；dirty/untracked 默认 `BLOCKED`

理由充分：快照要能唯一对应一个 base SHA，否则验证基线和补丁都失去意义。
别人拿到你的补丁，得能从那个 commit 重建出同样的起点。

于是我这么实现：

```ts
const status = git(hostPath, ['status', '--porcelain']).trim();
if (status) {
  throw new RepositoryImportError(
    '工作区有未提交改动，首个切片只接受干净的固定 commit',
    'DIRTY_WORKTREE',
    lines.join('\n'),
  );
}
```

自我感觉良好。

然后用户拿真实仓库一试，界面卡在「正在导入快照…」不动了。

## 卡住的其实是另一个 bug

先说这个，因为它更常见。

用户点「+ 授权本地仓库」，选了目录，然后**什么都没发生**。

```tsx
const pickProject = async () => {
  const { project } = await call('project.pick', {});
  if (!project) return;
  setProjects((prev) => [...prev, project]);
  setSelectedProject(project);
  setImported(null);
  // ← 漏了：从来没有调用 importProject
};
```

只有点侧栏里**已存在**的项目才会真正导入。新授权的走的是另一条路径，我漏了一步。

而 `SnapshotPanel` 的判断是：

```tsx
if (!imported) {
  return <div className="empty">正在导入快照…</div>;
}
```

**「没有结果」被渲染成了「正在进行」。** 于是永远转圈。

这个模式在 React 里太常见了：用 `data === null` 表示 loading。它在「一定会有结果」
的场景下没问题，但只要存在「可能永远没结果」的分支，它就是个 bug 工厂。

改成判别联合：

```tsx
type ImportState =
  | { status: 'idle' }
  | { status: 'importing' }
  | { status: 'done'; snapshot; profile; candidates }
  | { status: 'blocked'; code; message; detail; candidates; subPath }
  | { status: 'failed'; message; detail };
```

类型层面就不可能再退化成无限 spinner。

## 版本二：默认阻断，但可以显式越过

修好卡死之后，用户看到了真正的阻断信息：

```
工作区有 118 项未提交改动（DIRTY_WORKTREE）
```

反馈是三个字：**「不要卡死」**。

我回头看 PRD 原文，发现自己读漏了两个字：

> dirty/untracked **默认** `BLOCKED`

「默认阻断」和「永远不给走」不是一回事。我把前者实现成了后者。

于是版本二：阻断依旧，但带上「可越过」标记和越过入口。越过之后**如实标注**：

```ts
export type SnapshotBaseKind = 'CLEAN_COMMIT' | 'DIRTY_WORKTREE';

export interface RepositorySnapshot {
  readonly baseKind: SnapshotBaseKind;
  readonly dirtyFileCount: number;
  // ...
}
```

道理是：dirty 快照**仍然是不可变、内容寻址的**，验证基线依然成立。
失去的只是「base 能被他人重建」这一点。这该标注，不该禁止。

同时发现这个仓库是 monorepo，根目录不是 Vite 形态，于是又加了子包选择：

```
[selftest] PASS 默认导入 → BLOCKED DIRTY_WORKTREE overridable=true
                            子包候选=[apps/web✦, apps/api, packages/rule-engine, packages/shared]
[selftest] PASS 子包 apps/web → 49 文件 · profile=VERIFIED · 命令=[build,test,typecheck]
```

技术上挺漂亮。用户的反馈是：

> 我觉得 不用那么麻烦，不管他是什么仓库 导进来 确认 信任 当前的这个整个项目就可以查看 并操作了

## 版本三：门禁全拆，只守住一处

第二次被打回，我才想明白问题出在哪。

我一直在优化**「怎么让用户绕过门禁」**，而用户想要的是**「一开始就别设这道门」**。

选中目录本身就是信任手势。用户已经用系统的原生目录选择框，明确指定了这个目录 ——
再问一遍「你确定吗」，是把设计者的焦虑转嫁给用户。

于是版本三，导入侧的业务门禁全部拆掉：

| 情况 | 版本一 | 版本三 |
|---|---|---|
| dirty worktree | 拦死 | 直接进，标 `DIRTY_WORKTREE` |
| 非 git 目录 | 拦死 | 直接进，标 `NO_VCS` |
| 不是 Vite/React/TS | 不让建任务 | 随便建，`supportStatus` 只是信息 |
| monorepo | 要先选子包 | 整仓直接用，想切子包也行 |
| 检测不出命令 | 死路 | 自己填一条 argv |
| 一条验证命令都不选 | 不让提交 | 照跑，进未验证模式 |

只剩三种物理性失败：目录读不了、里面没文件、超容量。

```ts
/**
 * 导入只在**物理上做不到**时失败：目录不存在、里面没有可用文件、超出容量。
 *
 * 仓库脏不脏、是不是 git、是不是 Vite —— 都不再是门禁。用户选中目录
 * 就是信任手势，剩下的由 RepoPilot 如实标注，而不是拦住不让用。
 */
export type ImportBlockCode = 'PATH_UNREADABLE' | 'EMPTY_TREE' | 'CAPACITY_EXCEEDED' | 'GIT_FAILED';
```

## 但有一处没让

门全开了，那「成功」还剩什么含义？

答案是把约束**从入口移到出口**：

```
有通过的验证 + 用户接受  →  SUCCEEDED
只有用户接受            →  ACCEPTED_UNVERIFIED
```

新增一个终态，而不是放宽旧终态。你照样能接受任何补丁，只是系统不会替你说
「这是被证明过的」。

这个位置的好处：**它不阻止任何人做任何事，但它不会说谎。**

同时，所有越过默认行为的事实都写进事件日志，不只是当时那一次点击：

```ts
this.emit(record, 'RUN_CREATED', `任务已创建：${task.goal}`, {
  baseKind: snapshot.baseKind,
  dirtyFileCount: snapshot.dirtyFileCount,
  subPath: snapshot.subPath || null,
  profileSupportStatus: effectiveProfile.supportStatus,
  verificationCommands: input.verificationCommandIds,
});

if (snapshot.baseKind === 'DIRTY_WORKTREE') {
  this.emit(record, 'NOTE',
    `基线是工作区快照而非干净 commit（${snapshot.dirtyFileCount} 项本地改动）：` +
    `补丁的 base 无法被他人从 ${snapshot.baseSha.slice(0, 12)} 重建`);
}
```

三个月后回头看这个 Run，你能知道它是在什么条件下跑的。

## 哪些门该守，哪些不该

复盘下来，判据其实很清晰：

**该守的门：越过之后系统会说假话。**

- 没有任何验证命令 → 不能声称 `SUCCEEDED`（改成新终态，不是拦人）
- 模糊匹配 → 不能声称「改对了那一处」
- 空数组 `every()` → 不能声称「全部通过」

**不该守的门：越过之后只是用户自己承担后果。**

- dirty worktree → base 不可重建，标注即可
- 非 Vite 仓库 → 验证命令照样跑，退出码照样真实
- 没选验证命令 → 终态如实降级

我把第二类当成第一类来守，做了两轮无用功。

## 一个反直觉的观察

版本一「更安全」吗？

不见得。它把用户挡在门外，用户就去用别的工具了 —— 那个工具很可能连
`baseKind` 都不记录。**一个没人用的安全设计，安全收益是零。**

版本三看起来更宽松，但它实际提供的保障更多：因为用户真的会用它，
而它记录的每一条事实都在。

## 可以带走的

1. **区分「默认阻断」和「禁止」。** 文档里的「默认」两个字是有分量的。
2. **`data === null` 不等于 loading。** 有失败分支的地方都该用判别联合。
3. **约束尽量放在出口，不放在入口。** 入口拦人成本高、体验差；出口如实标注既不挡路又不撒谎。
4. **需要放宽时，加新状态，别改旧语义。** 旧语义一旦松动就再也收不回来。
5. **用户说「太麻烦」的时候，先别急着优化流程。** 可能整个流程都不该存在。
