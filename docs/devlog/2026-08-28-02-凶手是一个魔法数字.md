# 凶手是一个魔法数字

上一轮我登记了 `ASM-026`——「上下文压力缓解在首切片就承重」，证据是三个 Run 全部
死于规划阶段、输入 token 从 1206 涨到 32207（26 倍）。这一轮准备动手实现压缩层。

**动手前先去量了一下真实数据。三件事全翻了。**

## 翻掉的第一件：materialize 早就实现了

我以为要从零建"大输出物化成 artifact + 有界预览"。打开 `src/core/tools.ts` 第 13 行：

```ts
export const PREVIEW_MAX_BYTES = 4_000;
export const PREVIEW_MAX_LINES = 120;
```

而且第 49 行的注释写着「输出投影：Gateway 自己计量，**不信任工具自报 truncated**」，
带 `artifactRef` 存全文、带 `coverageNote` 报截断。**TD §9.10 的第一层，两个月前就落地了。**
我差点重建一遍。

## 翻掉的第二件：prune 在真实数据上只有 6%

第二层是"裁掉已被后续事实替代的旧观察"。最直觉的规则是"同一文件读了 N 次只留最后一次"。
去数 `run_074bde20cdec4d7dab29` 的 36 次工具调用：

```
总调用 36 · 唯一 (name,args) 35 · 重复组数 1
  2 x ('fs_read', '读取 pnpm-lock.yaml')
```

**36 次里只有 1 对重复。** preview 合计 64876 字符，去重能省约 4000，**6%**。
为 6% 去动"发给模型的历史"这种高风险区域，不划算。

## 翻掉的第三件（真凶）

那就再往下查：这个 Run 到底是被什么掐死的？读它的 `state.json`：

| 维度 | 用掉 | 上限 | 占比 |
|---|---|---|---|
| token | 218453 | 600000 | **36%** |
| 工具调用 | 36 | 80 | **45%** |
| 模型轮次 | 12 | **40** | **30%** |
| 末轮上下文 | 32k | 模型窗口（远大于） | — |

**三项预算全都远未耗尽。** 32k 上下文对任何现代模型都是宽裕的。

死因在 `agent.ts:483`：

```ts
const maxPlanTurns = Math.min(12, deps.task.budget.maxModelTurns);
```

一个**没有任何文档依据的硬编码**。PRD/TD 里检索"规划轮次上限"——查无此条。
它的后果是：**用户把 Run 预算调到 40 轮，规划仍然只有 12 轮，用户的选择对规划完全无效。**

再看模型当时在干嘛（最后 8 次调用）：

```
fs_read  packages/shared/src/index.ts
fs_read  .github/workflows/ci.yml
fs_read  AGENTS.md
fs_read  pnpm-lock.yaml          ← 4KB 截断
fs_grep  /packages/shared|rule-engine|zod|@types\/node/ in pnpm-lock.yaml
fs_read  pnpm-lock.yaml          ← 又读一次
fs_grep  /^  packages\/(shared|rule-engine):|…/
```

它在**收敛**，不是打转：精确追查依赖版本，撞上 4KB 截断后改用 grep 绕行。
然后在第 12 轮被常数掐断，而预算还剩 70% 的轮次。

顺带一个次生效应：**截断越紧，轮次消耗越多**——模型为一个大文件花了 4 次调用。
两个上限互相牵制，这条记进了 `Q-026`。

## 改了什么

### 一、规划子预算从常数改为派生

```ts
const maxPlanTurns = Math.max(2, Math.floor(deps.task.budget.maxModelTurns / 2));
```

守卫的**意图**保留了（一个死活不提交计划的模型不能烧光整个预算），变的是它的来源：
现在跟随用户的预算选择，一半给规划、一半留给执行与自修复。执行阶段本来就没有子上限
（`for (;;)` + 全局 `budgetExceeded()` 守卫），所以放宽这里不会饿死后面。

**比例本身仍是开放问题**（`Q-026`）。没有模型 key 就做不了对照实验，所以这次只做
"派生 + 如实报数"，**不声称"这样更好用"**。

### 二、触顶文案报数

旧文案：`规划阶段用满 12 轮仍未提交计划`。它把最关键的事实藏了——**其他预算根本没用完**。
用户因此无从判断该放宽预算还是该收窄任务。新文案点明子预算的来源、其他预算的状态，
并给出下一步。这是不变式 8「省略要报数」在文案上的应用。

### 三、状态栏显示绑定约束（顺带回答了"usage bar 怎么加"）

那次失败时，状态栏显示的是「预算 36%」——**报了最舒服的那个数字**，
而真正掐死它的维度完全不可见。**一个只报最舒服数字的仪表，比没有仪表更误导。**

改成挑四个维度里比值最大的那个显示、带名字（「工具 36/80」），
另外三项进 title（省略要报数）。≥90% 才变色，平时不喊。

这也是"要不要加一个 usage bar"的答案：我们不缺一条 bar，缺的是**让仪表指向真正绑定的
约束**。至于那个项目里的其他格子——速率限制、剩余额度、美元成本——BYOK 下套餐余量在
供应商侧，`App.tsx` 里早就写着「这里不猜」；照搬会变成编数字。

## 踩了什么

**差点建了一个不需要的子系统。** 如果按上一轮的结论直接开工，会花掉一大块工作量去实现
第二层 prune（6% 收益），重建第一层 materialize（已存在），而真凶——一行 `Math.min(12, …)`——
原封不动。做完还会觉得"我们实现了 P0 的上下文缓解"。

救我的是上一轮自己写下的那句 **"因果未证"**：当时观测到 token 26 倍增长与失败共存，
我很想写"上下文膨胀导致失败"，但证据只支持"共存"。ASM-026 的验证方式里也老实写了
「无变化即反证，此时应先查提示词与**轮次上限**」。这次的测量正好走到那一条。

**教训：观测到相关性时，把因果留空的那点克制，两周后会还你一个不做错的机会。**

## 诚实边界

- 本轮**没有证明**"放宽上限就能成功"——那需要模型 key 做对照，我们没有。
  能证明的只有"它不是资源不足"和"文案此前藏了这个事实"。
- `PRD-CONV-002`（三层缓解）的 P0 定性**不变**：它对长会话仍是正确设计，
  只是**不是首切片失败的主因**，实现优先级下调。
- `ASM-026` 已按"压缩不是主因"结案，证据 `EVI-PLANNING-CAP-001` 登记为 `VERIFIED`
  （数字可由用户本机的 Run 记录重算）。

64 文件 / 1153 测试全绿，typecheck 干净，selftest ALL PASS。
