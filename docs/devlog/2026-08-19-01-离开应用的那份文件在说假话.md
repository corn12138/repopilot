# 离开应用的那份文件在说假话

> 开发记录 · 2026-08-19 · RepoPilot

上一轮把 `prototype/` 逐条对照 PRD/TD 审了一遍（73 条发现，全部经过"默认判不成立"的
对抗复核）。13 条 high 里有四条有个共同点：**改动很小，但改之前应用会对用户说一句
字面为假的话**。这一轮只做这四条，别的都不碰。

## 1. `verified: yes`，写在一份验证失败的补丁上

```ts
const verified = p.verificationRunId !== null;
// ...
`# verified:    ${verified ? `yes (${p.verificationRunId})` : 'NO — accepted without machine verification'}`
```

判定只看 `verificationRunId` **非空**。而挽救封存恰恰把**失败的那次**验证 id 传进来了
（`sealSalvagePatch` → `sealPatch(..., final, ...)`，`final.passed === false`）。

于是：验证失败 → 现场被封存成挽救补丁 → 用户点「保存为 .patch」→ 文件头逐字打印
`# verified:    yes (ver_xxx)`。这份文件是会离开应用的，几天后回看、发给同事，
它和一份真正通过验证的补丁长得一模一样。

`decidePatch` 那边其实是对的 —— 它查 `record.verifications.some(v => v.id === ... && v.passed)`。
两处判定不同源，错的那处偏偏在唯一会离开应用的载体上。

修法：文件头与 `decidePatch` 用同一条判定，三态措辞：

```
yes (ver_x)                                                    ← 那次验证真的 passed
NO — verification ver_x FAILED (salvaged patch; not accepted as success)
NO — accepted without machine verification / no machine verification was run
```

测试：在挽救路径的 e2e 里加了对导出文件头的断言。**先把修法临时改回旧判定跑一遍，
确认断言真的会红** —— 一条不会红的断言等于没写。

## 2. 用户审批慢一点，批准后立刻「预算耗尽」

`PausableDeadline` 的存在理由写得很清楚：等人审批的时间不算计算预算。它在
`awaitPlanApproval` 处 `pause()`，决定后 `resume()`，TIMED_OUT 确实不会因为审批慢而触发。

但同一个 host 上的 `budgetExceeded()` 和 `charge()` 用的是**没暂停过的原始 `startedAt`**：

```ts
if (Date.now() - startedAt >= lim.maxWallClockMs) return { exceeded: true, ... };
ledger: applyLedgerCharge(record.view.ledger, delta, Date.now() - startedAt),
```

默认 `maxWallClockMs = 20min`，而 `APPROVAL_TTL_MS = 30min` —— 比整个墙钟预算还长。
所以路径**日常可达**：计划 t=2min 生成，用户 t=25min 批准（仍在 TTL 内），
执行阶段第一次 `budgetExceeded()` 立刻命中 → 零动作 → 工作区无变更 → 走 `NO_CHANGES`
分支 → 终态 `FAILED`，文案「模型结束了执行但没有产生任何文件变更」。

真实原因（预算被审批等待吃光）只留在事件流里，**终态归因写到了模型头上**。

修法：`PausableDeadline` 加 `elapsedMs()`（净运行时长），`budgetExceeded` 与 `charge`
都从它取，`Date.now() - startedAt` 的两处口径全部删掉。一个 Run 只能有一种"用了多久"。

测试：黄金路径 e2e 里在批准前故意 `sleep 1500ms`，断言账本 `elapsedMs` 比墙钟少掉
那段延迟。用旧口径跑：`expected 1544 to be less than 334` —— 红了，说明它咬得住。

## 3. 「子进程已随进程退出释放」—— 它没有

验证命令是以 `detached: true` 起的独立进程组，父进程死了它不跟着死。Core 对 SIGTERM
**没有任何处理**（Node 默认直接退出），`killTree()` 只在超时/取消路径上调用。

所以：应用退出 → Core 被 kill → `vite build` 继续以用户身份跑、继续往工作区写。
而重启时 `closeInterruptedRun` 无条件追加：

```
子进程与模型流已随进程退出释放；工作区 仍在磁盘上（gen-7）
```

孤儿还活着的时候，这是一条**伪造的清理事实**。

两处修：

- Core 注册 SIGTERM/SIGINT/SIGHUP → `authority.shutdown()`：同步向所有活动 Run 发 abort
  （runCommand 的 abort 监听里 `process.kill(-pid, 'SIGTERM')` 是同步的），同步追加一条
  持久化事件 `PROCESS_EXIT_SIGNAL`，然后 `process.exit(0)`。全程同步，不等任何 Promise ——
  父进程随时可能连根拔掉我们，能保证的只有"信号发出去了"。
- `closeInterruptedRun` 分两种说：有那条事件 → 「已发 SIGTERM，未确认终止」；没有（崩溃 /
  强杀 / 老版本）→ 「状态未知，可能仍在执行」。模型流是进程内 fetch，可以确定地说"已释放"。

测试用一条真的挂着不退的命令（`hang.mjs` 写下 pid 后 `setInterval`）：
`shutdown()` 之后 `process.kill(pid, 0)` 必须在 5s 内抛 ESRCH —— 断言的是"进程没了"，
不是"发过信号"。重启路径的两个变体各一条：`shutdown()` 后**不让出事件循环**就构造新
Authority（模拟真进程立即 exit、abort 的异步续段永远跑不到），说明必须写"未确认"；
不 shutdown 直接构造新 Authority，说明必须写"未知"，且此刻孤儿确实还活着。

已知不做的：不等 SIGKILL 升级（那是 runCommand 里的定时器，进程马上就退了）。
所以文字只能承诺"发过 SIGTERM"，不能承诺"已终止" —— 措辞照此写死。

## 4. 一个域一个字节都没扫，汇总照样 COMPLETE

```ts
function listFiles(dir) {
  try { return readdirSync(dir, ...) } catch { return []; }
}
```

四个域的枚举函数在 readdir 抛错时一律返回空数组，而 `status()` 只看「有无 FAILED 项」
和「有无被上限截断」。于是 artifacts 目录读不了 → 一项都没检查 → 汇总
`COMPLETE · 已释放 X 字节`。README 自己写的是"任一失败或截断整体只能 INCOMPLETE"。

修法：枚举返回 `{ names, error }`；`error` 非空时在该域根目录上落一条 `FAILED`，
现有的 `failed.length > 0 → INCOMPLETE` 自然接住。预演同样如实 —— 读不了就是读不了，
不因为"没真删"就假装检查过。

## 顺带：一条会随机变红的门禁测试

第一次全量跑 `pnpm test` 时 `App.owner-state.test.tsx:607` 红了一次，单跑 10/10 绿。
按 role 查询要在 jsdom 里遍历整个可达树，满负载并行时一次查询就可能上百毫秒，
`findByRole` 默认 1000ms 会随机超时。

它必须先修：迁移期间每一批都要靠"测试全绿"当验收，一个会随机变红的门禁测试会让
这句话在整个过程里都不可信。修法只是把那两处等待上限显式放宽到 5s ——
放宽的是"愿意等多久"，不是被测行为。之后 8/8 绿。

## 顺带：三个新用例把一个真的交叉污染逼了出来

加完上面那批测试之后，全量跑开始随机红：`文件不存在: src/app.js`、模型脚本对不上
（"期望上下文里有 receiptId"）、`挂起命令没有在预期时间内启动`。三种表现，都指向
"工作区里的文件没了"。

不是 flake，是**真删**。

`RunAuthority` 的构造函数会 `startRetentionSchedule()`：+5s 跑一次 `runSweep('startup')`，
之后每 6 小时一次；另外任何 Run 进终态时也会在 +30s 排一次。产品里这没问题——
一个进程只有一个 Authority。

但 e2e 文件里 `vi.mock('./paths')` 整个文件**共用一个受管数据根**，而每个 `new Harness()`
都是一个新的 Authority。之前这个文件的 Harness 少、用例短，5 秒窗口很难撞上；
我新加的三个用例每个都要再造一到两个 Harness（重启路径要构造"新进程"），
于是好几个 startup sweep 落在了黄金路径那 20 多秒里，把别的用例正在用的工作区、
快照按"孤儿 / 已终态过宽限期"删掉了。

修法是给构造函数加一个显式开关，测试关掉**调度**（不是 sweep 本身，retention 的行为
仍由 `retention.test.ts` 直接测）：

```ts
constructor(push, options: { backgroundRetention?: boolean } = {}) { ... }
```

值得记下来的是它伪装成什么：三种不同的报错、随机出现、单跑必绿、机器空闲时也必绿。
一开始我把它当成了机器负载导致的超时（当时 load average 确实到了 130）。分辨的关键是
报错内容不是"超时"而是"文件不存在"——**超时是"没等到"，文件不存在是"有人动了它"**。
