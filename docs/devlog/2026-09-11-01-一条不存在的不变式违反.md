# 一条不存在的不变式违反

我在风险台账里写：EventStore 写盘失败后「正在违反不变式 3『失败时零写入』」，
理由是 `sealSalvagePatch` 会写工作区。这句话是**错的**。
`sealPatch` 对工作区是只读的。真正的危害比它更隐蔽，也更值得修。

## 一、问题是什么

`store.ts` 的 `append` 原来长这样：

```ts
this.maxSeqSeen += 1;                                  // 水位先推进
const event = { seq: this.maxSeqSeen, ... };
this.cache.push(event);                                // 内存先落定
appendFileSync(this.file, `${JSON.stringify(event)}\n`, 'utf8');   // 这里可能抛
```

写盘抛错时，内存里已经有一条**磁盘上不存在**的事件。我称之为幻影事件。

它有三个后果，按严重度排：

**1. 一个会说假话的一致性检查。** `authority.ts:481` 的 `persist()` 把 `lastSeq()` 当
`eventHighWatermark` 写进 `state.json`。幻影 seq 于是进了快照水位。重启后
`rehydrateRuns` 只做**一个方向**的比较：

```ts
const eventsAhead = events.lastSeq() > s.eventHighWatermark;
```

日志比快照**短**时这个式子是 `false`，于是落到 `evidence: 'INTACT'`。
**系统把「丢了事件」说成「证据完好」。** 对一个以「系统不能说谎」立身的项目，
这比丢事件本身严重得多 —— 丢事件是事故，说完好是谎言。

**2. 收口不可达。** 抢救封存路径自己会 emit。日志锁定时它抛出、被自己的 catch 接住、
catch 里再 emit 又抛一次 —— 异常逃出 `execute` 的 catch-all，而 `execute` 是
`void` 调用的。结果是 unhandled rejection：Run 既拿不到终态，也跑不到 `finally` 里的清理。

**3. 游标把幻影交给界面。** `after(afterSeq)` 会把那条不存在的事件推给 Renderer，
重启后它消失 —— 时间线在两次启动之间自己变了内容。

附带一条自相矛盾：`lastSeq()` 的文档写「事件流最高水位」，实现返回的却是 cache 末元素的
seq（= 文件末行）。日志乱序时两者分叉，而 `persist()` 正是拿它当快照水位。

## 二、我写错的那句话

修之前我在台账里给这条定了性：**违反不变式 3「失败时零写入」**，因为
「`sealSalvagePatch` 写工作区、`persist` 写 state.json」。

动手前我去核 `patch.ts:27-114`。`sealPatch` 的正文是：

```ts
const { authored, generated, deleted } = workspace.changedVsBaseline();   // 读
...
const raw = gitDiffNoIndex(before, after, rel);                            // git diff --no-index，读
...
return { patchId: ..., files, unifiedDiff, digest: ... };                  // 内存里的 PatchArtifact
```

**全是读。** 它不写工作区一个字节。失败路径从来没有碰过用户的副本，
不变式 3（「任何失败路径下工作区必须逐字节不变」）**并没有被违反**。

我写那句话时没有核 `sealPatch`。它听起来对（"封存"这个词暗示写），
它让定性显得更严重（"违反项目存在的理由"），所以它通过了我自己的审查。
这是本轮排查里我**第二次**把未核实的断言写进交付物 —— 上一次是 RISK-04 里
一句不存在的「目标文件已漂移」引用。两次都是同一个形态：**听起来合理的断言
比核过的断言更容易通过审查。**

更正动作：`store.ts` 与 `authority.ts` 的注释、`store.test.ts`、基线文档 §2.3、
风险台账 RISK-05 全改，并在台账里保留一段「本节曾有一处定性错误，已更正」的说明。
**不静默改掉** —— 一条被悄悄修正的错误定性，和一条从没写过的错误定性，
对下一个读者的价值是不同的。

## 三、怎么解决的

### 先落盘，再推进内存

```ts
const seq = this.maxSeqSeen + 1;
const event = { seq, ... };
try {
  appendFileSync(this.file, `${JSON.stringify(event)}\n`, 'utf8');
} catch (err) {
  this.failure = { reason: (err as Error).message, at: nowIso() };
  throw new EventLogUnavailable(this.failure.reason);
}
this.maxSeqSeen = seq;
this.cache.push(event);
```

幻影事件从成因上不可能再产生。

### 故障锁定，而不是重试

失败后本实例**永久拒绝** append，即使文件系统已经恢复可写。

我第一版测试写的是「恢复可写后接着 seq 2 继续」，写到一半发现这个设计是错的：
`EACCES` 这类失败 open 就没成功、一个字节都没写，重试是干净的；
但 `ENOSPC` 下 open 可能已成功、**部分字节已落盘**，重试会接在撕裂行后面，
把一条坏行变成两条 —— 而 `maxSeqSeen` 没推进，意味着重试用的是**同一个 seq**。
按 errno 区分这两者太脆弱（各家文件系统与中间层行为不一致），
所以一律锁定：Run 停下、原因如实报给用户、重启后 rehydrate 读盘上真实的内容。

### 上层要能查，而不是靠捕获异常

新增 `writeFailure()` 与 `refusedAppendCount()`。authority 的收尾用**状态**做判据，
不用异常类型 —— 异常可能在很深的地方被折叠成别的错误，
而「这个 Run 的事件日志已经写不下去了」是一个持续为真的状态。

`execute` 的 catch-all 把这个检查放在**所有分支之前**：

```ts
const journalFailure = record.events.writeFailure();
if (journalFailure) {
  const lost = 1 + record.events.refusedAppendCount();
  this.setStatus(record, 'FAILED', `事件日志写入失败（${journalFailure.reason}）：…`, 'RUNTIME_ERROR');
  return;
}
```

`lost` 是「触发锁定的那一条」加「此后被拒绝的每一条」—— 省略要报数（不变式 8）。

`setStatus` 在日志死掉时跳过 emit 与 persist，但**两条终态不变式检查照常执行**：
日志死了不等于 `SUCCEEDED` 可以不要 verification。

### 测试：真实 syscall，先证明会红

新建 `core/store.test.ts`（这个文件此前**不存在**，而 EventStore 是 Run 事实的唯一持久化载体）。
故障注入用 `chmod 0o444` 让 `appendFileSync` 撞真实的 EACCES，不 mock fs ——
要测的就是「真的写不进去时怎么办」，mock 出来的失败证明不了 syscall 层的行为。

一个前置探测：以 root 运行时 chmod 0o444 **不会**让写入失败。所以模块级先探一次，
无效则 `it.skipIf` **显式跳过** —— 不让它们「绿」过去假装验过。
这正是 AGENTS.md「缺隔离时写入型用例直接 BLOCKED」的同一态度。

在修复前的代码上跑，两条精准变红：

```
× 写失败：cache 与水位都不前进…   store.all() 里多出一条从未落盘的 "这条写不进去"
× 日志乱序时 lastSeq 返回最高 seq   expected 3 to be 7
```

而其余用例全绿 —— 包括「坏行计数」那条，说明既有行为没被我的修复碰坏。

## 四、踩了什么坑

### 坑 1：上面那条不存在的不变式违反

见第二节。教训不是「要更仔细」，而是**哪一类断言需要核**：
凡是「X 会导致 Y」里 Y 是危害陈述的，Y 必须落到具体代码行上读过才能写。
「听起来对」不是证据，「更严重」更不是。

### 坑 2：`emit` 该不该吞掉这个错误

第一版我让 `emit` 捕获 `EventLogUnavailable` 后静默继续。写完就发现这是错的：
如果吞了，agent 循环不知道自己该停，会继续改代码、跑验证，
而整条证据链一片空白 —— **比抛错更糟**。抛错至少会让 run 停下来。

所以 `emit` 让它抛，由 `execute` 的 catch-all 统一收口。
代价是 `finally` 里那条 CLEANUP_SUMMARY 也会抛、在 finally 中抛出会覆盖正常返回 ——
所以 `finally` 也要加守卫。三处守卫（catch-all、setStatus、finally）缺一不可，
少一处就是 unhandled rejection。

### 坑 3：我差点把「半修」当成「修好」

只把 `cache.push` 挪到写盘之后，测试就绿了。但故障锁定、上层守卫、`lastSeq` 修正
都还没做 —— 而那时会多出一条「已修复」的记录挡在那里，让下一个人不再看。
外部方案 §6.2 自己写了这句警告：「不能仅把 `cache.push` 调到后面就宣称完成恢复保障」。
**测试绿 ≠ 修好**，这条在这个仓库里已经被验证过太多次了。

## 五、可复用的结论

**1. 单向的一致性检查是一个会说假话的开关。**
「事件比状态新」只覆盖了崩溃窗口的一半方向。任何一致性判定都要问：
**反方向错了会显示成什么？** 如果显示成「正常」，那它就是一个谎言生成器。

**2. 「封存」不等于「写」。** 我被 `sealSalvagePatch` 的名字骗了。
函数名描述意图，不描述副作用；核副作用要读正文。

**3. 故障态要可查询，不要靠异常类型。** 异常会被折叠、被捕获、被转换；
「这个资源已经不可用」是一个状态，任何时刻都能查，也更难被无意绕过。

**4. 锁定比重试诚实，当你无法区分「没写」和「写了半截」。**
按 errno 分支是一种精确的幻觉 —— 它假设你能可靠地知道字节有没有落盘。
多数时候你不能。

**5. 先证明测试会红。** 两条红 + 其余全绿，同时证明了「缺陷存在」和
「既有行为没被碰坏」。只跑修复后的绿，你什么都不知道。
