# 同一道检查，只装在了一半的入口上

> 开发记录 · 2026-08-09 · RepoPilot

今天修的七条 P0 里，有三条是同一个形状：

- 补丁写回宿主仓库要求"必须先被接受" —— 检查只存在于 React 组件的一个布尔量里
- API 地址必须是 https —— 校验只装在 `saveCustomProvider`，`updateProfile` 那条路没有
- 模型出站要过 preflight —— `invoke()` 过，`testProfile()` 完全不过

三处都不是"忘了写检查"。检查**都写了**，而且写得挺认真。问题是同一件事有两个入口，
只在其中一个上装了闸。

## 一、唯一会写用户文件的动作，门禁在 React 里

`applyPatchToRepo` 是整个原型里唯一会写用户仓库的路径。它的注释这么写：

```ts
/**
 * 把补丁真正应用回宿主仓库。
 *
 * 这是整个原型里**唯一**会写用户仓库的路径，因此：
 *   - 交给 `git apply` 做，不自己实现 patch 应用逻辑。
 *   - 先 `--check` 干跑一遍；有任何一处冲突就整笔拒绝，不做部分应用。
 */
```

它确实校验了 patchId、evidence 没损坏、不是 NO_VCS、补丁非空、diff 没被截断。
唯独**不看 Run 的状态**，也不校验 digest。

而"必须先被接受"这条唯一的守卫，在这里：

```tsx
// renderer/views/RunDetail.tsx
<PatchReview
  patch={patch}
  canDecide={run.status === 'AWAITING_PATCH_REVIEW'}
  accepted={run.status === 'SUCCEEDED' || run.status === 'ACCEPTED_UNVERIFIED'}
  onError={onError}
/>
```

`accepted` 控制的是**按钮显不显示**。

于是这条路是通的：Run 进入 `AWAITING_PATCH_REVIEW` → 用户点「拒绝」→ 状态变 `BLOCKED`，
但 `record.patch` 仍留在内存里 → 任何一次 `patch.export {mode:'APPLY_TO_REPO'}`
就把**被拒绝的补丁**写进用户仓库。触发方式可以是一个渲染 bug、一次重放、
或者直接从 devtools 走 `window.repopilot.request`。

对比一下同一个文件里的 `decidePatch`，它是**真校验** digest 的：

```ts
if (record.patch.patchId !== input.patchId || record.patch.digest !== input.patchDigest) {
  return { run: record.view, reason: '补丁已变化，请刷新后重新决定' };
}
```

所以不是不懂，是这条路径漏了。

### 修法：抽成纯函数，让它能被单测打穿

```ts
/**
 * 「补丁能否写回宿主仓库」的门禁判定 —— 抽成纯函数，因为它是整个原型里
 * 唯一会写用户文件的动作的最后一道闸，必须能被单测直接打穿，而不依赖
 * 起一整个 RunAuthority + git 仓库。
 *
 * 两条规则：
 *   1. 必须先被接受（terminalFacts.patchAcceptanceId 存在）。REJECT / REQUEST_CHANGES
 *      走 BLOCKED、terminalFacts 为 null，被这条挡住。
 *   2. 请求里的 digest 必须与实际补丁一致；未提供一律拒绝 —— 写宿主仓库不接受"就地信任"。
 */
export function checkPatchApplyGate(input: {
  status: RunStatus;
  patchAcceptanceId: string | null;
  actualDigest: string;
  requestedDigest: string | undefined;
}): PatchApplyGate {
  if (!input.patchAcceptanceId) {
    return {
      ok: false,
      reason: 'NOT_ACCEPTED',
      detail: `补丁尚未被接受（当前状态 ${input.status}）。请先在补丁审查里接受，再写回仓库。`,
    };
  }
  if (input.requestedDigest === undefined) {
    return { ok: false, reason: 'DIGEST_REQUIRED', detail: '写回宿主仓库必须携带补丁 digest 以校验一致性' };
  }
  if (input.actualDigest !== input.requestedDigest) {
    return { ok: false, reason: 'PATCH_CHANGED', detail: '补丁已变化，请刷新后重新确认' };
  }
  return { ok: true };
}
```

为什么用 `patchAcceptanceId` 而不是判状态字符串？因为它是 `decidePatch` 的 ACCEPT 分支
唯一写下的东西：

```ts
record.view = {
  ...record.view,
  terminalFacts: {
    verificationRunId: verified ? record.patch.verificationRunId : null,
    patchAcceptanceId: acceptanceId,        // ← 只有 ACCEPT 才有
  },
};
```

REJECT 和 REQUEST_CHANGES 都走 `BLOCKED`，`terminalFacts` 保持 null。
判"有没有受理凭证"比判"状态是不是那几个字符串"更难写错。

顺带把 `patchDigest` 加进协议，**只有写仓库那条模式要求它**：

```ts
/**
 * `patchDigest` 是调用方看到的补丁摘要。写宿主仓库这条路径**必须**带上它，
 * 由 Core 侧比对（与 `patch.decide` 同一道校验）—— 「被应用的东西」必须等于
 * 「被审查/接受的东西」。SAVE_FILE / COPY 不写仓库，可以不带。
 */
'patch.export': {
  req: { runId: string; patchId: string; mode: 'SAVE_FILE' | 'COPY' | 'APPLY_TO_REPO'; patchDigest?: string };
  res: PatchExportResult;
};
```

7 条单测，其中一条专门盯门禁顺序：

```ts
it('门禁顺序：未接受优先于 digest —— 被拒补丁即使 digest 对也进不来', () => {
  const g = checkPatchApplyGate({
    status: 'BLOCKED', patchAcceptanceId: null,
    actualDigest: DIGEST, requestedDigest: DIGEST,
  });
  expect(g.ok).toBe(false);
  if (!g.ok) expect(g.reason).toBe('NOT_ACCEPTED');
});
```

## 二、https 校验只装在自定义 provider 那条路上

`saveCustomProvider` 校验得很仔细，注释还记着上一次踩的坑：

```ts
// 前缀正则会放过字符串 'https://' 本身，normalizeBaseUrl 随后把它变成 'https:'
// 存进配置，之后每次调用都拼出一个无效地址。用 URL 解析真正校验。
let parsed: URL;
try { parsed = new URL(input.api.trim()); } catch { throw new Error('API 地址不是合法 URL'); }
if (parsed.protocol !== 'https:' || !parsed.host) {
  throw new Error('API 地址必须是带主机名的 https:// 地址');
}
```

但用户改内置 provider 的地址走的是另一条路 —— `updateProfile`：

```ts
this.settings[providerId] = {
  modelId: patch.modelId?.trim() || current.modelId,
  baseUrlOverride:
    patch.baseUrlOverride === undefined ? current.baseUrlOverride : patch.baseUrlOverride.trim(),
};
```

只 `.trim()`。而 `normalizeBaseUrl` 又**显式放行** http：

```ts
if (url.origin === 'null' || (url.protocol !== 'http:' && url.protocol !== 'https:')) {
  return trimmed;
}
```

于是在设置页填 `http://attacker.example`，会被规范化成 `http://attacker.example/v1`
写进 `model-profiles.json`。

## 三、preflight 只装在 invoke 上

配好之后点「测试连接」：

```ts
async testProfile(profileId: string, signal: AbortSignal) {
  const profile = this.getProfile(profileId);
  const apiKey = this.keyFor(profile.providerId);
  // …
  await this.adapterFor(profile.wire).call(
    { system: '…', messages: [ /* ping */ ], tools: [], maxOutputTokens: 16, temperature: 0 },
    { apiKey, modelId: profile.modelId, signal, baseUrl: profile.origin },
  );
```

直接调 adapter，**完全不经过 `preflight()`**。而 `INSECURE_ORIGIN` 那道检查只存在于
`preflight` 里，`preflight` 只在 `invoke()` 里跑。

`x-api-key: ctx.apiKey` 就这么以明文 TCP 发到用户填的任意主机去了。

更要命的是这件事**不留任何痕迹**：`testProfile` 返回的只有 `{ok, detail, latencyMs}`，
不产出 `ModelEgressManifest`、不 emit `MODEL_INVOCATION`。事件流里查不到
「凭据曾被送去 http://attacker.example」。

而 `ModelGateway` 的类注释白纸黑字写着：

```ts
 *   - 每次调用必须声明 purpose；planning / execution / self-fix 都走同一条链路，
 *     没有"辅助调用免计费"的旁路。
 *   - 每次调用（包括被阻断的）都产出一条 ModelEgressManifest；
```

**注释是对的，代码有旁路。** 这跟昨天审计出的「注释说重启能恢复，代码只读 projects.json」
是同一个病。

### 修法：两处补齐，并且给探针一个归属

`updateProfile` 补上同一道校验（直接对齐 `saveCustomProvider` 的写法）：

```ts
// 非空覆盖地址必须是带主机名的 https —— 与 saveCustomProvider 同一道校验。
// 之前这里只 trim，normalizeBaseUrl 又放行 http:，于是 http://attacker 能被存进配置，
// 之后「测试连接」把 API key 明文发出去。空串表示清除覆盖，回落到环境变量/默认地址。
if (nextOverride) {
  let parsed: URL;
  try { parsed = new URL(nextOverride); }
  catch { throw new ModelCallError('API 地址不是合法 URL', 'BAD_REQUEST'); }
  if (parsed.protocol !== 'https:' || !parsed.host) {
    throw new ModelCallError('API 地址必须是带主机名的 https:// 地址', 'BAD_REQUEST');
  }
}
```

但光补这一处不够 —— 地址还能从**环境变量**来（`resolveOrigin` 会读 `apiEnv`），
那条路绕过 `updateProfile`。所以 `testProfile` 自己也得挡：

```ts
// 明文出站前拦住：即使 origin 来自环境变量（绕过 updateProfile 的校验），
// 也不能把 key 通过 http 发出去。testProfile 之前完全不过这道门。
if (!profile.origin.startsWith('https://')) {
  record({ ...baseManifest, sent: false, blockReason: 'INSECURE_ORIGIN', /* … */ });
  return {
    ok: false,
    detail: `拒绝测试：地址不是 https（${profile.origin}）。明文 HTTP 会暴露 API Key。`,
    latencyMs: null,
  };
}
```

至于记账：连通性探针不属于任何 Run，但它带真实凭据出站，所以给它一个自己的 purpose
和一个自己的日志：

```ts
export type ModelInvocationPurpose =
  | 'PLANNING' | 'EXECUTION' | 'SELF_FIX' | 'COMPACTION' | 'TITLE_SUMMARY'
  /** 设置页「测试连接」的连通性探针 —— 不属于任何 Run，但同样带真实凭据出站，
   * 因此同样要产出 ModelEgressManifest（没有"辅助调用免记账"的旁路）。 */
  | 'CONNECTIVITY_TEST';
```

```ts
/**
 * 把不属于任何 Run 的出站清单追加到全局 egress 日志。
 *
 * Run 内的调用清单进各自的事件流；设置页的连通性测试没有 Run 归属，
 * 但同样带真实凭据出站，必须留痕。写盘失败只记录不抛 —— 记账失败不该
 * 让「测试连接」这个动作本身崩掉，但也绝不能静默当作没发生。
 */
export function appendEgress(manifest: ModelEgressManifest): void {
  try {
    mkdirSync(dirname(PATHS.egressLog), { recursive: true });
    appendFileSync(PATHS.egressLog, `${JSON.stringify(manifest)}\n`, 'utf8');
  } catch (err) {
    console.error('[core] 写 egress 日志失败', err);
  }
}
```

四种结局（缺凭据 / 不安全地址 / 成功 / 失败）各记一条。注意即使是**合法 https 官方地址**，
「测试连接」也是一次带真实凭据、事后应当可查的出站 —— 这条修复的必要性不只在 http 场景。

```

× updateProfile: baseUrlOverride 必须是 https > 不是合法 URL 的覆盖地址被拒绝                1ms
× testProfile: 不经 http 送 key，且每次都留 egress 痕迹 > origin 是 http（经环境变量注入）：
  即使有 key 也拒绝发送，记 INSECURE_ORIGIN                                              134ms
Tests  3 failed | 3 passed
```

（同一天 A2 又给两个适配器补了 `adapters.test.ts` 30 条，`core/model` 从 45 条到 81 条 ——
那部分单独写在 [两个 wire 的翻译层](2026-08-09-06-两个wire的翻译层.md)。）

没有守卫的话，key 真的会发出去。

manifest 里也断言了不能带明文 key：

```ts
// manifest 里绝不能出现明文 key
expect(JSON.stringify(log)).not.toContain('sk-should-not-leak');
```

## 为什么三处是同一个病

把三条并排看：

| 能力 | 装了闸的入口 | 漏掉的入口 |
|---|---|---|
| 补丁必须被接受才能写仓库 | `RunDetail.tsx` 的按钮可见性 | Core 的 `applyPatchToRepo` |
| API 地址必须 https | `saveCustomProvider` | `updateProfile` + 环境变量 |
| 出站必须过 preflight | `invoke()` | `testProfile()` |

共同点是：**能力有两个入口，检查跟着"主入口"走了，副入口被当成"内部调用"忽略。**

而副入口恰恰是更容易被绕过的那个 —— 它通常更简单、更少人看、更少测试。

判断方法我总结成一句话：**如果一个检查回答的是"允不允许"，它就必须在权威层；
如果它回答的是"要不要显示"，才可以在界面层。** 前者放界面就是把安全属性
挂在渲染逻辑上，而渲染逻辑天生是可以被绕过的（重放、devtools、状态不同步）。

## 可以带走的

1. **数一数一个能力有几个入口。** 检查漏掉的那个通常是"看起来内部"的副入口。
2. **"允不允许"必须在权威层，"显不显示"才能在界面层。** 混了就是把安全挂在渲染上。
3. **注释里写了"没有旁路"，就去数一遍到底有几条路。** 注释与代码不一致是最贵的一类缺陷。
4. **门禁抽成纯函数。** 它是最该被单测打穿的东西，不该必须起一整个服务才能测。
5. **看单测耗时也能发现问题。** 一条本该是"拒绝"的用例跑了 134ms，说明它真的联网了。
6. **判"有没有受理凭证"比判"状态字符串是不是那几个"更难写错。**
