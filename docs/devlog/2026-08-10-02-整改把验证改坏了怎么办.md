# 整改把验证改坏了怎么办

> 开发记录 · 2026-08-10 · RepoPilot

第二个模型审出 3 条阻断，第一个模型进场整改，整改完一跑验证：build 红了。
此刻封存补丁还绑着整改前那次通过的验证，工作区里躺着整改后的坏代码 ——
用户打开文件树，看到的应该是哪一个？

[上一篇讲交叉审核](2026-08-09-05-让两个模型一写一审.md)结尾如实写了口子：
只跑 1 轮审核就交回人工，`remediations` 恒为 0。这次把 PRD 允许的完整循环接上
（**2 次审核 + 1 次整改**，硬上限），上面这个问题是整个循环里最不能含糊的一处。

## 循环长什么样

```
审核#1 ──无阻断──→ REVIEWER_PASSED
   │
   有阻断
   ↓
整改（实现方 route，标准执行通道）
   │ 没动文件 ──→ NO_DELTA
   ↓
重新验证 ──失败──→ 恢复工作区 → NO_PROGRESS
   │ 通过
   ↓
重新封存 ── digest 没变 ──→ NO_DELTA
   ↓
审核#2 ──无阻断──→ REVIEWER_PASSED
   │
   有阻断 ──阻断没减少 / 指纹重现──→ NO_PROGRESS
   └──否则──→ COUNTER_EXHAUSTED
```

无论哪个出口，终点都是 `AWAITING_PATCH_REVIEW`。审核方说"过"不等于验证通过，
更不等于可以接受 —— 这条从上一篇起就没松过。

两个结构性决定：

**流程写成直线，不写 while。** 上限 2+1 不该是"循环恰好走不满"，该是结构上
走不满。`CROSS_REVIEW_LIMITS` 仍然出现在条件里，但那是防御，不是驱动。

**语义和机制分层。** 收敛语义（何时整改、何时早停、counter 怎么走）在
`agent.runCrossReviewCycle`，重验/重封存/恢复工作区是调用方注入的钩子：

```ts
export interface CrossReviewCycleHooks {
  readonly reverify: (() => Promise<VerificationRun>) | null;
  readonly reseal: (verification: VerificationRun | null, truncationReason: string | null) => PatchArtifact;
  readonly adoptPatch: (patch: PatchArtifact) => void;
  readonly restoreWorkspace: () => void;
}
```

authority 绑真实现，测试绑替身 —— 于是「整改后验证失败必须恢复」这种最难
端到端复现的分支，可以在单测里用一个 `reverify: 'fail'` 的假钩子直接钉死。

## 核心决策：恢复用前进，不用倒退

整改后验证失败，有三条路：

1. **照样封存**。验证失败的树被封成补丁 —— 直接违反"补丁必须绑定它自己的
   验证"这条底线，第一个排除。
2. **不封存也不恢复**。补丁维持整改前版本，但工作区已经是整改后的坏代码 ——
   文件树展示的是一个被放弃的现场，和补丁指的不是同一棵树。静默的不一致，
   排除。
3. **恢复工作区**。补丁和文件树重新指同一棵树。

选 3，但工作区没有回滚 API：`commit` 的 CAS 只认 `staged === active + 1`，
代号单调前进。要不要加一个"把 active 指回去"的倒退操作？

不要。两个不变式都依赖代号单调：read receipt 的失效判定是"绑定旧代即作废"，
倒退会让同一个代号出现两次，"旧代"这个概念就浑了；`stage()` 按 `active + 1`
分配目录，倒退后再前进会撞上残留目录。所以恢复做成**前进式**的 —— 像
git revert，不像 reset：

```ts
restoreGeneration(sourceGen: number): { generation: number } {
  // gen-2 的整改坏了，恢复 gen-1 → 产生一个内容等于 gen-1 的 gen-3
  const next = this.active + 1;
  cloneTree(this.generationPath(sourceGen), path);
  if (!this.commit(next, this.active)) throw new Error(...);
  return { generation: next };
}
```

代价是一次 APFS clone（写时复制，几乎不占空间）。被放弃的整改现场留在
gen-2 里可以事后查看，恢复本身走的还是同一个 CAS —— 没有为恢复开任何后门。

## 三个容易做错的小口

**counter 记"消耗"，不记"产出"。** 整改的模型被调了但一个文件都没改
（它完全可以认为发现不成立）——`remediations` 记 1。记 0 看起来"谦虚"，
实际是把一次真实发生、真实花了 token 的调用从账上抹掉了。

**中断不清账。** 整改中途被取消，第一轮审核已经真实发生 —— 循环设计成
全函数（total）：可预期的异常折叠进 stopReason，已完成的 rounds 保留返回。
最初版本是让异常直接往上抛，authority 兜底 —— 那样 rounds 会在抛出瞬间丢掉，
`reviewerInvocations` 记 0，账就错了。

**归因分侧。** 同一个 `EgressBlocked`，发生在审核调用里是
`REVIEWER_UNAVAILABLE`，发生在整改调用里就只能是 `ERROR` + 注明实现方 route
—— 旧代码的 catch 不分侧，整改侧的出站阻断会被标成"审核方不可用"，
排查的人会去查错误的那半边。

另外整改没有任何特权：走标准执行通道，一样 receipt + exact-span、一样整笔
失败零写入、一样计入同一个预算账本。简报只喂阻断项，提示性发现不进 ——
不给"顺手优化"开口子，范围蔓延本身就是审核要抓的东西。

## 反向验证

+20 条测试（15 条循环/整改语义 + 5 条 `restoreGeneration`），全量 493 通过。
按惯例挑两条最贵的守卫各拆一次，确认它们真的在管事：

拆掉"验证失败必须恢复"（注释掉 `hooks.restoreWorkspace()`）：

```
× runCrossReviewCycle：终止语义与 counter > 整改后验证失败 → 恢复工作区、补丁维持原样、NO_PROGRESS
Tests  1 failed | 19 passed (20)
```

把进展判定改成只看数量（去掉 `|| repeated > 0`）：

```
× runCrossReviewCycle：终止语义与 counter > 第 2 轮指纹重现 → NO_PROGRESS，即使阻断数减少了
Tests  1 failed | 19 passed (20)
```

第二条守的场景值得展开：第一轮 2 条阻断，第二轮 1 条 —— 数量减了，看起来有
进展；但那 1 条和上轮是同一个指纹（平台按 severity/file/range/evidence 算的，
不信模型自报）。同一个问题被指出两次而没被修掉，这不是进展，是空转。
数量判据会放行它，指纹判据不会。

## 还没做的

- authority 侧的真实接线（真封存、真验证、真恢复串起来）没有独立 e2e，
  靠 typecheck + 钩子级单测。README 如实标注。
- 真实双模型下整改的**质量**（改得对不对、会不会越改越糟）只能真跑才知道 ——
  确定性测试钉的是平台语义，不是模型判断力。
- 一个既有语义原样保留：第一轮 `INCONCLUSIVE` 且零阻断会被映射成
  `REVIEWER_PASSED`。"没下结论"和"没发现问题"其实不是一回事，这次没动它，
  记在这里。

## 可以带走的

1. **不变式依赖编号单调时，恢复要做成前进式的。** 倒退式回滚动的不是一个
   指针，是所有把"编号更大"当作"更新"的隐含假设。git revert 优于 reset
   的理由，在工作区代际上同样成立。
2. **把循环语义和执行机制分开，早停分支才测得起。** "整改后验证失败"在
   端到端里要真实模型 + 真实构建失败才能复现；钩子注入后它是一行
   `reverify: 'fail'`。
3. **counter 记消耗不记产出，中断不清账。** 账本的用途是事后对账 ——
   "调了但没产出"和"没调"必须可区分，"中断前发生过什么"不能因为中断而消失。
   这是[「删除也要诚实」](2026-08-08-04-删除也要诚实.md)在另一个方向上的重演。
