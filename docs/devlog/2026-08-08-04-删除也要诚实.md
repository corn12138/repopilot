# 删除也要诚实

> 开发记录 · 2026-08-08 · RepoPilot

这个 Agent 每跑一个任务，都会把整个仓库克隆一份到隔离工作区。
每次改动再克隆出新的一代。跑十个任务，磁盘上就是十份仓库副本 —— 而且它们
从来不回收。

所以要做保留期清理。看起来是个很无聊的功能：加个定时器，删过期文件，完事。

实际写下来，一半的代码在处理**"不该删的绝不能删"**，另一半在处理
**"删不干净时怎么说"**。

## 一刀切是错的

第一版设计是"所有数据 30 天后删"。规则简单，但很快发现不合理：

各类数据的**成本和价值完全不匹配**。

| 数据 | 磁盘成本 | 保留价值 |
|---|---|---|
| 工作区副本 | 极高（每 Run 一份整仓克隆） | Run 结束后只剩考古价值 |
| 快照 | 中（多个 Run 可共用） | 有 Run 引用它就还有用 |
| 证据（事件/状态/补丁/验证） | 低（都是文本） | 这就是"可审计"承诺的载体 |
| artifact（工具大输出） | 中 | 随所属 Run |

用同一个 TTL 管它们，等于让最没价值的东西（工作区）和最有价值的东西（证据）
活得一样久。所以改成分类保留：

```ts
export const DEFAULT_RETENTION: RetentionPolicy = {
  evidenceDays: 30,
  workspaceGraceMinutes: 60,   // Run 终态后 1 小时回收工作区
  maxItemsPerSweep: 200,
  maxDurationMs: 5_000,
};
```

工作区在 Run 终态后一小时回收，证据留 30 天，快照按引用计数，
artifact 无引用即收。

那一小时的宽限期是有用意的：Run 刚跑完你可能还想翻翻文件树，
立刻删掉体验很差。

## 三条不能删的红线

**运行中的 Run，工作区绝不能碰。**

```ts
if (!info.terminal) {
  items.push(keep('WORKSPACE', runId, 'KEPT_REFERENCED', 'Run 尚未进入终态'));
  continue;
}
```

注意 `AWAITING_PATCH_REVIEW` 不是终态。这意味着"跑完了等你审补丁"的 Run
工作区会一直留着 —— 你随时可以翻文件树对照 diff。

**非终态的 Run，证据无论多老都不删。**

```ts
it('非终态的 Run 无论多老都不删 —— 它可能只是在等你审批', () => {
  const id = mkRun(newId('run'));
  const s = sweep(refs({ [id]: { terminal: false, ageDays: 400 } }), POLICY, NOW);

  expect(s.items.find((i) => i.domain === 'RUN_EVIDENCE' && i.target === id)!.outcome)
    .toBe('KEPT_REFERENCED');
});
```

400 天也不删。一个非终态的 Run 意味着"还有事没了结"，按时间删掉它是错的。

**保留天数被夹到安全区间。**

```ts
// 夹紧到安全区间：0 天等于立刻删掉刚跑完的 Run，那是脚枪
evidenceDays: clamp(stored.evidenceDays ?? 30, 1, 365),
```

`0` 是个特别容易手滑填进去的值，而它的语义是"跑完即焚"。

## 引用计数，不是时间

快照和 artifact 不按时间删，按**还有没有人用**：

```ts
private liveReferences(): LiveReferences {
  const snapshots = new Set<string>();
  const artifacts = new Set<string>();

  for (const [runId, record] of this.runs) {
    if (record.snapshot?.snapshotId) snapshots.add(record.snapshot.snapshotId);
    for (const tc of record.toolCalls.values()) {
      if (tc.artifactRef) artifacts.add(tc.artifactRef);
    }
    if (record.patch) artifacts.add(record.patch.patchId);
  }
  return { runs, snapshots, artifacts };
}
```

引用集合由权威层提供，而不是让清理器自己去扫。理由是：只有 `RunAuthority`
知道 Run 的终态，以及 toolCall / patch 引用了哪些 artifact。让清理器反向依赖
authority 会绕成环。

清理顺序也有讲究：

```
1. 工作区   —— 最占地方、最没争议
2. 过期证据 —— 删完之后一批快照会失去最后的引用者
3. 快照     —— 此时引用计数才是准的
4. artifact
```

## 「删完了」这句话不能随便说

PRD 里有一条要求：无法证明完整删除时必须标 `DELETION_INCOMPLETE`。
实现下来，这条比想象中重要。

清理有三种"没干完"：某一项删失败、被数量上限截断、被时间上限截断。
三种都不能报成功：

```ts
const failed = items.filter((i) => i.outcome === 'FAILED');
const incompleteReason =
  failed.length > 0
    ? `${failed.length} 项删除失败：${failed.map((f) => f.target).join(', ')}`
    : truncated;

const summary: PurgeSummary = {
  …
  // 有失败或被截断，一律 INCOMPLETE —— 无法证明删干净就不说删干净
  status: incompleteReason ? 'INCOMPLETE' : 'COMPLETE',
  incompleteReason,
};
```

这个三元表达式颠倒一下，就会把"没删干净"报成"删干净了"，而且不会有任何
运行时报错 —— 属于必须有测试盯着的那类代码。下面的用例就是干这个的。

而且**逐项**都要有结果，不是一句"清理完成"：

```ts
export interface PurgeItemResult {
  readonly domain: 'WORKSPACE' | 'SNAPSHOT' | 'RUN_EVIDENCE' | 'ARTIFACT';
  readonly target: string;
  readonly outcome: 'DELETED' | 'KEPT_REFERENCED' | 'KEPT_NOT_DUE' | 'FAILED';
  readonly bytesFreed: number;
  readonly reason: string | null;
}
```

四种 outcome 里有两种是"留着"，而且分开：`KEPT_REFERENCED`（还有人用）
和 `KEPT_NOT_DUE`（还没到期）是完全不同的原因，用户看到的提示也不一样：

```
Run 尚未进入终态
终态后宽限期未过（还剩 43 分钟）
还剩约 12 天到期
仍被至少一个 Run 引用
```

这样**后端**任何时候都能回答「这个东西为什么还在 / 为什么没了」——
注意目前只到后端，界面上还没有出口，见文末「还没做的」。

## rmSync 不抛不等于删掉了

```ts
function remove(domain, target, path, reason): PurgeItemResult {
  const bytes = dirSize(path);
  try {
    rmSync(path, { recursive: true, force: true });
    // 删完再确认一次 —— rmSync 不抛不等于目录真的没了
    if (existsSync(path)) {
      return { domain, target, outcome: 'FAILED', bytesFreed: 0, reason: '删除后路径仍然存在' };
    }
    return { domain, target, outcome: 'DELETED', bytesFreed: bytes, reason };
  } catch (err) {
    return { domain, target, outcome: 'FAILED', bytesFreed: 0, reason: (err as Error).message };
  }
}
```

`force: true` 会吞掉一部分错误。加一句 `existsSync` 复查，成本几乎为零。

## 一个容易被自己坑到的地方

计算目录大小时不能跟随 symlink：

```ts
for (const entry of readdirSync(path, { withFileTypes: true })) {
  if (entry.isSymbolicLink()) continue; // 不跟随，否则会把宿主 node_modules 算进来
  total += dirSize(join(path, entry.name));
}
```

工作区里的 `node_modules` 是指向宿主仓库的 symlink（详见
[三进程架构](2026-08-07-01-给agent做ide的三进程架构.md) 里的取舍）。
跟着它走，一个工作区能算出几百 MB —— 报给用户的"释放了 800MB"完全是假的，
而且真去 `rmSync` 那条链路会删掉宿主的依赖。

## 删掉之后要让 UI 知道

清理器删了东西，内存里的 Run 记录也要跟着走：

```ts
for (const item of summary.items) {
  if (item.outcome !== 'DELETED') continue;
  if (item.domain === 'RUN_EVIDENCE') {
    this.runs.delete(item.target);
  } else if (item.domain === 'WORKSPACE') {
    const record = this.runs.get(item.target);
    if (record) {
      // 工作区没了，但 Run 记录还在：如实记一笔，
      // 别让用户以为文件树只是加载失败
      record.events.append(
        record.view.attemptId,
        'CLEANUP_SUMMARY',
        `工作区副本已按保留策略回收（释放 ${formatBytes(item.bytesFreed)}）`,
        { domain: 'WORKSPACE', trigger },
      );
    }
  }
}
```

第一条：证据被删了，Run 也要从列表消失 —— 否则 UI 上挂着一个已经没有任何
磁盘数据支撑的条目，那是另一种形式的说谎。

第二条：工作区被删但 Run 还在，往事件流里补一笔。否则用户点开文件树看到报错，
会以为是 bug。

## 什么时候跑

```ts
/** 启动时跑一次，之后每 6 小时一次。不做高频轮询。 */
private startRetentionSchedule(): void {
  // 启动时延后一点，别和 rehydrate、首屏加载抢 I/O
  setTimeout(() => this.runSweep('startup'), 5_000).unref?.();
  const timer = setInterval(() => this.runSweep('scheduled'), 6 * 60 * 60 * 1000);
  timer.unref?.();
}
```

外加 Run 进入终态后 30 秒补一次（那时它的工作区通常是最大的一块）。

三个细节：`unref()` 让定时器不阻止进程退出；启动时延后 5 秒避开首屏 I/O；
单轮有数量和时间双上限，避免一次扫描卡住主流程。

## 测试

15 个用例，几乎全部是"不该删的没被删"：

```
运行中的 Run，工作区绝不能删
刚终态、宽限期未过 → 保留（这样用户还能浏览文件树）
终态且过了宽限期 → 删掉，并报出释放的字节
没有对应 Run 的孤儿工作区 → 回收
29 天的 Run 保留，并说明还剩几天
31 天的 Run 删除
非终态的 Run 无论多老都不删 —— 它可能只是在等你审批
仍被引用的快照不删 / 无引用的快照删掉
被工具调用引用的 artifact 不删，孤儿删
全部成功 → COMPLETE
被数量上限截断 → INCOMPLETE 且说明原因
逐项结果齐全 —— 不是一句"清理完成"
保留天数被夹到安全区间
```

其中一条专门盯着"截断不等于失败"：

```ts
it('被数量上限截断 → INCOMPLETE 且说明原因', () => {
  for (let i = 0; i < 5; i += 1) mkWorkspace(mkRun(newId('run')));
  const s = sweep(refs({}), { ...POLICY, maxItemsPerSweep: 2 }, NOW);

  expect(s.status).toBe('INCOMPLETE');
  expect(s.incompleteReason).toMatch(/处理数达上限/);
  // 关键：截断不等于失败，已处理的那些是真的处理了
  expect(s.items.length).toBeLessThanOrEqual(2);
});
```

还有一条检查逐项结果的完整性 —— 这条防的是有人图省事把 `items` 退化成计数：

```ts
for (const item of s.items) {
  expect(item.domain).toBeTruthy();
  expect(item.target).toBeTruthy();
  expect(['DELETED', 'KEPT_REFERENCED', 'KEPT_NOT_DUE', 'FAILED']).toContain(item.outcome);
  expect(item.reason).toBeTruthy();
}
// 汇总数字必须和逐项结果对得上，不能各算各的
expect(s.deleted).toBe(s.items.filter((i) => i.outcome === 'DELETED').length);
expect(s.bytesFreed).toBe(
  s.items.filter((i) => i.outcome === 'DELETED').reduce((n, i) => n + i.bytesFreed, 0),
);
```

## 还没做的

**这不是安全删除。** `rmSync` + APFS 不保证数据不可恢复。真要做删除证明，
需要落盘加密 + 销毁 data key，那是另一个量级的工作。目前 UI 上不能声称
"已彻底删除"，只能说"已从本地回收"。

**也不覆盖 Provider 侧。** 本地删干净了，你发给模型 API 的那些上下文
还在人家那儿按人家的政策留着。这两件事必须分开说 —— 这是 PRD-CONV-004
反复强调的一点。

**还没有界面出口。** `retention.get` / `update` / `sweepNow` 在协议和主进程白名单里
都通了，但 Renderer 一行都没接：设置页没有保留策略面板，`retention.swept` 事件
也没人消费。也就是说本文列的那些逐项 reason 目前只存在于内存对象里 —— 用户看不到，
30 天这个数字也改不了，只能从 Run 时间线里那条 `CLEANUP_SUMMARY` 知道工作区被回收了。
对一篇叫「删除也要诚实」的文章，这条不写出来就自相矛盾了。

## 可以带走的

1. **分类保留，别一刀切。** 成本和价值不匹配的数据用同一个 TTL，
   等于让最没用的和最有用的活得一样久。
2. **"还有人用"和"还没到期"是两种不同的保留原因**，分开报，用户才能理解。
3. **删除结果要逐项**，并且失败 / 截断都只能是 `INCOMPLETE`。
   "无法证明删干净"和"删干净了"是两回事。
4. **`rmSync` 不抛不等于删掉了**，加一句 `existsSync` 复查。
5. **算目录大小别跟随 symlink**，否则数字是假的，删除路径是危险的。
6. **删完要通知上层**，让内存状态和 UI 跟着走，别留一个没有数据支撑的空壳条目。
