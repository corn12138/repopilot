# 隔离的自检，照旧写你的真实凭据

> 开发记录 · 2026-08-13 · RepoPilot

`pnpm selftest` 一直是被封印的。阶段审计里写着：

> selftest 仍使用基于真实 HOME 的默认数据根，会启动 retention，并在没有可靠全局
> `try/finally` 的情况下创建 credential / project / snapshot / run。
> **在修复前，不得为了"补一个 ALL PASS"而在真实用户数据根运行 selftest。**

这轮就是去解封它。思路很直接：跑之前建一个一次性目录，`finally` 里删掉。

```ts
function prepareSelfTestRoot(): void {
  selfTestOwnedRoot = mkdtempSync(join(tmpdir(), 'repopilot-selftest-'));
  process.env[DATA_ROOT_ENV] = selfTestOwnedRoot;
}
```

时机是硬要求，我在注释里特意写了：

```ts
/*
 * 在 Core 启动**之前**准备隔离根。
 * `core/paths.ts` 与 `main/credentials.ts` 都在模块加载时就把 DATA_ROOT 定下来了，
 * Core 又是带着 process.env 快照 fork 出去的。晚一步设置，隔离就只在 Main 生效。
 */
```

`app.whenReady()` 里先 `prepareSelfTestRoot()` 再 `startCore()`，跑起来：

```
[selftest] 已创建一次性 data root：/var/folders/.../repopilot-selftest-yeVYVA
[selftest]   ✓ dataRoot(READY) /var/folders/.../repopilot-selftest-yeVYVA
...
[selftest] ALL PASS
```

Core 的 doctor 检查自己报出了隔离根。看着是对的。

## 收尾检查抓到了我自己

我给收尾加了一段残留检查——不是为了发现 bug，是为了在删掉临时目录**之前**报个数，
因为先删再数出来的零是自证的。它顺手也核对了凭据文件落在哪：

```
[selftest] 隔离根内种子数据：runs=1 workspaces=1 snapshots=1 artifacts=0 · credentials=隔离外（异常）
[selftest] FAIL 凭据文件落在隔离根之外：/Users/…/Library/Application Support/RepoPilotPrototype/credentials.bin
```

Core 用了隔离根，Main 自己没有。原因就写在我上面那段注释里，只是我把它用在了错误的地方：

```ts
// credentials.ts
const FILE = join(resolveDataRoot(), 'credentials.bin');   // ← 模块加载时算一次
```

**Main 的模块在 `app.whenReady()` 之前就全部加载完了。** 我为 Core 想到了这一层
（fork 时带 env 快照，所以先设置就有效），却没想到 Main 自己的模块加载更早。
Core 隔离成功，Main 照旧读写用户真实的 `credentials.bin` —— 而自检里有
`credentials.setKey('anthropic', 'sk-ant-selftest-ABCD1234')`。

改成调用时解析：

```ts
function storageFile(): string {
  return join(resolveDataRoot(), 'credentials.bin');
}
```

## 那这次跑到底动了我的 key 没有

跑之前我存了一份 SHA-256 清单（442 个文件）。跑完之后 diff：

```
真实 data root：442 个文件逐字节不变
```

没动。但**这是运气**，不是设计保证：自检末尾有还原逻辑（`before` 存在就写回，
不存在就 removeKey），而 macOS 的 safeStorage 加密是确定性的，
所以「写入 → 还原」之后密文字节恰好一致。如果那台机器上原本有 anthropic key，
它会先被测试值覆盖再被还原；中途崩一次，用户的 key 就没了。

补了回归测试，钉的是"调用时解析"这条语义本身：

```ts
it('路径在每次调用时解析，而不是在模块加载时冻结', async () => {
  process.env[DATA_ROOT_ENV] = first;
  const credentials = await import('./credentials');
  expect(credentials.storagePath()).toBe(join(first, 'credentials.bin'));

  // 模块已经加载过了 —— 换根之后它必须立刻跟上，这正是当初出错的地方。
  process.env[DATA_ROOT_ENV] = second;
  expect(credentials.storagePath()).toBe(join(second, 'credentials.bin'));
});
```

根因不只是那一行。真正的问题是**受管数据根有两个独立的拼装点**：
`core/paths.ts` 从 homedir 拼一遍，`main/credentials.ts` 又拼一遍。
漏改一处隔离就失效。现在合并成 `shared/dataRoot.ts` 一个解析点。

## 同一轮的另外两件事

### 每个请求都必须有明确结局

`callCore` 原来是这样：

```ts
return new Promise((resolve) => {
  pending.set(requestId, resolve);
  core!.postMessage({ kind: 'request', requestId, method, payload });
});
```

Core 退出时有兜底，但 **Core 活着而这个请求永远不回应**时没有 —— 那个 Promise
永远挂着，UI 上表现为"点了没反应"，与"正在处理"无法区分。

抽出一个账本，四选一：成功、失败、超时、Core 退出。超时后要立刻把条目摘掉，
否则迟到的响应会把已经交付的 TIMEOUT 改写成成功：

```ts
const entry = this.pending.get(requestId);
if (!entry) return;          // 已超时 → 丢弃这次迟到的响应
```

抽出来还有个附带好处：它不 import electron，所以能真被测到 ——
超时、迟到响应、进程退出这三条路径恰恰是最难在 GUI 里复现的。

### 逐方法校验，和一个我差点写错的校验器

Main 原来只有三道检查：协议版本、方法白名单、总字节数。方法名对但 payload 是
`null`、数组、错类型、超深嵌套的请求，会被原样转交给 Core，由 Core 用
`String(payload.x)` 去猜调用者的意思。

补逐方法合同的时候有两个地方值得记：

**第一，不能先 `JSON.stringify` 再量长度。** structured clone 允许循环引用，
`JSON.stringify` 遇到环直接抛，会把 `ipcMain.handle` 变成一个 rejected invoke，
Renderer 那边只看到一句无来源的报错。

**第二，校验器不能用递归。** 一个两万层深的 payload 会把递归校验器自己的栈打爆 ——
那样"校验超深嵌套"的代码本身就成了那个崩溃点。用显式栈：

```ts
const stack: Array<{ node: unknown; depth: number }> = [{ node: payload, depth: 1 }];
while (stack.length > 0) { ... }
```

仓库里其实有 zod（Core 用它校验模型输出）。没用它，理由就是上面第二条：
递归下降的校验器解决不了栈的问题。分两层——先用显式栈证明结构可安全遍历，
再逐字段核对——之后，字段那层简单到不值得为它把依赖引进 `shared/`。

## 可以带走的

1. **模块加载时算出来的路径，早于任何运行时配置。** 凡是"启动前设置环境变量来改行为"
   的机制，都要检查每一个消费方是在**加载时**还是**调用时**读它。
   我为子进程想到了这一点，却漏掉了自己所在的进程。
2. **同一个事实有两个拼装点，就等于有一天会不一致。** 这次是数据根被拼了两遍，
   隔离只生效了一半。
3. **收尾检查要在清理之前报数。** 先删再数出来的零证明不了任何事。
   这次的 bug 不是推理出来的，是这段"多余的"检查抓到的。
4. **"这次没出事"和"设计上不会出事"是两回事。** 442 个文件逐字节不变是真的，
   但它靠的是确定性加密加还原路径跑到了，不是隔离生效了。区分清楚，
   否则下一次就会把运气当保证。
5. **校验超深输入的代码，自己不能怕深。** 递归校验器面对递归攻击是同归于尽。
