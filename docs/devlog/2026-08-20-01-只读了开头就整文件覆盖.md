# 只读了开头，就整文件覆盖

> 开发记录 · 2026-08-20 · RepoPilot

`fs_read` 超过 120 行就只把开头给模型 —— 但**照样签发覆盖全文的 receipt**。
于是任何一个稍大的源文件，模型只看见前 120 行，也能合法地发起 `REPLACE_WHOLE_FILE`：
receipt 校验通过（文件确实没变）、整笔提交成功、**尾部被静默删除**。
这是 08-17 审计里那条 `MUT-receipt-coverage-vs-truncated-read`。这一刀连着把"验证命令不进账本"一起切了。

## 一、digest 相同证明不了"你看过全文"

receipt 里原本有 `fileDigest` + `byteLength`，apply 时比对 digest —— 它能证明的只有"文件自读取以来没变"。
它证明不了的是"提交者看过多少"。这两件事在整文件替换面前差别是致命的：模型拿着一份只覆盖前 120 行的认知，
提交一份"完整的新内容"，剩下 280 行就没了，而且 diff 看起来完全正常（就是删了 280 行）。

所以给 receipt 加一个字段：

```ts
coverage: 'FULL_BLOB' | 'BYTE_RANGE'
coveredBytes: number   // 实际给出去的原始内容字节数
```

`issueReceipt(path, coverage, coveredBytes?)` 由**调用方声明**覆盖范围 —— 因为只有调用方知道自己把多少交出去了。
`fs_read` 在投影之后签发：预览被截断就只能签 `BYTE_RANGE`。mutation 引擎里加一条：

```ts
if (op.kind === 'REPLACE_WHOLE_FILE' && receipt.coverage !== 'FULL_BLOB') {
  throw new Blocked('RECEIPT_COVERAGE_INSUFFICIENT', `…只覆盖 ${receipt.coveredBytes}/${receipt.byteLength} 字节…`);
}
```

exact-span 不受限：它的 `oldText` 由引擎在**真实全文**里校验唯一命中，改哪一段是可证明的。
这也是给模型的出路 —— 被拒时的错误消息直接写"请改用 REPLACE_EXACT_TEXT_SPAN"，`fs_read` 的返回里也提前写了
`coverage=BYTE_RANGE（只展示了前 120/400 行）—— 这个 receipt 不能用于 REPLACE_WHOLE_FILE`。规则要在它撞墙之前就告诉它。

外部作者那条路不受影响：`normalizeCandidate` 是平台自己读了 active 的全文、也拿到了 candidate 的全文新内容，
`FULL_BLOB` 名副其实。我在那里把参数显式写出来，而不是靠默认值。

端到端那条断言最直白：400 行的文件，fs_read 只给前 120 行，模型据此整文件替换 → 被拒 → `line 399` 还在。

## 二、顺带：平台自己跑的命令，此前不进任何账

同一份审计还记着：`runVerification` 直接调 `runCommand`，绕过 `dispatchTool` —— 没有 ToolCall 记录、没有风险闸门、不计预算。
用户在时间线上看不到平台跑了什么，账本上也看不到它花了多少。

`runVerification` 现在接一个 recorder（结构上就是 `AgentHost` 的子集，agent 和 authority 各把自己的 host 传进去），
每条命令留一条 `verify_command` ToolCall：`argsSummary` 带 role（`BASELINE` / `VERIFICATION`）、commandId、argv，
`resolution` 由命令结果的判别联合映射（EXIT_ZERO→SUCCEEDED、CANCELLED→CANCELLED、其余 FAILED），
执行完计一次账。**取消不计账**（没跑完的东西不该收费），**未登记的命令也留记录**（它没消失，只是没跑成）。

再加一道纵深防御：验证只执行 R1。用户手填的命令在登记时就只放 R1 进来（昨天的 I-1），这里再挡一次 ——
万一将来有别的路径往 profile 里塞命令，它也不能借"验证"这个身份绕过分级。拒绝不是通过：记 `SPAWN_ERROR`，验证不会 passed。

## 三、踩了什么坑

**1. 三条测试红了，但它们是对的。** `expect(host.toolCalls).toHaveLength(0)`（"零工具副作用"）、
`toolCalls.filter(t => t.risk !== 'R0')`（"规划阶段没有 R1 副作用"）—— 基线验证现在是一条 R1 的 ToolCall，全中。
这些断言的**意图**是"没有模型发起的副作用"，而它们用"有没有 R1 记录"来近似。近似在语义变化时失效了。
改法不是放宽断言，是让它更准：`filter(t => t.toolName !== 'verify_command')`，并在其中一条里补上正向断言 ——
基线那条 ToolCall 必须存在、role 是 BASELINE、resolution 是 FAILED、账本 +1。**修红测试时要问它想说什么，别只让它变绿。**

**2. 取消路径绕过了记录器。** `signal.aborted` 时那条 early-push 没走 `record()`，于是"取消"这件事在 ToolCall 里不存在。
测试先红的正是这条。取消也要留记录 —— 用户要能看出"这一步没跑"，而不是它凭空消失。

**3. 时间线会把同一件事说两遍。** verify_command 有了 ToolCall，Transcript 就会给它画一行，
而下面的验证块本来就逐条列了命令与结果。重复展示和静默丢弃是一枚硬币的两面：
所以合并进"另有 N 条事件没有单独成行，但内容已并入对应的行或卡片"，并点名说明 —— 报数，不重复，也不消失。

**4. `afterEach(cleanup)` 在别人的 describe 里。** 我新加的 describe 没有 cleanup，第二条用例在第一条的 DOM 上跑，
`getByText(/pnpm build/)` 报"找到多个"。单独跑绿、一起跑红 —— 又一次"绿测试证明不了什么"。

## 四、数字

`domain.ts` 加 `coverage/coveredBytes` 与 `RECEIPT_COVERAGE_INSUFFICIENT`、`CommandRole`；
`workspace.issueReceipt` 改签名；`tools.ts` fs_read 先投影后签发；`mutation.ts` 一条准入；
`verify.ts` recorder + 风险闸门；`agent.ts`/`authority.ts` 三个调用点传 host；`Transcript.tsx` 合并报数。
测试 876 → 891（tools +4、mutation +3、verify +6、Transcript +2），typecheck 与 selftest 均过。

## 五、可复用的结论

- **摘要类凭证要带覆盖范围。** "内容没变"和"我看过全部内容"是两件事；只有后者能支撑整体替换。
- **拒绝要给出路**：被拒的那一刻告诉它换哪条路，最好在它动手之前就说。
- **平台自己的动作也要进账本和时间线**，否则"同一 Gateway 同一账本"只是半句话。
- **修红测试先问它想断言什么**：这三条测试想说"模型没有副作用"，不是"没有任何 R1 记录"。
