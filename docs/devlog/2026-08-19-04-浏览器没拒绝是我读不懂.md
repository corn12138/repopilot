# 浏览器没拒绝，是我读不懂

> 开发记录 · 2026-08-19 · RepoPilot

批 1 交出的产出是一个 0：组件层直达第 1 层 palette 的次数为 0。批 2 要把这个 0 花掉 ——
把 `:root` 之外剩下的 45 处硬编码颜色收进角色层，让"换皮"真的只剩改 `:root`。

45 处收完，`:root` 之外剩余硬编码颜色：0。

## 手挑的淡底反解不出 α

批 2 里最花时间的不是那 45 处，是 11 个语义淡底。

原来它们是手挑的：`failed` 的底 `#2a1a1d`、`blocked` 的底 `#1e3358`……每个都是单独调出来的
字面值。既然要收进角色层，自然想写成派生式：淡底 = 语义色按某个 α 混进底色。

问题是**反解不出这个 α**。把手挑值按 `mix(fg α%, panel)` 去解，每个通道解出来的 α 不一样，
而且好几个是负数 —— 说明它们根本不是"面板染了色"，是一口口比面板更暗的彩色井。

所以这里必须承认是在**改设计**，不是在做等价重写。定档稿写的是 `mix(fg 14%, panel)`，
我实际用的是 `mix(fg 8%, canvas)`。偏离的理由是可量的：panel@14% 会把 `failed` / `unknown`
在自己淡底上的对比度压到 4.44 / 4.34，**低于 4.5**。定档稿里那个数是在别的面板色上算的，
换到当前面板就不成立了。这条偏离连同这两个数写在 `styles.css` 的注释里，注明「等批 V 把正文改成中性字之后再回到 panel 基底，那时这两个数要一并复核」——
不是悄悄改掉，也不是当成新的定论。

派生完的实测：

| 语义 | fg/淡底 | fg-strong/淡底 | 主文字/淡底 | 淡边/面板 | 淡边/淡底 |
|---|---|---|---|---|---|
| verified | 6.74 | 9.34 | 13.23 | 1.449 | 1.418 |
| warning | 6.74 | 8.75 | 13.17 | 1.440 | 1.402 |
| failed | 5.25 | 9.05 | 13.60 | 1.292 | 1.300 |
| blocked | 5.39 | 9.39 | 13.35 | 1.348 | 1.331 |
| unknown | 5.16 | 5.16 | 13.38 | 1.333 | 1.320 |
| **门槛** | **4.50** | **4.50** | **4.50** | **1.250** | **1.250** |

## 我给一个不存在的性质设过门槛

淡底刚派生完时，我给合同测试加的第一条是"淡底对面板 ≥ 1.05"。

然后量了一下**当前**的值：1.003–1.038。这条门槛从来就没成立过。

它错在测的是一个这套设计并不打算提供的性质 —— 淡底和面板本来就该几乎同亮，靠的是色而不是
明暗跟面板分开。真正承担"这一条和周围不一样"的是淡**边**，它对面板是 1.292–1.449。

所以门槛换成边框对面板 ≥ 1.25，理由写在测试里：

```
对不存在的性质设门槛，只会逼着后来的人把门槛调低，而不是把东西做对。
```

## 顺手撞出来的一处真缺陷

给"实心底 + 上面的字"补对比度断言时，`#fff` 打在 `--accent-interactive`（`#4c8dff`）上
量出来 **3.20:1**。这不是批 2 引入的，是一直就在那儿、没人量过。

改成 `--accent-fg-on-accent: var(--palette-ink-on-solid)`（`#0f1216`）= 5.87:1。
这也正好跟定档稿在暖色强调色上的判断一致：实心块上压深墨，不压白。

## 探针把"我读不懂"报成了"浏览器不支持"

批 2 的淡底是 `color-mix` 合成的，而且百分比本身是 `var()`：

```css
--state-failed-tint-bg: color-mix(in srgb, var(--state-failed-fg) var(--palette-tint-alpha-bg), var(--surface-canvas));
```

合同测试跑在 jsdom 上，`color-mix` 是我自己用 JS 算的。**我的实现算得出来，不能证明
Chromium 算得出来。** 而 `color-mix` 一旦不被接受，属性在计算值阶段就无效、背景静默变成
透明 —— 界面不会报错，只会看起来"没那么好看"。

所以往 `renderProbe`（Electron 里真开一个窗口量计算值的那条自检）加了一段：造个 div、
背景设成 `var(--state-failed-tint-bg)`、读 `getComputedStyle`。

第一次跑，红的：

```
FAIL 渲染层 · color-mix 淡底未被浏览器接受：
     底=color(srgb 0.128314 0.0867451 0.102274)
     边=color(srgb 0.29349 0.131922 0.138275)（应为不透明 rgb）
```

看清楚这行 —— **浏览器把值算出来了**。它只是没序列化成 `rgb(...)`：`color-mix(in srgb, …)`
的计算值序列化成 `color(srgb r g b)`，分量是 0–1 而不是 0–255。我的 `parseColor` 只认
`rgb()` 和 `#rrggbb`，读不懂，`opaque()` 于是返回 false，探针报"浏览器不接受"。

这跟前几天 retention 那个坑是同一种病：**"我读不了"被当成了"它不存在"**。差别只在这次
是我自己新写的探针犯的，而且它失败得很像"功能真的坏了"—— 一个坏掉的检测器和一个坏掉的
功能，在报告里长得一模一样。

修法不是把判断放宽成"只要非空就算过"，那样探针就废了。是**教它认这一种色，且只认这一种**：

```ts
// 只认 srgb：真出现 display-p3 之类的色域，就该 return null 让调用方失败，
// 而不是当 srgb 硬算。
const srgb = /^color\(\s*srgb\s+([\d.]+)\s+([\d.]+)\s+([\d.]+)\s*\)$/.exec(value.trim());
```

`opaque()` 也从"字符串以 rgb 开头"改成"解析得出且 alpha 不为 0"—— 这样 `transparent`
和 `rgba(0,0,0,0)` 仍然会被判死，而合法的新写法能过。

## 两套算术互相对账

修完再跑，绿的。这时候才拿到批 2 真正想要的那个证据 —— 把浏览器算的和我算的摆一起：

```
合同测试算出的 tint-bg : [33, 22, 26]        浏览器实测 : [33, 22, 26]
合同测试算出的 border  : [75, 34, 35]        浏览器实测 : [75, 34, 35]
合同测试 fg-on-tint    : 5.25:1              浏览器实测 : 5.25:1
```

逐通道相同。这条对账的意义不在"这次对了"，在于**它把 jsdom 里那 16 条合同测试从"我的实现
说 OK"升级成了"浏览器背书过我的实现"**。以后改 α、改语义色，合同测试仍然跑在 jsdom 上、
仍然是秒级的，但它算的东西已经被真浏览器校准过一次了。

自检里也留下了这一行，每次都会重量：

```
PASS 渲染层 · color-mix 淡底真的算出来了：底 color(srgb 0.128314 …) 边 color(srgb 0.29349 …)
PASS 渲染层 · 语义色在自己淡底上实测 5.25:1
```

## 然后才敢换暖色

批 2 的最后一个提交才是换 warm。上面那一堆是它的前提：只有"淡底真的是派生的、派生真的
被浏览器认、门禁真的会红"三件事都立住了，换色板才可能是改 `:root` 而不是改 5853 行。

换完的验收是拿基线自己公布的数字反查 —— 如果我抄错一个 hex，这些数就对不上：

| 项 | 基线 v1.1 写的 | 代码实测 |
|---|---|---|
| focus 环对 canvas / panel / raised | 5.85 · 5.13 · 4.23 | 5.85 / 5.13 / 4.23 |
| 主按钮字对 accent 底 | 5.51 | 5.51 |
| dark canvas↔panel / panel↔raised | 1.14 / 1.21 | 1.140 / 1.211 |
| text.primary / secondary 对 panel | 13.76 / 7.33 | 13.76 / 7.33 |

三处结构性改动，每一处都不是"换个值"：

**accent 从 blocked 里分出来了。** v1.0 §2.1 让它们共用一个蓝，理由挺好：blocked 不是错误，
是"可点、轮到你"。但 v1.1 把 accent × 六语义色的 ΔE₀₀ 写进了门禁 —— 同源等于 ΔE=0，
这一关过不去。"轮到你"改由形状轴和闸门位置承担，那本来就是它该待的地方。

**四个手挑的"淡底正文色"变成了一条按门槛倒推的规则。** cool 时代这四个值反解不出任何 α
（拟合平均色距 28.9，warning 差 62），所以当时如实写了"手挑"。warm 没有历史包袱，于是直接
按门槛定义：`-strong = mix(语义色 α, ink-1)`，α 取"五个语义在自己淡底上全部 ≥7.0
（WCAG AAA 正文）能过的最大整档" = 85%（最紧的 unknown 7.28）。

这里的关键不是 85 这个数，是**它由谁决定**。门槛写在测试里，α 写在 CSS 里；谁想调 α，
测试当场红。顺带把 unknown 补齐了 —— 它以前正文直接用 fg（5.16），五个语义走同一条规则，
"换皮只改第 1 层"才成立。

**三级字对基线做了第二处有意偏离。** 基线的 warm tertiary `#928a80` 在 raised 上只有 **4.07**，
基线用一条用法规则兜住（"dark 禁入 raised"）。但组件今天确实把三级字放在 raised 上，
而且 renderProbe 每次都会量它。用法规则改不动的东西，只能由颜色让步：朝 ink-1 提亮 10%
得到 `#9b938a`，canvas 6.32 / panel 5.54 / raised 4.57。等批 V 真把三级字从 raised 上撤掉，
这个值放回 `#928a80`。

基线没给值的另外五个（overlay / 强描边 / 控件 hover 面 / 终端深底 / 代码字），没有自己挑：
反解 `canvas→ink-1` 这条线，基线给的三个面正好落在 6.1–6.8% / 10.4–11.8% / 12.7–14.1%，
说明它们本来就是同一条线上的三站，所以 17% / 20% / 25% 是**续这条线**，不是另挑三个颜色。

浏览器复核了换色后的合成结果：

```
PASS 渲染层 · color-mix 淡底真的算出来了：底 color(srgb 0.135686 0.0977255 0.0930196)
PASS 渲染层 · 语义色在自己淡底上实测 7.12:1
```

`[35, 25, 24]` = `#231918`，与合同测试逐通道相同；7.12 也与合同测试相同。
