# 推不出厂商，不该被写成"已异构"

A2A 评审（§4.4）收尾时点名了一件事：异构断言里"推不出 vendor 就跳过"是个受限例外，
但远程化之后**所有**调用都会落进这个例外，`SAME_VENDOR_REVIEW_DENIED` 会变成死码。
当时的结论是协议先不接，例外先留着。这次把例外本身解决掉——顺带把评审勘察时
翻出来的另外两个耦合点（选手注册表硬编码、身份用字符串前缀承载）一起收了。

## 问题是什么

`authority.ts` 里厂商推断的全部家当是这个：

```ts
function vendorOfProvider(providerId: string): ExternalVendor | null {
  if (providerId === 'anthropic') return 'ANTHROPIC';
  if (providerId === 'openai') return 'OPENAI';
  return null;   // "无法证明同厂商，此时不拦"
}
```

注释写得很坦然："宁可放过一次同源审核（价值有限但无害）"。
但它低估了两件事。

**第一，中转站上的厂商经常是可以证明的。** 内置注册表里就摆着证据：

```ts
// registry.ts —— openrouter 的模型清单
models: ['anthropic/claude-sonnet-4.5', 'openai/gpt-5.1', ...]
```

`anthropic/claude-sonnet-4.5` 的命名空间就是中转站自己声明的上游厂商。
用户拿 openrouter 上的 claude 当实现方、Claude CLI 当审核方——同一家模型写完自己审，
`vendorOfProvider('openrouter')` 返回 null，断言跳过，静默放行。
"放过的同源审核"并不都无害：它恰好放过的是**能证明**的那一批。

**第二，跳过断言之后，绑定处写下的不是"没查"，是"已证异构"：**

```ts
// bindCliReviewer（旧）
const implementerVendor = vendorOfProvider(implementer.providerId);
if (implementerVendor) assertHeterogeneousVendor(implementerVendor, connector.vendor);
return {
  ...
  heterogeneous: true, // 上面已断言，同厂商到不了这里
};
```

那行注释只在 `implementerVendor` 非 null 的分支里为真。null 分支跳过了断言，
却共享同一个 `heterogeneous: true`，界面上是蓝色的"异构审核方"徽章。
TD §9.14 要求"若供应商相同必须显式披露非异构审核"——这里不但没披露，还披露了反话。

这与上一篇（INCONCLUSIVE 被折成 PASS）是同构的病：**没证据的方向上编了结论。**

## 怎么解决的

### 一、厂商推断搬进 `model/vendor.ts`，证据分级，三态输出

```ts
// 证据优先级（高 → 低）：
//   1. 模型 id 的命名空间前缀（anthropic/claude-… 的 anthropic）
//   2. 模型名的家族前缀（claude- / gpt- / kimi- —— 跨托管方稳定）
//   3. 单一厂商官方 provider 的归属（anthropic 官方只服务自家模型）
// 三条都给不出证据 → UNKNOWN，带原因返回
export type VendorInference =
  | { kind: 'KNOWN'; vendor: ModelVendor; evidence: string }
  | { kind: 'UNKNOWN'; reason: string };
```

家族名排在 provider 归属**之前**是有讲究的：火山方舟（字节官方）上托管着
`deepseek-v3-1` 和 `kimi-k2`，按 provider 归它们是字节的，按家族归才是对的——
异构不变式关心的是"模型出自谁家"（同家族共享盲区），不是"数据送到谁的服务器"。
也因此官方兜底表只收单一厂商的官方站，火山方舟、阿里百炼这类托管第三方模型的
故意不进表：它们只能靠前两条给证据，给不出就是 UNKNOWN。

判定从布尔换成三态：

```ts
export interface VendorParity {
  readonly kind: 'HETEROGENEOUS' | 'SAME_VENDOR' | 'UNVERIFIABLE';
  readonly detail: string;   // 双方各归入哪个家族依据什么，或为什么归不出来
}
```

拦截立场**没有变**：证明同厂商才拦（CLI 侧硬拒，模型对模型披露不拦），
证明不了照旧放行。变的是放行时写下的东西——`UNVERIFIABLE` 带着原因进披露、
进事件、进 `CrossReviewRecord`，`heterogeneous` 字段只在**已证明**异构时为 true。

判定还进了出站披露本身（`DataEgressDisclosure` v2，digest 覆盖它）：
用户点头之前就能看见"写审厂商：已证异构 / 同厂商 / 无法判定——依据是什么"，
而不是任务创建之后才在事件流里发现。

### 二、选手注册表：表是唯一事实源

`ExternalVendor` / `ExternalConnectorKind` 两个闭包字面量联合删掉了。
厂商并进 `ModelVendor`（将来接 gemini-cli 就有 GOOGLE 可用），
kind / connectorId 由描述符表派生：

```ts
const DESCRIPTORS = [ /* claude-cli, codex-cli */ ] as const satisfies readonly ExternalConnectorDescriptorShape[];
export type ExternalConnectorKind = (typeof DESCRIPTORS)[number]['kind'];
export type ExternalConnectorId = (typeof DESCRIPTORS)[number]['connectorId'];
```

加第三家 CLI = 在表里加一个条目，不用再去别处扩枚举。
表刻意留在代码里而不是配置文件："不接受运行时拼接的任意 argv"这条安全选择不因注册表化而放宽。

### 三、身份不再靠 `external:` 前缀

`CrossReviewRecord.reviewerProfileId` 此前用 `external:` 字符串前缀区分两种选手——
第三种选手进来时只会长出第三个前缀。现在身份是判别联合：

```ts
export type CrossReviewerIdentity =
  | { kind: 'MODEL_API'; profileId: string }
  | { kind: 'EXTERNAL_CLI'; connectorId: string };
```

旧字段保留为遗留展示派生，前缀约定收进唯一一个函数（`legacyReviewerProfileId`），
新分支进来时编译器会点名所有消费处。旧持久化记录没有新字段——可选字段 + UI 回落，
按当年记下的展示，不重写历史。

## 踩了什么坑

### 一、`as const` 把测试的合法变体一起锁死了

注册表化第一版直接 `export type ExternalConnectorDescriptor = (typeof DESCRIPTORS)[number]`，
typecheck 立刻红了二十几处——全在测试里。测试要构造"binaries 指向假二进制"的
描述符变体去探测隔离行为，而元素字面量类型把 `binaries` 锁成了 `readonly ['claude']`。

"表是唯一事实源"指的是**枚举成员**（kind / id 的取值集合），
不是"所有入参都必须是表里的那两个字面量"。对外类型改成"形状宽型 + kind 收窄"，
表管成员，函数收变体，两边都对。

### 二、预览不镜像降级 = 同意永远对不上

改完拒绝逻辑去追"被拒之后用户看到什么"，发现一个此前就潜伏的死循环：
`disclosureFor`（预览）不做同厂商判定，`createTask` 做。于是用户确认的是
"含审核方"的 digest，创建时降级成"无审核方"重算——`CONSENT_STALE`，
提示"请重新查看披露并确认"，再确认，再 STALE。我的改动把可判定面扩大了，
这个循环的触发面也会跟着扩大，必须一起修。

模型审核方那条分支其实早就写了镜像（"披露也按'不审核'算，两边一致"），
CLI 分支漏了。补齐之后降级不静默：Renderer 发现"选了审核方但披露里没有
REVIEWER 目的地"时明说会降级、为什么。

### 三、我的测试用例先输给了自己的设计

写负向用例时造了个对抗名 `claude-like-but-not`，期望 UNKNOWN——红了。
家族前缀规则说 `claude-` 开头就是 Anthropic 家族的证据，这正是我自己定的规则。
对抗名想赢，得先回答"真实世界里谁会叫这个名字"：中转站的路由标识和厂商的
商标性命名都不会。用例改成真正无家族名的 id，规则不动。

## 可复用的结论

- **"跳过检查"之后写下的每个字段都要重新审视。** 跳过的那条路径往往共享着
  "检查通过"分支的赋值，于是"没查"被记录成"查过了"。
- **放行要分"证明不了"和"证明了没问题"。** 前者是 UNVERIFIABLE，后者才是
  HETEROGENEOUS；折在一个布尔里，总有一边在说谎。与 INCONCLUSIVE ≠ PASS 同一条原则。
- **归属判定要选对维度。** provider 回答"数据去哪"，vendor 回答"模型出自谁家"；
  拿前者代替后者，中转站一出现就失效。
- **预览和执行共用判定，否则"确认"会变成永远差一步的追赶。** 哪边少一条规则，
  digest 就永远对不上。
- **派生类型时分清"枚举成员"与"入参形状"。** 前者该收窄，后者收窄就是把测试
  和未来的合法变体一起焊死。
