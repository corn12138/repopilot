# 夹具差一个短横

一条测试的名字叫「内容行本身以 ++ / -- 开头时被当成文件头漏计（**产品缺陷**）」。
它注释里点名的现实场景是「SQL 的 `-- 注释`」。它的夹具写的是 `--- 旧分隔线`。
差一个短横，于是它测的是另一件事，而真正的缺陷在旁边活了很久。

## 一、问题是什么

发现它的过程跟缺陷本身一样值得记：我不是在找 bug，是在做风险排查，读到
`patch.ts` 里 `countPrefix` 的注释——

```ts
/**
 * 统计增删行数。
 *
 * 只在 `@@` hunk 内计数，不用 `'+++'`/`'---'` 的形状去猜文件头 ——
 * 顶格的内容行会误命中：`-- 注释` 变成 `--- 注释`、`++i;` 变成 `+++i;`，
 * 于是一增一删的改动会被报成 0/0。SQL 注释、YAML 分隔符、C 风格自增都会触发。
 */
```

它上面 12 行是兄弟函数 `normalizeHeaders`，干的是同一件事的另一半：把 diff 头里的
宿主绝对路径换成仓库相对路径。它的实现是这样的：

```ts
return diff.split('\n').map((line) => {
  if (line.startsWith('diff --git ')) return `diff --git a/${rel} b/${rel}`;
  if (line.startsWith('--- ')) return line.includes('/dev/null') ? '--- /dev/null' : `--- a/${rel}`;
  if (line.startsWith('+++ ')) return line.includes('/dev/null') ? '+++ /dev/null' : `+++ b/${rel}`;
  return line;
});
```

**逐行无条件改写，没有 hunk 内外的概念。** 而 `countPrefix` 为了完全相同的输入类，
已经加了一个 `inHunk` 状态机。

同一个文件、相邻 12 行、同一类输入，一个修了一个没修。这是 devlog
`2026-08-09-02-同一道检查只装在一半的入口上.md` 那个模式的又一次复发。

### 触发条件完全良性

SQL / Lua / Haskell 的行注释是**两个**短横加空格：`-- 旧注释`。
补丁删掉或改掉这一行时，diff 把它渲染成 `-` + `-- 旧注释` = `--- 旧注释`
—— 三个短横加空格，正好命中 `startsWith('--- ')`，于是被改写成 `--- a/db/schema.sql`。

用户的代码行被换成了一个文件头。

后果分两层：

- 导出的 `.patch` 与剪贴板副本**静默损坏**；
- 宿主写回时 `git apply --check` 找不到待删的那一行，失败经 `authority.ts:3236`
  映射成 `reason: 'APPLY_CONFLICT'`。「冲突」这个词指向**目标仓库分叉**，
  而真正坏掉的是平台自己生成的 diff。detail 文本倒是诚实的
  （「git 认为这个补丁无法干净应用」+ git 原始 stderr）—— 误导发生在 reason 代码这一层。

## 二、那条测试为什么没抓住

它有正确的名字、正确的注释、正确的意图，夹具差一个短横：

```ts
const { ws, runId, baseSha } = open({ 'db/schema.sql': '--- 旧分隔线\nSELECT 1;\n' });
mutate(ws, runId, [{ kind: 'REPLACE_EXACT_TEXT_SPAN', path: 'db/schema.sql',
                     oldText: '--- 旧分隔线', newText: '++inc' }]);
```

`--- 旧分隔线`（三个短横）被删掉时渲染成 `---- 旧分隔线`（**四个**）。
`startsWith('--- ')` 要求第四位是空格，而它是 `-`。**擦过去了。**
`++inc` 渲染成 `+++inc`，第四位是 `i`，同样擦过 `startsWith('+++ ')`。

而且那个夹具形态本身也不现实：SQL 里没有以三个短横开头的行注释，
YAML 的文档分隔符是 `---`（无尾随空格，渲染成 `----`，也擦过）。
**能命中的恰恰是两短横加空格，也就是最常见的行注释形式。**

这条测试测的是 `countPrefix`（它确实需要 `inHunk`，而它已经有了），
顺带给人一种「这一类已经覆盖」的错觉 —— 于是 `normalizeHeaders` 没人再看。

## 三、怎么解决的

### 判据收成一处，而不是写一条提醒

最省事的修法是给 `normalizeHeaders` 也加一个 `inHunk` 局部变量，跟 `countPrefix` 各写各的。
那样两个函数就各自持有一份「什么算 hunk 边界」的知识 —— 而它们**已经漂过一次了**。

所以抽出来：

```ts
/**
 * 统一 diff 里「这一行是不是 hunk 边界」。
 *
 * `@@` 开启一个 hunk，`diff --git` 关掉上一个。判据只有这一份，
 * `normalizeHeaders` 与 `countPrefix` 共用 —— 它们必须对"什么算 hunk 内"有
 * **同一个**答案，而它们曾经没有。
 */
function hunkEdgeOf(line: string): 'OPEN' | 'CLOSE' | null {
  if (line.startsWith('@@')) return 'OPEN';
  if (line.startsWith('diff --git ')) return 'CLOSE';
  return null;
}
```

两个消费者各自保留自己的循环（一个 map、一个计数），只共用判据。
没有为了「统一」把迭代也抽成高阶函数 —— 那会让 `countPrefix` 变成一个
带副作用的 map，读起来更绕，而收益为零。

风险台账里我原本写的监控条件是「改 `patch.ts` 时记得检查两个函数口径一致」。
写完就意识到那是个弱保证：**代码里能表达的约束，不要降级成一句提醒。**

### 两层测试：diff 文本 + 真的能 apply

`patch.test.ts` 钉文本：

```ts
// 文件头仍然被归一化，且**只有一份** —— 被改写的内容行会造出第二个一模一样的头
expect(lines.filter((l) => l === '--- a/db/schema.sql')).toHaveLength(1);
// 内容行逐字节保住：这才是补丁能被 apply 的前提
expect(lines).toContain('--- 旧注释');
```

这里绕开了既有的 `headerLines()` 辅助函数 —— 它的正则是 `^(diff --git |--- |\+\+\+ )`，
**本身分不清文件头与内容行**。修好之后那条完好的内容行 `--- 旧注释` 同样会被它捞进来，
所以断言它的长度反而会失败。用「某个字符串只出现一次」才是真判据。

`apply.test.ts` 钉用户可见的结果：走完整链路（真 git 仓库 → importSnapshot →
真 mutation 引擎 → sealPatch → `applyPatchWithGit`），断言

```ts
// 这一句是本条测试的全部意义：修复前它是 { ok: false, stage: 'CHECK' }
expect(applied.ok).toBe(true);
expect(readFileSync(join(host, 'db/schema.sql'), 'utf8')).toBe('-- 新注释\nSELECT 1;\n');
```

文本对了不代表能 apply。这两层缺一不可：只测文本，测不出「补丁交不到用户手上」；
只测 apply，测不出「头被复制成了两份」这种仍然能 apply 的损坏。

## 四、踩了什么坑

### 坑：我差点写下一句不存在的引用

第一版测试注释里我写「失败被报成 `APPLY_CONFLICT`「目标文件已漂移」」。
写完去核 `authority.ts:3236`，原文是：

```ts
detail: `git 认为这个补丁无法干净应用，已整笔拒绝、未改动任何文件：\n\n${result.detail}`,
```

**没有「目标文件已漂移」这句话。** 那是 README 证据清单里描述**真实漂移**场景的措辞，
我把它张冠李戴到了这里。误导确实存在，但在 reason **代码**这一层（`APPLY_CONFLICT`
这个词暗示目标分叉），不在 detail 文案层。三处引用（两条测试注释 + 风险台账）全部改准。

这正是我在同一轮排查里归类为 RISK-11 的形态：**声称的东西与实际不一致**。
我在写「项目有说谎风险」的台账时，自己写了一句不存在的话。

### 一次失败的安装留下了持久化改动

跑 `pnpm vitest run` 时 pnpm 突然触发了一次安装，失败在 `ERR_PNPM_IGNORED_BUILDS`，
并顺手在 `prototype/` 下创建了一个 `pnpm-workspace.yaml`，内容是占位符：

```yaml
allowBuilds:
  electron: set this to true or false
```

`package.json` 里本来就有生效的 `pnpm.onlyBuiltDependencies`，这个残桩只会干扰后续安装。
AGENTS.md 写的是「自检和测试**不能留下持久化改动**」，所以确认它是几分钟前
我那条命令产生的未跟踪文件之后删掉了，并核对 `pnpm-lock.yaml` 与 `package.json`
逐字节未变。

### 证明测试能抓到缺陷，比让它变绿重要

修完之后我把 `normalizeHeaders` **临时退回旧实现**，跑了一遍：

```
patch.test.ts  → × 被删掉的 SQL 行注释…  expected [ '--- a/db/schema.sql', …(1) ] to have a length of 1 but got 2
                 Tests  1 failed | 18 passed (19)
apply.test.ts  → × 补丁改的是 SQL 行注释…  expected false to be true
                 Tests  1 failed | 14 passed (15)
```

两件事被这一次回退同时证明了：新测试**真的会红**（不是恒绿的装饰），
以及**其余 18 / 14 条测试在缺陷代码上全绿** —— 既有套件确实没覆盖，
这不是「测试漏了一条」，是「整类输入没人测」。

然后才还原修复。多花两分钟，换来的是「这个缺陷曾经真实存在、且现在被钉住了」的
机器证据，而不是一句「我修了」。

## 五、可复用的结论

**1. 注释是缺陷的探测器。** 这次不是测试红了我才去看，是 `countPrefix` 的注释
点名了一类输入，而我在隔壁函数里没看到对应的处理。**当一段注释解释了某个非显然的
防御，就去查同一文件里其他处理同类输入的地方有没有同样的防御。**

**2. 夹具要用现实形态，不是「差不多能触发」的形态。** 差一个短横，测试就从
「钉住缺陷」变成「钉住另一个东西」，而且它还是绿的 —— 绿得让人安心。
写夹具时该问的是「现实中这个字节序列长什么样」，不是「什么样的输入能让我的断言成立」。

**3. 辅助函数也会撒谎。** `headerLines()` 的正则分不清文件头与内容行，
在它之上写断言会得到一个**修好了反而失败**的测试。用之前先看它到底筛出了什么。

**4. 代码里能表达的约束，不要降级成一句提醒。** 我原本要在台账里写
「改这个文件时记得检查两个函数口径一致」。改成共用 `hunkEdgeOf` 之后，
忘了检查这件事变得不可能。

**5. 两层证据：文本层与结果层。** 「diff 看起来对」和「补丁真的能 apply」
是两个独立命题，各自的失败模式不同。这个仓库的 `applyPatchWithGit` 是唯一会写
用户仓库的函数，值得一条端到端。
