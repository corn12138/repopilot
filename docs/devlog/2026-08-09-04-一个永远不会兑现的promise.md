# 一个永远不会兑现的 Promise

> 开发记录 · 2026-08-09 · RepoPilot

场景：Agent 生成了计划，界面上弹出「批准执行计划」，你去开了个会。
25 分钟后回来，点「批准并执行」。

按钮响应了，返回 `accepted: true`，时间线上多出一条「用户批准了计划」。

**然后什么都没发生。**

Run 的状态是 `TIMED_OUT`，「取消」按钮也不见了。你既不能前进也不能后退，
只能新建一个任务重来。

## 四个问题叠在一起

`execute()` 一开始就挂了一个墙钟 deadline：

```ts
const deadline = setTimeout(() => {
  if (!isTerminal(record.view.status)) {
    record.abort.abort();
    this.setStatus(record, 'TIMED_OUT', '超过任务时间预算');
  }
}, record.task.budget.maxWallClockMs);   // 默认 20 分钟
deadline.unref?.();
```

而审批是一个只能由 `decideApproval` / `cleanupPendingApprovals` 兑现的 Promise：

```ts
return new Promise<ApprovalDecisionKind>((resolve) => {
  record.approvals.set(request.approvalId, { request, resolve });
  this.pushApprovals(record);
});
```

`agent.ts` 里 `await host.awaitPlanApproval(plan)`，**没有和 abort 赛跑**。

### 问题一：人在思考的时间被算进了计算预算

`maxWallClockMs` 的本意是"这个任务最多跑 20 分钟"，防的是模型死循环、构建卡死。
但它从 `execute()` 开始就一直在走，**覆盖了等待人工审批的时间**。

用户审一个计划审 25 分钟，是完全合理的行为 —— 尤其这个产品的整个卖点就是
"让你看清楚它要干什么再放行"。结果认真审反而会被判超时。

### 问题二：超时回调不兑现 Promise

deadline 到点只做了 `abort()` + `setStatus()`，**没有调 `cleanupPendingApprovals`**。

于是那个 Promise 永远不 resolve → `runAgent` 永远挂在 `await` 上 →
`execute()` 的 `try` 永远挂着 → **`finally` 永远不执行**：

```ts
} finally {
  clearTimeout(deadline);
  this.cleanupPendingApprovals(record);
  if (isTerminal(record.view.status) && record.view.status !== 'AWAITING_PATCH_REVIEW') {
    this.emit(record, 'CLEANUP_SUMMARY', '已释放模型流、子进程与审批等待', {
      workspaceRetained: record.view.status === 'SUCCEEDED',
    });
  }
}
```

PRD §9 要求 `TIMED_OUT` 页面必须给出清理凭证 —— 那条 `CLEANUP_SUMMARY` 事件
**永远发不出来**。

### 问题三：过期分支只删不兑现

`decideApproval` 里有一条过期检查：

```ts
if (Date.parse(pending.request.expiresAt) < Date.now()) {
  record.approvals.delete(input.approvalId);
  this.pushApprovals(record);
  return { accepted: false, reason: '审批已过期' };
}
```

`delete` 了，但**没有 `resolve`**。resolver 被从 map 里删掉却从未兑现 ——
此后 `cleanupPendingApprovals` 遍历空 map 也救不回来。这是从"暂时挂起"升级成
**永久泄漏**。

有意思的是，这条分支在 Run 仍是非终态时**不可达**：`APPROVAL_TTL_MS` 是 30 分钟，
而 `maxWallClockMs` 是 20 分钟 —— deadline 总是先到。所以它只在
"已经 TIMED_OUT 之后、用户在计划生成满 30 分钟后才点按钮"这个窗口里可达。

顺带说明另一件事：PRD 6.2 要求的「审批过期 → BLOCKED」在代码里**从来没被实现过**。
Run 只会变成 `TIMED_OUT`。

### 问题四（UI 侧）：终态上还能点批准

```tsx
{approvals.length > 0 && plan && (
  <PlanApproval approval={approvals[0]!} plan={plan} onError={onError} />
)}
```

没有状态门禁。Run 已经 `TIMED_OUT` 了，审批卡片照样渲染。点下去往一个终态 Run
的事件流里追加一条「用户批准了计划」—— 一条**不对应任何实际执行的假审计记录**。

## 修法一：让 deadline 可以暂停

核心认识是：**"人在审批"和"模型在跑"是两种时间，不该用同一个预算。**

```ts
/**
 * 可暂停的墙钟 deadline。
 *
 * 存在的理由：等待**人工审批**的时间不该算进 Run 的计算预算 —— 用户花 25 分钟
 * 审一个计划，不该导致 Run 被判 TIMED_OUT。所以进入审批等待时 pause()，
 * 用户决定后 resume()。审批期间模型并没有在跑，计算时间仍然是有界的。
 *
 * 之前是一个从 execute 开始就一直在走的 setTimeout，它覆盖了审批等待时间，
 * 且到点只 abort + setStatus，不兑现 awaitPlanApproval 的 Promise —— 于是
 * runAgent 永远挂在 await 上，execute 的 finally（清理 + CLEANUP_SUMMARY）永不执行。
 */
export class PausableDeadline {
  private handle: ReturnType<typeof setTimeout> | null = null;
  private remaining: number;
  private startedAt = 0;
  private done = false;

  constructor(totalMs: number, private readonly onFire: () => void) {
    this.remaining = totalMs;
    this.arm();
  }

  private arm(): void {
    if (this.done || this.handle) return;
    this.startedAt = Date.now();
    this.handle = setTimeout(() => {
      this.handle = null;
      this.done = true;
      this.onFire();
    }, Math.max(0, this.remaining));
    this.handle.unref?.();
  }

  pause(): void {
    if (this.done || !this.handle) return;
    clearTimeout(this.handle);
    this.handle = null;
    this.remaining -= Date.now() - this.startedAt;
  }

  resume(): void { this.arm(); }

  clear(): void {
    this.done = true;
    if (this.handle) { clearTimeout(this.handle); this.handle = null; }
  }
}
```

几个刻意的设计：

- `arm()` 里的 `if (this.done || this.handle) return` 让 `resume()` 在已触发或已清除后
  是 no-op —— 不会把一个已经停掉的 deadline 复活
- `pause()` 里的同一个 guard 让重复 pause 不叠加扣时
- `unref()` 让定时器不阻止进程退出

## 修法二：审批和 abort 赛跑

```ts
// 人工审批不消耗计算预算：暂停墙钟，用户决定后再恢复。
deadline.pause();

return new Promise<ApprovalDecisionKind>((resolve, reject) => {
  // 已被取消就别挂起了，否则 runAgent 永远等不到（addEventListener 对已 abort
  // 的 signal 不会再触发）。正常路径上 runAgent 在调用本函数前刚 throwIfCancelled 过。
  if (record.abort.signal.aborted) {
    deadline.resume();
    reject(new AgentCancelled('审批开始前已取消'));
    return;
  }

  const cleanup = (): void => {
    clearTimeout(expiry);
    record.abort.signal.removeEventListener('abort', onAbort);
    record.approvals.delete(request.approvalId);
    this.pushApprovals(record);
  };

  // 取消 / 超时（deadline 兜底）→ abort：兑现 Promise，让 runAgent 解开、finally 执行。
  const onAbort = (): void => {
    cleanup();
    reject(new AgentCancelled('审批等待期间被中止'));
  };

  // 审批自身的过期（30 分钟未决定）→ BLOCKED，与「计算超时 TIMED_OUT」区分。
  // 之前这条只能被"用户回来点按钮"惰性触发，且那条分支只 delete 不 resolve，
  // 于是 Promise 永久泄漏、CLEANUP_SUMMARY 永远发不出来。
  const expiry = setTimeout(() => {
    if (!record.approvals.has(request.approvalId)) return;
    this.emit(record, 'NOTE', '计划审批已过期（超过 30 分钟未决定），已停止');
    this.setStatus(record, 'BLOCKED', '计划审批已过期（超过 30 分钟未决定）');
    record.abort.abort(); // 触发 onAbort → cleanup + reject
  }, APPROVAL_TTL_MS);
  expiry.unref?.();

  record.approvals.set(request.approvalId, {
    request,
    resolve: (decision: ApprovalDecisionKind) => {
      cleanup();
      deadline.resume();   // 决定完成，计算预算继续计时
      resolve(decision);
    },
  });
  record.abort.signal.addEventListener('abort', onAbort, { once: true });
  this.pushApprovals(record);
});
```

那句 `if (record.abort.signal.aborted)` 是这类代码最经典的坑：
**`addEventListener('abort')` 对一个已经 abort 的 signal 不会再触发**。
这个仓库在 `runCommand` 里踩过一次一模一样的（"进来时就已经取消了 —— 必须在 spawn
之前返回"），这次是同一个陷阱换了个位置。

审批过期现在是**主动**的（一个自己的定时器），而不是等用户回来才惰性发现。
而且它落 `BLOCKED` 而不是 `TIMED_OUT` —— 「你没在时限内决定」和「计算跑太久」
是两件不同的事，事后审计要能分开。

## 修法三：把 resolve 包起来

现在 `PendingApproval.resolve` 不再是裸的 resolver：

```ts
interface PendingApproval {
  readonly request: ApprovalRequest;
  /** 兑现审批：内部会清理超时定时器、abort 监听，并恢复墙钟 deadline */
  readonly resolve: (decision: ApprovalDecisionKind) => void;
}
```

所有兑现路径（用户决定 / 过期 / 取消 / execute 收尾）都走它，不可能只删不兑现。

`decideApproval` 的过期分支改成和代理定时器同样的处理：

```ts
if (Date.parse(pending.request.expiresAt) < Date.now()) {
  // 与代理超时定时器同样处理：置 BLOCKED 并 abort（→ onAbort 兑现 Promise 并清理）。
  // 绝不能只 delete 不 resolve —— 那正是之前 Promise 永久泄漏、CLEANUP_SUMMARY
  // 永远发不出来的根因。
  this.setStatus(record, 'BLOCKED', '计划审批已过期');
  record.abort.abort();
  return { accepted: false, reason: '审批已过期' };
}
```

并且加了终态门禁，堵住那条假审计记录：

```ts
// 已进入终态的 Run 不再接受审批决定 —— 否则会往一个 TIMED_OUT/CANCELLED 的
// Run 上追加一条"用户批准了计划"的假审计记录，然后什么都不执行。
if (isTerminal(record.view.status)) {
  return { accepted: false, reason: `当前状态 ${record.view.status} 不再接受审批决定` };
}
```

`cleanupPendingApprovals` 也要改 —— 因为 `resolve` 现在会在遍历过程中修改 map：

```ts
private cleanupPendingApprovals(record: RunRecord): void {
  // 先快照：pending.resolve 内部会从 record.approvals 删除自己，
  // 边遍历边删原 map 容易漏项。
  const pendings = [...record.approvals.values()];
  for (const pending of pendings) {
    pending.resolve('REJECT');
  }
  record.approvals.clear();
  this.pushApprovals(record);
}
```

UI 那条一行：

```tsx
{approvals.length > 0 && plan && run.status === 'AWAITING_PLAN_APPROVAL' && (
  <PlanApproval approval={approvals[0]!} plan={plan} onError={onError} />
)}
```

注意这是**纵深防御**，不是主要防线 —— 主要防线是 Core 侧那个终态门禁。
上一篇讲过：「允不允许」在权威层，「显不显示」才在界面层。

## 测试：用假定时器算时间账

`RunAuthority` 目前没有直接的测试装置（要起 gateway、要落盘、要真跑 Agent）。
但 `PausableDeadline` 是这条修复的核心机制，而且是纯的 —— 抽出来就能用假定时器精确测：

```ts
it('有效计算时间等于 totalMs，与暂停时长无关', () => {
  const fire = vi.fn();
  const d = new PausableDeadline(1000, fire);

  // 三段计算 + 两段（很长的）审批等待
  vi.advanceTimersByTime(300);
  d.pause();
  vi.advanceTimersByTime(99999);
  d.resume();
  vi.advanceTimersByTime(300);
  d.pause();
  vi.advanceTimersByTime(88888);
  d.resume();
  vi.advanceTimersByTime(399);
  expect(fire).not.toHaveBeenCalled();
  vi.advanceTimersByTime(1);        // 300+300+400 = 1000
  expect(fire).toHaveBeenCalledTimes(1);
});
```

这条用例把这个类的**语义**写清楚了：不管中间暂停多久，有效计算时间就是 1000ms。
另外 6 条覆盖 clear 后不复活、触发后 pause/resume 是 no-op、重复 pause 不叠加扣时。

我知道这不等于测了整条审批链路 —— 那需要一个能起 `RunAuthority` 的装置，
还没有。**所以这条修复的覆盖是不完整的，机制层有测试，编排层没有。**
写出来是因为不写的话，`PausableDeadline` 7 条绿会给人一种整件事都被测过的错觉。

## 可以带走的

1. **人的时间和机器的时间要分开计。** 一个覆盖了人工等待的"任务超时"，
   惩罚的恰恰是认真审的用户。
2. **任何 `await` 一个手工 Promise 的地方，都要问：谁保证它一定会兑现？**
   超时、取消、过期，每一条路径都得能兑现它。
3. **`addEventListener('abort')` 对已 abort 的 signal 不会触发。** 挂监听前先查一次
   `signal.aborted`。这个坑会反复出现在不同位置。
4. **把 resolver 包起来，别把裸 resolve 存进 map。** 包装函数是"兑现时一定会做的清理"
   的唯一落点。
5. **不同原因的停止要给不同的终态。** 「你没在时限内决定」（BLOCKED）和
   「计算跑太久」（TIMED_OUT）事后审计要能分开。
6. **纯机制抽出来用假定时器测。** 起不了整个服务的时候，至少让核心机制有精确的时间账断言。
7. **说清楚哪里没测到。** 7 条绿不等于整条链路被覆盖了。
