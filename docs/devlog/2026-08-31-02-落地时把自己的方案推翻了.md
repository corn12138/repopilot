# 落地时把自己的方案推翻了：我引的是一份被淘汰的文档

上一篇（[08-31-01](2026-08-31-01-三家候选过一遍准入.md)）给出的排序是
「Kimi 最顺、OpenCode 次之」。用户说「按方案落地执行」，我开工前按方案自己写的那句
「落地前逐条重核」去核了一遍 —— **排序反了**，而且我方案里为 Kimi 设计的那个机制
建立在一个不成立的前提上。

这篇记两件事：错在哪一步，以及最后落了什么。

## 一、错在哪一步：Kimi 有两个产品，我引的是被淘汰的那个

| | 旧版 `kimi-cli` | 当前版 `kimi-code` |
|---|---|---|
| 实现 | Python/uv | Node.js 重写 |
| 文档站 | `moonshotai.github.io/kimi-cli` | `www.kimi.com/code/docs` |
| 配置 | `~/.kimi/config.toml` | `~/.kimi-code/config.toml` |
| 非交互 | `--print`（隐含 `--afk`） | **没有 `--print`**，只有 `-p / --prompt` |
| 环境变量给 key | `KIMI_API_KEY` 可覆盖配置里的密钥 | **明文警告：`export KIMI_API_KEY` 不给任何 provider 提供 key** |

官方迁移文档写着旧版 "will gradually be phased out"。我上一篇引的每一条 —— `--print`、
`~/.kimi/config.toml`、`KIMI_API_KEY` 可覆盖 —— **都来自那个正在被淘汰的产品**。

搜索结果把两个站的内容混在一起返回，而两边都自称 "Kimi CLI 文档"。我没有停下来问
「这两个 URL 是不是同一个东西」。这是这次的直接教训：**同名产品出现两个文档站时，
先确认哪个是当前的，再引任何一句。**

### 连带的第二个错：我为它设计的机制前提不成立

方案里写的是「描述符加一个**播种配置文件**的钩子，播一份引用环境变量的 `config.toml`」。
两头都不成立：

- 当前版 Kimi 的 `[providers.<name>.env]` 子段语义是「**让你用熟悉的键名，在文件里写
  字面值**」，文档原文明说 "read only from the config file and does not modify the shell
  environment"、"The CLI reads only from `config file`, not from `process.env`"。
  它既不是"设给子进程"，也不是"从环境变量读值"—— 我猜的两种都不对。
- 也不支持 `${VAR}` 插值（全量文档 grep `\${` 只命中 system prompt 模板）。

所以"播一份引用环境变量的配置"这条路根本不存在。当前版唯一能让 key 不落盘的通道是
`KIMI_MODEL_*` 一组环境变量（`KIMI_MODEL_NAME` + `KIMI_MODEL_API_KEY` + 可选
provider/base_url），CLI 会在内存里合成一个临时 provider。

**而 OpenCode 需要的也是环境变量**（`OPENCODE_CONFIG_CONTENT` 必须走 inline，见下）。
两家候选都不需要"播文件"，都需要"注入静态非密环境变量"。我建了一个没有消费者的机制。

## 二、重核之后，排序反了

### Kimi Code —— ⚠️ 降级：一条硬需求未确认，且没有沙箱

- **stdin 收 prompt：当前版未确认。** 旧版 FAQ 写了「`--prompt` 或 stdin」，
  当前版文档只演示 `kimi -p "<prompt>"` 的 argv 形态。而"prompt 不进 argv"是我们的
  硬需求（进程列表可见）。这一条不落实，整家进不来。
- **没有工具白名单 flag。** `--allowedTools` 类参数在当前版 CLI 一个都没有；等价能力只在
  `config.toml` 的 `[tools]`/`[[permission.rules]]` 与 agent 文件 frontmatter 里，
  而 config **只有用户级、没有项目级**，隔离只能靠 `KIMI_CODE_HOME` 指到一次性目录。
- **没有沙箱、也没有工作目录强制。** 当前版连 `--work-dir` 都删了；changelog 明写
  "YOLO mode no longer asks before writing or editing files outside the working directory"。
  唯一的兜底 PreToolUse hook 是 **fail-open**（脚本报错/超时一律放行）——
  只能当审计，不能当安全边界。
- `-p` 与 `--yolo`/`--plan` 互斥（违反即启动失败），而文档自己的示例又写了
  `kimi --yolo -p "…"`。**文档自相矛盾**，管线里只能用裸 `-p`。

### OpenCode —— ✅ 升级：证据是源码级的

| 事实 | 等级 |
|---|---|
| stdin 收 prompt：判 `process.stdin.isTTY`，非 TTY 整块读走当 prompt | **源码确证**（v1.18.25），但**官方文档一个字没提** |
| 纯环境变量凭据：models 目录里 deepseek 的 `env` 是**单元素**，代码只在单元素时自动填 apiKey | 源码确证 |
| `deny` 规则把工具**从模型可见工具表里整个摘掉**（`disabled()`/`visibleTools()`），不是运行时才拒 | 源码确证 |
| 启动期两条出站：`models.opencode.ai/api.json` + 自动更新检查，各有 kill switch | 文档 + 源码 |

**两个必须传下去的坑**（都是我原方案没想到的）：

1. **`OPENCODE_CONFIG` 在 precedence 里排第 3，低于目标仓库自带的 `opencode.json`（第 4）。**
   把权限配置写进一次性目录再用 `OPENCODE_CONFIG` 指过去，会被目标仓库自己的配置覆盖 ——
   **一个现成的沙箱逃逸口**。要压过项目配置只能用 `OPENCODE_CONFIG_CONTENT`（第 6，inline）。
   这一条正好又说明了「播文件」是错的方向。
2. **`--auto` 与权限配置必须成对下发**：默认 "most permissions default to allow"，
   而不带 `--auto` 时 run 会把所有 ask **自动 reject**。只给一半，要么全放行要么全失败。

还有一条 `truthy()` 只认 `"true"`/`"1"` —— 写 `"yes"` 无效。

### zcode —— 结论不变

桌面 ADE，无 CLI 入口。GUI 自动化被合同 :18/:149 明令禁止。GLM 的目标已由内置
`zhipuai` API provider 达成。

## 三、落了什么

方案里的 P0（配 key）是用户的动作；P1.5 / P2 的实测项需要**装上 CLI**，而本机
`kimi` / `opencode` / `codex` 都没装（只有 `claude`）、0 个 key。所以能真做的是机制层
与那一半站得住的证据：

### 1. `extraEnv`：描述符可以给非密环境变量，顺序即强制

替代了原方案的 `seedFiles`。两家候选真正需要的都是这个。

```ts
readonly extraEnv?: Readonly<Record<string, string>>;
```

值是**编译期字面量** —— 结构上装不下 API key，凭据仍然只有 `credential` 一条路
（不变式 7）。而它**覆盖不了隔离键**，靠的是赋值顺序而不是黑名单：

```
extraEnv 先落 → PATH/HOME/XDG_*/凭据 后落 → 后写覆盖先写
```

反过来写的话，描述符里一行 `HOME: '/Users/…'` 就能把 synthetic HOME 指回真实 HOME，
整套隔离一句配置就没了。**黑名单会漏，顺序不会。** 三条负向断言钉着（覆盖不了
HOME/PATH/XDG、覆盖不了凭据变量、内置表里不含凭据字面量），去掉排序当场红两条。

### 2. 分阶段准入：`authorArgv: null` = 只准入审核方角色

两个角色的证据门槛差得远：审核方只读一段 diff、cwd 是空目录，"能不能写文件"
不影响结果；作者要在 candidate 目录里真的改代码，「工具白名单能不能压住 shell」
是安全边界，必须有实测证据。

没有这个字段，选择只剩「整家都不接」（浪费掉站得住的那一半证据）或
「连没验过的作者角色一起接」（拿安全边界赌文档）。

闸门落在 `author.ts` 而不只在 authority —— 那是所有作者调用的必经之路，
挡在那里才不依赖上游每个调用点都记得查。负向断言：拒绝发生在起进程之前，
candidate 目录逐字节不变、无退出码可记。

### 3. `opencode-deepseek` 条目：只准入审核方

- 选 DeepSeek 是因为它**没有自己的编码 CLI** —— 这条目才真的扩了覆盖面，
  而不是重复已有的 claude/codex 两条。vendor=DEEPSEEK 与两家都异构。
- `reviewArgv: ['run', '--model', 'deepseek/deepseek-chat']` —— argv 里**不放任何
  positional message**，prompt 全走 stdin；也刻意不写 `opencode run -`
  （源码里没有对 `-` 的特殊处理，它会被当成普通 message，把 prompt 污染成 `-\n<正文>`）。
- `extraEnv` 关掉两条启动期出站，权限走 `OPENCODE_CONFIG_CONTENT` 全 deny。
- **`authorArgv: null`** —— 作者角色待实测：多份 config 的 permission 是深合并还是
  整体替换**没有确证**，而那决定 bash deny 压不压得住。不拿文档推断赌安全边界。

顺带修了一条测试：原来断言"内置**两个**连接器"，现在改成断言**性质**
（vendor 两两互异、connectorId 唯一）—— 表是会长的，钉数字的断言每加一家就红一次，
而它想保护的性质根本没变。

## 四、验证

67 文件 / **1232 测试**全绿；node+web 双 typecheck；完整构建；三进程自检 `ALL PASS`。
两个新守卫都做了"去掉就红"的确认。

**没有的证据**：`opencode-deepseek` 这一条**没有真机跑过**——本机没装 opencode、
没有 DEEPSEEK_API_KEY。它今天的行为是探测报 `NOT_INSTALLED`（如实）。

## 五、教训

1. **同名产品出现两个文档站，先分清哪个是当前的。** 这次三条引用全部来自被淘汰的
   产品，而它们看起来都像官方文档。
2. **"落地前重核"不是走形式。** 上一篇自己写了这句，这次真核出了推翻性的结论 ——
   如果直接按方案写代码，会做出一个前提不成立的播种机制，外加一个 stdin 未确认的
   Kimi 条目。
3. **机制的形状要等消费者确定之后再定。** 我先建了 `seedFiles` 再去核实，
   结果两家候选都不需要它。顺序反过来只多花了十几分钟，但如果没核实就提交，
   那就是一个没有消费者的机制长在安全边界上。
4. 与 08-28 那批是同一个教训的第四次：**动手前先量**。

## 落点

三个待人决定（D1 已被证据改写）：

- **D1'**：Kimi 暂不接入 —— 等它 ① 确认 `-p` 能从 stdin 收 prompt、
  ② 给出 headless 可控的工具白名单。两条都不是我们能替它解决的。
- **D2'**：OpenCode 取了方案 A（一模型一条目），且**只准入审核方**。
  作者角色等一次实测：目标仓库放 `{"permission":{"bash":"allow"}}`，
  我们用 `OPENCODE_CONFIG_CONTENT` 下 deny，验证 bash 真的消失。
- **D3**（不变）：计划语言里的「接入 zcode」改写为
  「GLM 已支持（API）/ zcode 等 CLI」。

以及那句没变的：**这条线此刻最值钱的一步仍然是 `export` 两个 API key。**
