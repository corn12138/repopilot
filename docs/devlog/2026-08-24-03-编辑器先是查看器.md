# 编辑器先是查看器

方向升级：把原型推进成**真正可用的 Agent IDE**。第一片是 IDE 骨架 ——
多标签代码编辑器面板 + 四栏布局（侧栏 | 文件树 | 编辑器 | 运行面板）。
路线判断先说清楚：不另起炉灶。1020 条测试、权威层、三进程边界都是资产，
"真正的 IDE"是在这上面长出来的，不是旁边再盖一栋。

## 第一个设计决定：编辑器是查看器

一个"IDE"最扎眼的缺口是没有代码编辑器。但这个产品的核心不变式是
**宿主仓库只读、改动只经 MaterializedWorkspace 的 CAS 事务**——
如果编辑器一上来就可写，用户的手改和 Agent 的补丁会在同一棵树上打架，
整个 mutation 权威模型（generation、receipt、事务回滚）都要重谈。

所以第一片的编辑器**显式只读**：CodeMirror 6 挂了 `readOnly` + `editable: false`，
空态文案直接写给用户看："改代码的唯一路径仍是任务 → 补丁 → 你来接受"。
用户可写的编辑器不是不做，是它必须作为"用户发起的 mutation"走同一套权威
（改动进 candidate → 归一化 → CAS，与外部作者同形），那是下一个需要单独设计的切片，
不该在铺布局的这一片里顺手做掉。

## 数据通道：一条新 IPC 都没加

和证据聚合那片一样，动手前发现要的通道早就在：`files.tree` / `files.read`
本来服务文件树预览，带着完整的诚实语义 ——
generation 守卫（读文件必须携带最后一次 tree 确认的代号，错代 CONFLICT）、
二进制探测（NUL 字节，不往 Renderer 塞乱码）、截断如实标注、
`resolveManaged` 路径安全（拒绝越界与 symlink）。

编辑器面板直接消费这两条：每个标签懒加载，读到 generation 冲突自动
"刷新来源重试**一次**"——只一次，再冲突就把错误摆出来，不做无限重试。
Agent 改动落地（refreshKey 变化）→ 全部标签内容作废重读。
Renderer 依然没有 FS，一个字节都不绕过 Core。

## 布局：显式指定列，不依赖 DOM 顺序

编辑器活跃时进 `app.ide` 布局。四个面板的 grid-column 全部显式指定 ——
文件树的开关只改列数，不许让编辑器换位置。CodeMirror 全部本地打包
（electron-vite 构建过 selftest），语法高亮颜色走 `--syn-*` CSS 变量，
主题层可整体覆盖；认不出扩展名的文件按纯文本展示，不硬套语法。

## 踩了什么坑

### 挂载时两个 effect 抢着加载同一个标签

「来源初始化」和「激活标签」两个 effect 在挂载时都会想加载活动标签，
双请求的结果互相覆盖 —— 后到的赢，而后到的可能是过时的那个。
测试先红的是重试用例（期望 2 次 tree 调用，实际 3 次）：竞态不是猜出来的，
是断言数出来的。

修的时候又发现第一版的 epoch 设计有个更隐蔽的洞：`load()` 内部自增 epoch，
会把**并行加载的其他标签**误判为过期 —— 快速切两个标签，先发的那个永远
落不了地，而且状态停在 LOADING 不再重试。修法：epoch 只代表"来源代"
（快照/Run/Agent 改动时由来源 effect 递增），load 只读取；同路径用
in-flight 集合去重，finally 释放。

教训：**竞态防护的"代"要绑在真正会失效的那个维度上。** 绑在"每次请求"上，
防护本身就成了误伤源。

## 可复用的结论

- **给现有系统加大件，先问它撞不撞既有权威。** 可写编辑器撞 mutation 权威 →
  拆成"查看器现在做、写路径单独设计"，而不是先做了再补规矩。
- **通道齐不齐是设计质量的回声。** 文件树当年把 generation/二进制/截断做诚实了，
  编辑器就是纯消费方；又一次零新 IPC。
- **布局的列位置显式声明。** 依赖 DOM 顺序自动放置，任何面板开关都可能让
  别的面板跳位。
- **重试要有次数上限，且上限写在注释里。**
