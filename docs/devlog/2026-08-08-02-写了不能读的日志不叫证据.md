# 写了不能读的日志，不叫证据

> 开发记录 · 2026-08-08 · RepoPilot

`store.ts` 的注释是这么写的：

```ts
/**
 * 追加事件日志。
 *
 * 这是 Run 事实的持久化载体：Renderer 重载、Core 重启后都从这里恢复时间线，
 * 而不是从 UI 内存或模型总结重建（PRD-RUN-001 / PRD-DESK-003）。
 */
export class EventStore { … }
```

README 里也写着同样的承诺。事件确实一条不落地写进了 `events.jsonl`。

但 `authority.ts` 的构造函数是这样的：

```ts
constructor(private readonly push: (event: PushEvent) => void) {
  ensureDataRoot();
  for (const rec of readJson<ProjectRecord[]>(PATHS.projects, [])) {
    this.projects.set(rec.ref.projectId, rec);
  }
}
```

只 rehydrate 了 `projects.json`。而 `new EventStore(runId)` **只在 `createTask` 里
构造过**。也就是说：磁盘上那些 `events.jsonl`，对已经存在的 Run 永远不会被读回来。
`run.get` 一律走到 `require()` 抛 `NOT_FOUND`。

**关掉应用，所有历史 Run 连同已经跑完但还没导出的补丁，在界面上全部消失。**

写了不能读的日志，不叫证据。

## 光有事件流还不够

第一反应是"那就在启动时把 events.jsonl 读回来"。但很快撞墙：
**从事件流重建不出可交付的补丁。**

`PATCH_SEALED` 事件的 payload 长这样：

```ts
this.emit(record, 'PATCH_SEALED', `补丁已封存：${patch.files.length} 个文件`, {
  patchId: patch.patchId,
  digest: patch.digest,
  files: patch.files.map((f) => f.path),
});
```

只有 id、摘要和文件名 —— `unifiedDiff` 正文不在里面（当初刻意不放，怕事件日志膨胀）。
所以事件流能告诉你"曾经封存过一个补丁"，但给不出那个补丁。

结论是需要两份互补的东西：

| | 记什么 | 回答什么问题 |
|---|---|---|
| `events.jsonl` | 追加的流水账 | 发生过什么、按什么顺序 |
| `state.json` | 当前状态快照 | 现在是什么、补丁正文是什么 |

## 两份文件之间的崩溃窗口

有两份文件就有不一致的可能。崩溃可能落在两次写之间，产生两种方向：

- **事件比状态新** —— 时间线走到了一半，状态还停在上一步
- **状态比事件新** —— 状态说「成功了」，时间线里却没有对应的事件

第二种危险得多：它是一个**凭空出现的成功**。

所以定死写入顺序：

```ts
/**
 * 把 Run 的当前状态快照写盘。
 *
 * 调用约定：**先 append 事件，再调这个**。事件流是流水账，状态快照是结算结果；
 * 顺序反了会在崩溃窗口里产生"状态说成功、时间线停在半路"的说谎方式。
 */
private persist(record: RunRecord): void { … }
```

并且在快照里记下当时的事件水位：

```ts
eventHighWatermark: record.events.lastSeq(),
```

启动时对一下账，不一致就**如实标注**，不假装同步：

```ts
const eventsAhead = events.lastSeq() > s.eventHighWatermark;

evidence: eventsAhead ? 'EVENTS_AHEAD' : 'INTACT',
evidenceDetail: eventsAhead
  ? `事件流已到 seq ${events.lastSeq()}，状态快照停在 seq ${s.eventHighWatermark} —— 末尾若干事件未反映在状态里`
  : null,
```

UI 上是一条黄色横幅：「时间线是完整的，但上面的状态、预算和补丁可能不是最后一刻的样子。」

## 被打断的 Run 该是什么状态

一个在 `EXECUTING` 时被杀掉的 Run，重启后应该是什么？

不能保持 `EXECUTING` —— 它等的那个执行器已经不存在了，界面上转圈转到天荒地老。
也不能算 `CANCELLED` 或 `FAILED` —— 那两者是**在运行中做出的决定**，
而这个是"没来得及有结论"。混用会让事后审计分不清「用户取消了」和「应用被关了」。

所以加了一个终态：

```ts
/**
 * 进程退出时该 Run 还在执行中，重启后无法续跑。
 *
 * 与 CANCELLED / FAILED 严格区分：那两者是**在运行中做出的决定**，
 * 这个是"没来得及有结论"。
 */
| 'INTERRUPTED';
```

## 一个例外：待审补丁可以跨重启活下来

最初的方案是"所有非终态一律落 `INTERRUPTED`"。写到一半发现这条太粗暴。

`AWAITING_PATCH_REVIEW` 是特殊的：补丁已经封存、验证已经跑完，
**接受与否是一次纯粹的状态转换，不需要活的执行器**。

如果把它也打成 `INTERRUPTED`，那就意味着：你晚上跑完一个任务，
补丁摆在那儿等你看，你关了电脑，第二天打开 —— 补丁作废了。

而这恰恰是最有价值的场景。所以：

```ts
/** 非终态且不是待补丁审查的，落成 INTERRUPTED 并补一条清理说明 */
private closeInterruptedRun(record: RunRecord): void {
  const status = record.view.status;
  if (isTerminal(status) || status === 'AWAITING_PATCH_REVIEW') return;
  …
}
```

重启后这个 Run 依然可以接受、可以导出补丁、可以 `git apply` 回仓库。
只有工作区文件树不可用（那份隔离副本随进程结束了），UI 上说清楚就行。

## 快照坏了怎么办

现有的 `model-profiles.json`、`custom-providers.json` 都是这个套路：

```ts
export function readJson<T>(path: string, fallback: T): T {
  try {
    return JSON.parse(readFileSync(path, 'utf8')) as T;
  } catch {
    return fallback;   // 读失败静默降级成空
  }
}
```

后果是：**「配置损坏」长得跟「从未配过」一模一样。** 用户打开设置页，
看到所有 provider 都是「未配置」，以为自己没填过。

证据文件不能重蹈覆辙。`readRunState` 返回判别联合，失败要说原因：

```ts
export type LoadResult =
  | { readonly ok: true; readonly state: PersistedRunState }
  /**
   * 读不出来是一种**要展示的结果**，不是"当作没有"。
   * 一个损坏的 Run 必须留在列表里并标明损坏，而不是凭空消失。
   */
  | { readonly ok: false; readonly reason: string };
```

读不出来的 Run 用事件流能捞多少算多少，标成 `DAMAGED` 留在列表里：

> **状态快照损坏，只能展示事件流。**
> 补丁内容与验证记录无法恢复，因此不能导出或应用。
> 这个 Run 保留在列表里是为了让「曾经跑过一次」这件事本身不丢失。

顺带一提，`state.json` 也带了 `schemaVersion`，版本高于当前程序时**拒绝读取**
而不是按旧格式硬解。

## 悬空的工作区

恢复出来的 Run 没有活工作区（目录可能还在，也可能已被清理）。
类型上直接体现：

```ts
interface RunRecord {
  /**
   * 从磁盘恢复的 Run 没有活工作区（目录可能还在，也可能已被清理），
   * 所以这里可空。所有摸它的地方都必须显式处理 null，不能让它抛未分类异常。
   */
  readonly workspace: MaterializedWorkspace | null;
}
```

改成可空之后，TypeScript 直接把所有需要处理的地方点了出来 —— `execute`、
`browseRoot`、`setStatus`、`cancel`、`applyPatch`。每一处给一个 typed 拒绝，
而不是让一个 `null` 在深处炸成未分类异常。

`execute()` 里那道特别写成不变式违规：

```ts
// 恢复态的 Run 没有活工作区，永远不该走到执行路径。真走到了就明确停住，
// 而不是让一个 null 在深处炸成未分类异常。
const workspace = record.workspace;
if (!workspace) {
  this.setStatus(record, 'INTERRUPTED', '内部不变式违规：尝试执行一个没有工作区的 Run');
  return;
}
```

## 测试抓到的一个真 bug

写单测的时候，`writeRunState` 单独调用直接 ENOENT：

```
Error: ENOENT: no such file or directory, open '…/runs/run_xxx/state.json.tmp'
```

原因是它靠 `EventStore` 的构造函数顺手 `mkdirSync` 建目录。生产路径上
`createTask` 里 EventStore 先构造，所以碰巧成立 —— 这是**隐式耦合**。

修在根上，让 `writeJsonAtomic` 自己保证父目录：

```ts
/**
 * 自己保证父目录存在 —— 不依赖"调用前某个别的东西已经建过目录"这种隐式耦合。
 * （这条是被测试抓出来的：writeRunState 原本靠 EventStore 构造函数顺手建目录，
 * 生产路径上碰巧成立，单独调用就 ENOENT。）
 */
export function writeJsonAtomic(path: string, value: unknown): void {
  mkdirSync(dirname(path), { recursive: true });
  …
}
```

## 自检抓到的另一个真 bug

我给自检加了真实的重启验证：造一个 Run → 杀 Core → 看历史还在不在。
第一次跑出来：

```
[selftest] FAIL 重启后 run.list → {"code":"CORE_UNAVAILABLE","message":"Agent Core 已退出"}
```

`core.kill()` 之后 `coreReady` 不会同步变 false —— `exit` 事件是异步到达的。
在那个窗口里 `callCore` 认为 Core 还活着，把消息 `postMessage` 给一个已死进程，
然后那个 Promise **永远不会 resolve**。

```ts
/**
 * 主动杀掉 Core。
 *
 * 必须**同步**把 coreReady 置 false —— `exit` 事件是异步到达的，在那之前
 * callCore 会认为 Core 还活着，把消息 post 给一个已死进程，然后那个 Promise
 * 永远不会 resolve。（这条是被重启自检抓出来的。）
 */
function killCore(): void {
  coreReady = false;
  core?.kill();
}
```

## 最后的证据

自检里造一个真实的、跑到一半的 Run，然后杀进程。为了不产生任何外部网络请求，
把模型路由临时指向一个必然连不上的本地端口（`https://127.0.0.1:9/v1`，
discard 端口），Run 依然会真实地走 createTask → 基线验证（真跑 `npm run build`）
→ 模型调用失败，我们在基线验证那一两秒的窗口里下手：

```
[selftest] 已造出 Run run_36c89112...，等它进入执行中
[selftest] 杀 Core 前该 Run 的状态：EXECUTING
[selftest] Core 重启用时 2255ms
[selftest] PASS 重启恢复 → 重启前 1 个，重启后 1 个（1 个 restored）；残留非终态 0
[selftest] PASS 恢复的 Run 可读 → 6 条事件 · status=INTERRUPTED · evidence=EVENTS_AHEAD
[selftest] PASS 被打断的 Run 有明确终态 → INTERRUPTED（进程退出时该 Run 处于 EXECUTING）
```

`evidence=EVENTS_AHEAD` 也是对的 —— 进程正好死在两次写之间，一致性检查
如实抓到了。

## 一句必须说清的

**PRD-RUN-004 仍然是 PARTIAL，不是 DONE。**

这次只做了「重启后历史可读、被打断的 Run 有明确终态」，不含带
snapshot/profile/policy hash 校验、hash 不匹配 fail-closed 的**可续跑 Checkpoint**。

这个区分我写进了 commit message。因为这一整轮审计抓的就是这类
「把能读回历史说成能恢复运行」的判宽 —— 自己犯同样的错就太滑稽了。

## 可以带走的

1. **注释里的承诺要有测试撑着。** "重启后从这里恢复"写了三个月，没人验过。
2. **只写不读的日志是负资产。** 它给人一种有审计能力的错觉。
3. **两份文件就要定死写入顺序**，并记水位对账。允许"事件比状态新"，
   绝不允许反过来。
4. **读失败要报原因，不要静默 fallback。** 否则「损坏」和「从未存在」长得一样。
5. **需要新语义时加新状态，别复用旧的。** `INTERRUPTED` 和 `CANCELLED` 的区别，
   三个月后回来看是救命的。
6. **把字段改成可空，让类型系统帮你找出所有要处理的地方。**
