# 作者说"写完了"不算，目录差异才算

> 开发记录 · 2026-08-19 · RepoPilot

用户要一个高效 MVP：把双审也加上 —— Codex 写、Claude 审，或者反过来；
"Codex 写完/审完的状态怎么拿到，然后立刻通知另一边"，他说这是难关。

这篇写这一轮怎么把"难关"拆没的，以及落地时踩的三个坑。结论先放这：
**状态不用"获取"。只要外部 Agent 是我们起的一次性子进程，"写完了" = 退出码 + 平台对它工作目录做的 tree diff，
没有第二种来源；"通知另一边" = 编排器在这个 promise resolve 的下一行发起下一次调用。** 不需要 webhook、轮询、共享状态文件。

## 一、审核那一侧早就是这样了

原型里外部 CLI 当只读审核方（[connector.ts](../../prototype/src/core/external/connector.ts)）的形态是固定的：
`claude -p` / `codex exec … -`，prompt 走 stdin，synthetic HOME、整份替换的环境、一个凭据变量、超时、进程组整树终止。
结束态是判别联合：`TIMED_OUT | CANCELLED | FAILED(exitCode) | SEALED`，解析不出 JSON 就 FAILED 且**不编造发现**。

所以"Codex 审完了"这个状态从来就是"子进程退出 + stdout 解析成功"。缺的是"写"那一侧 ——
README 里明确写过 `CANDIDATE_AUTHOR` 不做："需要 disposable candidate workspace + single-writer epoch + normalizer，风险高一个量级"。
这一轮就做这三样。

## 二、边界：外部作者只在副本里写，主线只认归一化后的 MutationPlan

TD-DEC-016 其实早把允许的形状写好了：`disposable candidate workspace → normalized MutationPlan → canonical CAS`。落到代码上是四步：

```text
workspace.exportCandidate()        把 active generation 的内容 clone 成一次性 candidate-<id> 目录（不是 generation，没有编号）
runExternalCliAuthor(...)           cwd = candidate；退出为零 → listTree(candidate) vs baseTree → CandidateTreeSeal
applyCandidate(...)                 seal → MutationPlan：MODIFIED→REPLACE_WHOLE_FILE+receipt，ADDED→CREATE_FILE，
                                    DELETED→整笔拒绝，非 UTF-8→整笔拒绝 → applyMutationPlan（receipt/CAS/protected/预算/失败零写入照旧）
workspace.discardCandidate(path)    finally 里丢弃
```

这样主线上**没有第二条落盘路径**。外部作者写了什么不算数：退出非零/超时/取消，candidate 里的内容一个字节都不读（`seal=null`）；
退出为零也只是"可以去 diff"，能不能进主线由 `applyMutationPlan` 说了算。它输出的那段 `{"summary":…}` 只是 `authorNote`，
进事件、展示给人，**不驱动任何判定** —— 测试里专门造了一个嘴上说"只改了 app.ts"、实际改了三个文件外加删一个的假 CLI，seal 记的是三改一删。

为什么 MODIFIED 用 whole-file 而不是 exact-span？因为我们手里有整个新文件，receipt 绑的是整文件 digest、apply 时重验，
比从 diff 反推 oldText 再去"唯一命中"更不可能改错位置；而且 whole-file 本来就是 P0 允许的三种 operation 之一。
DELETED 不降级成"留个空文件"—— 删除是 P0 hard deny，空文件是撒谎。

双审循环一行没改。`runAgent` 里执行/自修复、`runRemediationPass` 里整改，都是"如果有 `externalAuthor` 就调它，否则走内部模型"；
交叉审核的收敛语义（2 审 1 改、指纹判进展、转人工）对"谁在写"无知 —— 和"谁在审"一样。

## 三、踩了什么坑

**1. 整改悄悄走回了内部模型。** 黄金路径、自修复、拒绝路径都绿了，双审闭环那条红：`stopReason=ERROR`，事件里一行
"自动整改 … 由实现方 route 执行 → 模型调用失败：api.deepseek.com 的模型脚本已耗尽"。
`runCrossReview` 在 authority 里为循环**另建了一份 AgentDeps**，我只在 `execute()` 那份里塞了 `externalAuthor`。
后果不是报错，是换了作者 —— 用户点名 Codex 写，整改却由内部模型写。幸亏 e2e 的模型脚本"耗尽即抛"而不是复读最后一条，
否则这条会绿着过去。修法是两份 deps 都带 `externalAuthor`，那条 NOTE 也改成如实写"外部作者，candidate → 归一化 → CAS"。

**2. 一个 `vi.fn()` 把四条 a11y 测试全红了。** 任务输入区要列出本机连接器，我在 `useEffect` 里 `call('crossreview.reviewers').then(...)`。
已有的 a11y 测试把 `call` mock 成裸 `vi.fn()`，返回 undefined，`.then` 直接炸。
我没去改那四条测试的 mock —— 它们的断言和连接器无关，改 mock 是让测试迁就新代码。改成 `await call(...)` + try/catch，
mock 返回 undefined 也只是"没有外部选项"。**探测失败不该阻断建任务**，这本来就是该有的语义。

**3. 作者的 flag 是写死的。** `claude -p --permission-mode acceptEdits --allowedTools Read,Glob,Grep,Edit,Write,MultiEdit`、
`codex exec … --sandbox workspace-write -`，都是在本机对着 `--help` 核过的（Claude 不放行 Bash：验证由平台跑，它不需要起进程；
Codex 靠自己的 seatbelt 只写 cwd、默认无网）。版本一换这些 flag 可能漂。这里没有做 capability probe 去探 flag，
但漂移的表现是 FAILED/TIMED_OUT，**不会假绿**：退出码非零不读 candidate，卡在交互提示上会被平台超时。先接受这个残余。

还有一条不是坑，是要明说的取舍：外部作者是**结果层治理**（diff 归一化 + protected path + 验证），没有内部 Agent 那种逐 tool call 的动作层审批。
它改文件的过程是黑盒，平台只在它退出后审它留下的东西。对自用 MVP 我认为可接受，但这得写进 DEC-013 的修订，不能默认。

## 五、可复用的结论

- **把外部 Agent 变成你起的一次性子进程，状态问题就消失了**：退出码是终态，目录差异是事实，stdout 是备注。
- **采用与封存分开**：封存只描述"有什么不同"，采用必须走你唯一的写入路径；这样任何新选手都自动继承所有不变式。
- **编排器的每一份 deps 都要带上"谁在写"**，否则换作者会静默发生 —— 让测试脚本"耗尽即抛"，别复读。
- **删除不能降级成空文件，未知 token 不能记成 0，作者自述不能当状态** —— 同一条原则的三个面。
