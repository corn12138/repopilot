上午把「同屏工位与本机会话观察」写进 PRD/TD r14（见 [01](2026-09-02-01-窗口嵌不进来但日志本来就在.md)），
其中 ASM-027 承认了一件不舒服的事：观察面板要读的两份日志都是**未文档化内部格式**，
没有任何合同保障，随版本静默漂移。当时开的药方是「字段快照回归断言，照 OpenCode stdin
断言的先例」。下午把药方落成了代码 —— 面板还不存在，断言先存在。

## 一、核心取舍：两层字段模型，防一个具体的误报

最直接的做法是「把见过的字段存下来，下次少了就报警」。这会立刻误报：
今天抓的样本恰好没有 `queue-operation` 记录，不等于 claude 删了这个 type ——
**样本里没出现 ≠ 格式里被删掉**。

所以快照按 type 记两层：`required` = 该 type **每条**记录都有的键；`optional` =
只在部分记录出现的键。对照时只有两种情况判红（都以基线 required 为准）：

- **MISSING**：本次观测到了该 type，但某必现键一条记录都没有；
- **DEMOTED**：必现键只剩部分记录有。

整个 type 没观测到？进 `unobservedTypes` 报数，不定罪。新键新 type？ADDITIVE，
词表该更新了，但面板照常工作。只有 BREAKING 才要求观察面板降级为「格式未知」——
错读比不读更糟，这是 ASM-027 里写好的降级语义。

## 二、基线从 1 个样本扩到 79 个文件

上午的 `EVI-LOCAL-SESSION-JOURNAL-001` 是单机各一份样本（580 行 + 124 行），
narrow claim 只敢说「存在且可解析」。生成基线时改成有界扫描（每家最新 40 个文件、
单文件 20k 行上限，超限跳过并报数）：

- claude：40/545 个文件、46777 条记录、17 种 top type（比单样本多出 9 种 ——
  `atis-latch`、`bridge-session`、`cost-state`、`file-history-snapshot`、`pr-link` 等，
  单样本基线要是直接拿去对照，第一次全量扫描就会把这些误报成「新 type 漂移」）；
- codex：39/1226 个文件、18052 条记录、7 种 top type + 23 种 payload type，
  1 个文件读失败 —— 计数，不抛（观察者不能被日志垃圾弄崩，这条也进了负向测试）。

快照文件只含**键名与 type 名**，不含任何记录值，所以可以提交进公开仓库
（DEC-020 的「内容零出站」在这里的具体形态：schema 元数据不是内容）。
两份合计 12KB，17+7 种 type 名逐个看过，全是枚举值，无一沾用户内容。

## 三、probe 是显式 opt-in，`pnpm test` 不碰 HOME

工程诚实规则说自检不碰真实数据，但这个工具的**全部意义**就是读真实日志比对。
解法是拆开：纯逻辑（capture/diff/parse）走普通单测（19 个，负向为主体：坏 JSON、
超键数记录、超行数截断、乱序快照、required∩optional 重叠、跨 vendor 对照全都得抛
或计数）；真实 HOME 的读取只在 `pnpm probe:journals` 里发生 ——
环境变量门控，默认整个文件 skip，CI 和别人的机器上永远不跑。
`REPOPILOT_PROBE_JOURNALS=update` 重生成基线（升级两家之后跑的那一次），
默认模式纯对照。update → compare 闭环今天跑过：两家 verdict 都是 MATCH。

放置位置遵守 TD-DEC-022：`src/main/observer/` —— 观察读点在体验侧，不进 Core。
