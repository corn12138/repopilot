# 98.7% 在等模型

上一篇修完规划轮次上限，剩下的清单是「R0 读并行」——TD §9.4 冻结过的 P0 设计，
图上也画着 `tools: reads overlap, writes exclusive`。我开了个工作流去做勘察与
对抗验证，准备认真写这段并发代码。

**动手前又量了一次。这次的数字让整件事直接取消。**

## 读并行值多少钱

同一个 `run_074bde20cdec4d7dab29`，把每次工具调用的 `durationMs` 加起来：

| | 耗时 | 占比 |
|---|---|---|
| Run 总墙钟 | 171,343 ms | 100% |
| **全部工具执行** | 2,171 ms | **1.3%** |
| ├ `verify_command`（命令类，本就串行） | 1,927 ms | 1.1% |
| └ **全部 `fs_*` 读取** | **244 ms** | **0.14%** |
| 工具耗时**中位数** | **1 ms** | — |
| **模型往返** | 169,172 ms | **98.7%** |

并行 36 次读取，理论上限省 244 毫秒——**在 171 秒里**。而这是整个改动清单里
最危险的一段代码：共享账本、`tool_use`/`tool_result` 配对、取消语义、预算原子性。

道理很简单：这些读取是**本地文件系统**读一个**已物化的工作区**，本来就是亚毫秒级。
TD 的 `READ_PARALLEL` 设计没错，它对**昂贵的工具**（网络调用、LSP、远程沙箱）是对的；
只是我们现在的工具不昂贵。

于是我把那个工作流停了。它的三个前提——materialize 要建、prune 有收益、读并行值得做——
**已经被测量逐个推翻**，让它跑完只会产出一份诱人去做错事的设计。

## 那 98.7% 能动吗

顺着这个数往下查，问题变成"模型往返里有什么是我们能改的"。查到两件事：

**一、我们不发流式请求。** `src/core/model/` 全文没有 stream。每轮阻塞等完整响应，
12 轮 × 约 14 秒。流式能改善**感知**延迟（字一个个出来），但改不了吞吐；
而图上那个 `starts tools mid-stream`（边出边起工具）在我们这儿也省不到东西——
工具本身就 1 ms。

**二、我们把计费构成扔了。** 这个是真问题：

```ts
// openai-compatible.ts
inputTokens: data.usage?.prompt_tokens ?? null,
// anthropic.ts
inputTokens: data.usage?.input_tokens ?? null,
```

只取总数。而多轮循环**每一轮都把整段历史重发一遍**——那个 Run 12 轮累计输入
218,453 token，绝大部分是重复前缀。这类 token 在支持前缀缓存的 provider 上
按远低于常规输入的价格计费：DeepSeek 自动前缀缓存会返回 `prompt_cache_hit_tokens`，
Anthropic 显式 `cache_control` 会返回 `cache_read_input_tokens`。

**我们一个都没解析。** 账本上写着"218k 输入 token"，看起来比实际贵得多。
对一个把"诚实记账"当立身之本的产品，这是**少报事实**——和把未知折算成 0 是同一类问题。

## 改了什么

`ModelResponse` 增加两个**可选**字段（可选是为了让既有测试替身与历史记录兼容——
没写就是没报），两家适配器分别解析：

- anthropic：`cache_read_input_tokens` / `cache_creation_input_tokens`
- openai 兼容：`prompt_cache_hit_tokens`（DeepSeek 口径）
  ∥ `prompt_tokens_details.cached_tokens`（OpenAI 口径）

经 Gateway 进 `ModelEgressManifest`，用量面板多一行「其中缓存命中」，
显示 token 数与占本轮输入的百分比。

**没有回报时写「未回报（该 provider 没给缓存构成）」，不是「0」。**
这条单独有测试钉着——provider 可能根本没有前缀缓存，也可能有但没告诉我们，
两种都不该显示成"命中 0"。

## 这也是"usage bar 怎么加"的答案

用户问能不能把一个 Claude Code 用量条加进来。逐格拆完，只有一格真属于我们，
而且不是抄来的：**把已经收到、却被我们丢掉的计费构成显示出来。**

其余几格都过不了自家的线：速率限制与剩余额度——BYOK 下套餐余量在供应商侧，
`App.tsx` 里早写着「这里不猜」；美元成本——要靠价格表推算；
上下文百分比——我们**根本不知道任何模型的窗口大小**（全局搜索 `contextWindow` 零命中），
按 TD:707「缺少 context limit 必须标 UNKNOWN，不能伪造百分比」，那一格只能空着。

**不做缝合怪的判据不是"这个功能好不好"，是"这个数字我们能不能诚实地拿到"。**

## 一天之内同一个教训三次

| 打算做的 | 量完发现 |
|---|---|
| 建 materialize 层 | 早就实现了（`tools.ts:13`） |
| 建 prune 层 | 真实数据上只有 6% |
| 建读并行 | 0.14%，而它是最危险的代码 |

三次都是同一句话：**动手前先量。** 三次的代价分别是"白建一个子系统"、
"为 6% 冒风险"、"为 0.14% 写并发"。而真正找到的两件事——一个魔法数字 12、
一份被丢掉的计费构成——都不在原计划里，都是量的时候撞见的。

还有一个次生教训：**我为一个未经测量的前提开了工作流。** 那个工作流本身没问题，
错在它的输入——三个"要做的事"没有一个先验证过值不值得做。
下次的顺序应该是：先量，再开工作流。
