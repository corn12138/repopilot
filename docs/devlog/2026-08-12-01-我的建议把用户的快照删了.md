# 我的建议，把用户正要用的快照删了

> 开发记录 · 2026-08-12 · RepoPilot

上一轮我给保留策略做了界面出口，末尾顺口说了一句：

> 顺带：真实数据根里躺着历史测试留下的 42 个快照垃圾，用刚上线的
> 「设置 → 数据保留 → 立即清理」就能扫掉（被引用的不会删）。

第二天用户点「开始」，报错了。

```
[core] unhandled Error: ENOENT: no such file or directory, lstat
  '.../RepoPilotPrototype/snapshots/snap_f9c419f92fa3456284ff'
  at cloneTree → MaterializedWorkspace.create → RunAuthority.createTask
```

## 先查证，别猜

清理器每轮都会落一份摘要。翻出来：

```
$ cat last-purge.json | python3 -c "…"
status COMPLETE scanned 33 deleted 4
deleted snapshots: 1
  snap_f9c419f92fa3456284ff        ← 正是报错路径里那个
```

链条完整了：导入项目 → 界面拿到 `snapshotId` → 跑清理 → 清理判定它「无 Run 引用」
删掉 → 点「开始」→ `cloneTree` 找不到目录。

我那句"被引用的不会删"是对的，问题在于**刚导入、还没创建任务的快照，
天然就是"无引用"**。而那恰恰是用户盯着界面准备开工的时刻。

## 三处都有问题

### 1. 快照没有宽限期

工作区早就有：

```ts
const due = (info.terminalAt ?? info.updatedAt) + workspaceGrace;
if (now < due) { items.push(keep('WORKSPACE', runId, 'KEPT_NOT_DUE', …)); continue; }
```

快照那段直接就是：

```ts
if (liveSnapshots.has(snapshotId)) { keep(…, 'KEPT_REFERENCED'); continue; }
items.push(remove('SNAPSHOT', snapshotId, snapshotDir(snapshotId), '无 Run 引用'));
```

复用同一条宽限期，新鲜快照一律 `KEPT_NOT_DUE`，理由里写明"可能正要用它建任务"。

### 2. `createTask` 不校验，让裸 ENOENT 冒泡

内存里的 `snapshots` map 有它、磁盘上没有 —— 这是**真实会发生的组合**，
不是不可能状态。之前不校验，直接进 `cloneTree`，抛出带宿主绝对路径的原始
`ENOENT`，一路冒泡成 `[core] unhandled`。用户看到的是一个没有原因、
也不知道该怎么办的失败。

悬空引用要在入口处判死，并且告诉用户下一步：

```ts
if (!existsSync(snapshotDir(snapshot.snapshotId))) {
  throw platformError('CONFLICT',
    '这个快照已不在磁盘上（多半是被数据保留清理回收了），无法用它创建任务',
    '点项目名重新导入一次即可 —— 重新导入会生成新的快照。');
}
```

### 3. 界面没有自救出口

现在 composer 顶部会出现「快照已被清理回收，**重新导入**后即可继续」加一个按钮，
而不是把红色堆栈丢给用户琢磨。

## 测试里的坑：固定的 NOW 遇上真实的 mtime

给宽限期补测试时，两条既有用例红了：

```
× 无引用的快照删掉
× 本轮刚被删掉证据的 Run，其独占快照同一轮就回收
```

它们造的是刚创建的快照并期望立即删除 —— 正是被宽限期改掉的行为，红得合理。
但改的时候发现更深一层：

```ts
const NOW = Date.UTC(2026, 7, 7, 12, 0, 0);   // 固定的过去时间
function mkSnapshot(id) { mkdirSync(dir); … }  // mtime 是真实当下
```

目录的 mtime 是**真实当下**（2026-08-12），而 `NOW` 是固定的 08-07。
`createdAt > NOW` 恒成立，所有快照相对 `NOW` 永远算"新鲜"——
宽限期这条分支根本测不了，写什么断言都是假的。

给 `mkSnapshot` 加可控年龄，用 `utimesSync` 相对 `NOW` 回拨：

```ts
function mkSnapshot(id: string, ageMinutes = 0): string {
  …
  const at = new Date(NOW - ageMinutes * 60_000);
  utimesSync(dir, at, at);
}
```

然后原来那条"无引用就删"改成"无引用**且过了宽限期**才删"，
再补一条钉住这次事故本身：刚导入、无引用的快照必须 `KEPT_NOT_DUE`。

## 同一天的另外两处"看不见"

用户还指了两个地方："我有没有自定义搞不清"、"任务选项填写成功与否也是无感的"。

第一个里藏着更糟的东西。`hasCustom` 要求命令非空才生效，但 chip 只有
选中/未选中两态 —— **"打开了自定义但没填命令"时它显示为选中，实际什么都不执行**。
界面说生效、实际不生效，比没有反馈更坏。改成三态：未开 / `自定义 · 未填写`
（虚线警示色，明说现在不会生效）/ `自定义 · <命令原文>`。

第二个是纯反馈缺失：任务选项弹层一关就什么都看不见了。现在按钮带数字角标，
旁边列出已设条目的小标签。判据是"与默认值不同"，不是"碰过这个控件"——
点开看了一眼但留空，不算设置过。

## 可以带走的

1. **给出运维建议前，先想清楚它会删掉什么。** 这次的根因不是清理器有 bug，
   是我建议用户在一个有活跃引用（但还没落成 Run）的时刻去跑清理。
   工具的默认行为要能扛住"用户在任意时刻按下它"。
2. **"无引用"不等于"没人要"。** 生命周期里总有一段"已创建、尚未被引用"的窗口，
   而那常常正是用户最在意它的时候。回收策略要按**年龄**而不只是按引用计数。
3. **内存有、磁盘没有，是真实状态而不是不可能状态。** 凡是跨进程/跨时间的引用，
   在入口处判死，并给出下一步 —— 让原始 `ENOENT` 冒泡等于把排查成本转嫁给用户。
4. **固定的 NOW 配上真实的 mtime，测出来的是幻觉。** 只要断言依赖时间差，
   两端的时间来源就必须都可控。
5. **两态显示三态的东西，会主动骗人。** "开了但没填"和"已生效"长得一样，
   用户的每一次确认都在强化一个错误结论。
