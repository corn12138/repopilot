# 引入 AI 协议，先问它站在哪一边

产品想接"现在 AI 开发的那些协议"。第一个撞进脑子的是 MCP —— 生态最热、Anthropic 主推、
一堆工具都在往它上面挂。但真要说"接进来"，得先回答一个问题：**这个协议的核心断言，
是靠它自己说，还是靠我看得见？**

答完之后我没接 MCP，接的是 ACP —— 而且只接了一条翻译缝。

## 仓库里其实早有过一次协议裁决

翻 [08-21 那篇](2026-08-21-02-自述式协议接不进观察式判据.md)：当时评估 A2A
（Agent2Agent），逐条判下来结论是 `REJECT_AS_CROSS_REVIEW_TRANSPORT / DEFER_AS_REMOTE_REVIEWER_CHANNEL`。
理由一句话概括：**A2A 说"任务完成了"靠的是 `Task.status.state=COMPLETED` 这个自述字段，
而本仓判"改完了"靠的是退出码 + tree diff 这种观察得到的东西。** 自述式协议接不进观察式判据。

那 MCP 和 A2A 是一类吗？

- MCP 是**工具供给**协议：Agent 挂上 server 就多了一批工具。它撞的是本仓不变式 #5
  —— "所有副作用走同一个 Tool Gateway，先分级、留 ToolCall 记录、进同一本账"。
  任意 MCP server 会往执行门里灌没分级、没留痕的工具。所以 MCP 早在 AGENTS.md 的
  范围纪律里被列成"不在当前范围"，这不是保守，是它和唯一执行门直接冲突。
- ACP（Zed 的 **Agent Client Protocol**，别和 IBM 那个同名已归档的 ACP 搞混）就反过来了：
  它是**客户端驱动编码 Agent**的同步 JSON-RPC。Agent 要写文件得**回头求客户端**调
  `fs/write_text_file`，且客户端得先声明有这个能力；工具执行前要发 `session/request_permission`
  问人；一轮结束在 `session/prompt` 的响应里带 `stopReason`。

**这三条恰好和本仓三条不变式同向**：写权在人手里（宿主只读）、批准是人工边界（模型不能自宣成功）、
结束原因是判别联合（撞上限≠成功）。所以我采 ACP 的**线形**，拒 MCP 的**当下接入**。

## 最有意思的发现：我早就在说一种方言 ACP

打开 `codexAdapter.ts` 准备动手时愣了一下 —— 它已经在过 JSON-RPC over stdio 了，
只是用的是 Codex `app-server` 的私有词表：

```
thread/start   ←→ ACP 的 session/new
turn/start     ←→ ACP 的 session/prompt
turn/completed ←→ ACP 的 session/prompt 响应带 stopReason
turn/interrupt ←→ ACP 的 session/cancel
```

同族、不同名。也就是说本仓**缺的从来不是传输，是一个把外部 Agent 协议翻译进
内部 `AdapterEvent` 判别联合的翻译层** —— 和当年两个模型 wire 之间那个翻译层是同一件事。

## 这条缝我只让它做翻译

`acpWire.ts` 是一个纯函数式的入站翻译器：给它一条 ACP 通知/请求，它吐出零或多条
`AdapterEvent`，外加一份省略清单。它**不 spawn、不读写盘、不构造任何 JSON-RPC 响应**。
把协议里最诱人的三样东西按本仓纪律降级：

| ACP 里的语义 | 翻译层的处理 | 为什么 |
|---|---|---|
| `stopReason=end_turn` | → `finished/COMPLETED` | 只算"本轮结束"，投影不出 `SUCCEEDED` |
| `stopReason=max_tokens` | → `finished/FAILED` | 话没说完不是成功，和 exit code 一个待遇 |
| `session/request_permission` | → `waiting{APPROVAL}` | 只呈现"谁在等你批"，绝不代答 |
| `tool_call`（含 edit/diff） | → `activity`（不执行） | 副作用只走 Tool Gateway |
| `fs/write_text_file` / `terminal/*` | 计入省略 | 客户端**故意不 advertise 写能力** |

## 踩的坑：诚实版 vs 假装版只隔一个 default 分支

写 `mapAcpStopReason` 时，如果 default 分支图省事返回 `COMPLETED`，整套映射看起来"也能跑"，
测试大概率也能过 —— 因为它只在遇到未知 stopReason 时才露馅，而那恰好是最危险的时刻
（对端协议升级、加了新结束原因）。这和本仓 `stopReasonAllowsToolExecution` 里
"`OTHER` 绝不是默认成功"是同一条纪律，我在翻译层差点把它反着写出来。default 只能落 `UNKNOWN`。

另一个是 `agent_thought_chunk`。ACP 会把 Agent 的思考原文推给客户端。本仓立场是
不暴露 raw chain-of-thought，所以它只能翻成一条**固定标签**的活动，思考一个字都不能带出去。
测试里专门塞了个含"密钥 12345"的思考块，断言序列化后的事件里搜不到那串 —— 否则"不泄漏"只是注释里的愿望。

## 可复用的结论

- **接协议先问它靠什么"算完成"。** 靠自述字段的（A2A/MCP 的 tool 成功）和本仓观察式判据天然冲突；
  靠客户端手里有否决权的（ACP 的 permission/写回）才同向。这决定了是"接"还是"给自研套壳"。
- **采线形 ≠ 接语义。** 借它的方法名和消息结构省一个翻译层，但"成功/已写/已批"这些断言
  进本仓一律降级成"只呈现、不驱动终态"。
- **翻译层的 default 分支是诚实的照妖镜。** 未知输入折成成功，和把 `null` 用量当成 0，是同一类说谎。
- **别信缩写。** ACP 有两个，一个已并入 A2A 归档，一个是本文这个正主。查资料时混了就得出反结论。

裁决落在 `docs/contracts/acp-agent-client-protocol.md`（含 Revisit Trigger），
机器证据是 `acpWire.test.ts` 的一组负向断言。MCP 仍未开门，A2A 的远程通道仍是 DEFER ——
这一轮没有因为"生态热"就松动任何一条边界。
