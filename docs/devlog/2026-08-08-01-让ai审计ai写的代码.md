# 让 AI 审计 AI 写的代码：0 / 59 DONE

> 开发记录 · 2026-08-08 · RepoPilot

一天时间用 AI 写出 10000 行代码，跑通了完整闭环，44 个测试全绿。
那么问题来了：**这堆代码离需求文档到底还差多远？**

我不信自己的判断 —— 写的人和验的人是同一个，天然会往好里看。
所以我把 PRD 的 P0 需求逐条切开，扔给一组 agent 去比对代码，
然后**再派一组 agent 专门推翻第一组的结论**。

结果：**0 DONE / 46 PARTIAL / 10 MISSING / 3 DEFERRED。**

一条 DONE 都没有。

## 为什么要加"推翻"这一步

第一轮判定出来的时候，是有 DONE 的。

问题在于「符合需求」这件事，宽松地看和严格地看差别极大。一个 agent 读完
`PRD-RUN-004`（Worker 崩溃后可从校验通过的 Checkpoint 恢复），再看到代码里
有 `EventStore`、有 `events.jsonl`、注释还写着"Core 重启后从这里恢复时间线"
—— 判个 DONE 太自然了。

所以复核 agent 的指令是**反过来的**：

```
你的任务是**试图推翻这个判定**。去 PRD 里找到 XXX 的完整验收条件，
逐条对照代码检查。只要有任何一条验收未被满足，就判 upheld=false。

特别注意这几类常见的"判宽了"：
- 只实现了 happy path，异常/边界分支没有
- 有数据结构但没有真正消费它的代码
- UI 上展示了但后端没有对应约束（或反之）
- 验收要求"必须阻断"但代码只是记了个日志

不确定时倾向 upheld=false —— 漏报缺口比误报缺口危害大。
```

最后一句是关键。**审计的默认方向必须偏向严格**，否则它会自动退化成
"看起来做了就算做了"。

复核结果：**声称 DONE 的全部被推翻。**

## 编排长什么样

```js
phase('Analyze')
// 6 个分片，按 PRD 章节切，每个 agent 拿到精确行号范围 + 该看哪些源文件
const raw = await parallel(SLICES.map((s) => () => agent(prompt(s), { schema: FINDING_SCHEMA })))

// 只复核"声称已完成"的 —— 漏判缺口比误报缺口危害大
const claimedDone = all.filter((f) => f.status === 'DONE')

phase('Verify')
const verdicts = await parallel(claimedDone.map((f) => () =>
  agent(refutePrompt(f), { schema: VERDICT_SCHEMA, effort: 'high' })))

// 把复核结果合并回主表
for (const v of verdicts.filter(Boolean)) {
  const f = byId.get(v.requirementId)
  if (f && !v.upheld) {
    f.status = v.actualStatus
    f.gap = `${f.gap}；复核发现：${v.missingCondition}`
  }
}

phase('Synthesize')
const plan = await agent(rankPrompt(merged), { schema: PLAN_SCHEMA, effort: 'high' })
```

13 个 agent，25 分钟，152 万 token。

两个编排上的细节值得记：

**给精确的行号范围。** PRD 是 82k token 的中文文档，让每个 agent 都通读一遍
既慢又容易跑偏。切成"读第 345-356 行（7.3 Run、工具与恢复）"之后，
每个 agent 的注意力都落在自己那一片。

**声明"什么不算缺口"。** 原型明确不做 Docker 沙箱、不做加密、不做 Skill。
不说清楚的话，agent 会把这些全报成 MISSING，淹掉真正的问题。

```
**原型的明确非目标**（命中这些的需求判为 DEFERRED，不算缺口）：
- Docker/容器沙箱（当前用 utilityProcess + 受控子进程，残余风险已记录在案）
- 数据静态加密、保留期、级联清理、DLP
- Skill 导入、External Coding Agent/CrossReview、多交互表面（CLI/SDK）
```

## 结论里最扎心的两条

### 1. 写了不能读的日志

> `store.ts` 的注释和 README 都写着「Core 重启后从这里恢复时间线」，
> 但 `authority.ts` 构造函数只 rehydrate 了 `projects.json`，
> `new EventStore(runId)` 只在 `createTask` 里构造。
> **磁盘上的 events.jsonl 对已存在的 Run 永远不会被读回**，`run.get` 一律抛 NOT_FOUND。

这条同时命中六个需求（RUN-004 / EVID-001 / DESK-003 / DESK-004 / RUN-001 / PROJ-003），
是个共因缺陷。而且它的性质很糟：不是"少做了一个功能"，是**产品最核心的
「可审计」承诺在重启后为假**，而代码注释还在信誓旦旦地保证它。

### 2. 授权只在控制流上，不在平台上

> `dispatchTool` 查全局 `TOOLS_BY_NAME`，函数签名里没有 phase 参数。
> `PLANNING_TOOLS` 只被用来决定「给模型看哪些 schema」。

意思是：规划阶段的只读是**提示词约束**。模型只要凭记忆点名 `workspace_mutate`
（它在训练数据里见过无数次类似的工具名），就能在"只读阶段"真的改文件。

我写这段代码的时候，注释里写着「规划阶段由平台 capability envelope 强制 read-only，
不能只依赖 Prompt 自律」。**注释是对的，代码没做到。**

## 一个必须承认的失败

6 个分析分片里，`§6 异常路径 + §8 视图状态矩阵` 那个 agent 挂了：

```
[gap:§6 异常路径 + §8 视图状态矩阵] failed: API Error: Connection closed mid-response.
```

所以视图状态那一片的缺口，到现在仍然是**未知数**。

这条要写出来。一个审计报告如果不说清"哪里没审到"，读的人会默认它审全了 ——
那就是另一种形式的假绿，而这正是整个项目在反对的东西。

## 关于"AI 审计 AI"这件事本身

有人会问：让 AI 去审 AI 写的代码，不是左手打右手吗？

我的观察是**分开的角色确实能产生独立信号**，前提是给它们不同的立场：

- 写代码的 agent 立场是"让它跑起来"
- 分析的 agent 立场是"逐条对照验收条件"
- 复核的 agent 立场是"**试图推翻**上一个结论"

第三个立场是最有价值的，也是最容易被省略的。省掉它，你得到的是一份
互相点头的报告。

但它也有明确的边界：这次审计**没有**发现任何 UI 层的问题（那个分片挂了），
也**没有**发现性能问题（没人跑过压测）。它只在"代码 vs 文档"这一个维度上有效。

## 可以带走的

1. **审计的默认方向必须偏严。** "不确定时倾向推翻"这一句能改变整份报告的质量。
2. **单独派人推翻结论。** 让同一个 agent 既判定又复核，等于没复核。
3. **切片要给精确行号，并声明什么不算缺口。** 否则注意力发散、噪音淹没信号。
4. **注释和代码不一致，是最危险的一类缺陷。** 它让读代码的人（和写测试的人）
   相信一件不成立的事。
5. **报告必须说清哪里没审到。** 沉默会被读成"这里没问题"。
