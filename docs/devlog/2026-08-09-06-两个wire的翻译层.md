# 两个 wire 的翻译层，以及它可以怎么骗你

> 开发记录 · 2026-08-09 · RepoPilot

同一个 Agent Loop 要能同时对着 Anthropic 和一堆 OpenAI 兼容端点跑。
中间那层翻译只有两个文件、加起来三百来行，看着很平淡。

它在今天之前**一行测试都没有**。而今天补的 30 条里，有一大半是在验证
「这层翻译不许自作主张」。

## 为什么单独给它补测试

`core/model/` 下原本只有 `registry.test.ts`（45 条，测的是"用户填的地址怎么变成
真正会被 fetch 的 URL"）。`gateway.ts` 和两个适配器完全没覆盖 ——
上一轮那个写测试的 agent 连接中断挂在了这里。

问题是这层的失败模式特别隐蔽：**它不会崩，它会给你一个看起来合理的错东西。**
翻译丢了一个块、把 null 变成 0、把畸形 JSON 兜底成 `{}` —— 这些都不抛异常，
只是让上层拿到一个稍微不对的世界。

## 翻译方向：1:1 和 1:N

Anthropic 的形状和我们的中立 `ContentBlock` 几乎同构，逐块映射就行。
OpenAI 那边不是 —— 它按 **role** 分消息，而我们按 **块类型** 分：

```ts
// user 侧：tool_result 必须变成独立的 role:'tool' 消息，且要排在文本之前
for (const r of toolResults) {
  out.push({ role: 'tool', tool_call_id: r.toolUseId, content: r.content });
}
if (texts.length) {
  out.push({ role: 'user', content: texts.map((t) => t.text).join('\n') });
}
```

一条我们的 user 消息，在 OpenAI 侧可能变成 N 条。顺序还不能反 ——
`role:'tool'` 必须紧跟在产生它的 `assistant(tool_calls)` 之后。

有条测试专门盯这个：

```
tool_result 变成独立的 role:tool 消息，且排在同条 user 文本之前
```

写的时候只觉得是个格式细节。**第二天它成了另一个 bug 的关键解释** ——
我在补 `tool_result` 时造出了两条连续 user 消息，Anthropic 直接 400，
而 OpenAI 侧因为这层拆分看到的是合法的 `assistant → tool → user`，一点事没有。
（那个故事见 [我修的那个 bug，制造了另一个 bug](2026-08-10-01-我修的bug制造了另一个bug.md)。）

## 不许自作主张之一：usage 缺不到就是 null

```
usage 缺失时 token 记 null，绝不记 0
```

这条在两个适配器里各写了一遍。理由是：**0 和"不知道"是完全不同的两件事。**

provider 不返回 usage 的情况很常见（尤其中转站）。记成 0 的话，界面上显示
"本次用了 0 token"，而钱是真花了的；更糟的是预算闸门
`inputTokens + outputTokens >= maxTotalTokens` 会永远为 false，那道硬上限整条失效。

所以 `ModelResponse.inputTokens` 的类型是 `number | null`，一路保到
`ModelEgressManifest`。

诚实地说：**这条链目前只保到 manifest 为止**。`agent.ts` 里 `chargeModelTurn` 那行
还是 `manifest.inputTokens ?? 0`，"未知"在账本类型里没有位置，所以最后一步又被抹平了。
适配器这层做对了，账本那层还没改 —— 那是 Track B 的活，README 的「还没做的」里
列着「账本诚实性」。

## 不许自作主张之二：畸形输入不兜底

模型偶尔会吐出解析不了的 tool call 参数。最省事的写法是 `try { JSON.parse } catch { return {} }`。

那样上层看到的是"模型调了 `fs_read`，参数是空对象" —— 一个合法但错误的世界。

```ts
it('畸形 arguments 不 fallback 成 {}，而是原样上报 __malformed_arguments__', async () => {
  stubFetchJson({
    choices: [{
      message: {
        content: null,
        tool_calls: [{ id: 'c1', function: { name: 'fs_read', arguments: '{path: a.ts' } }],
      },
      finish_reason: 'tool_calls',
    }],
  });
  const r = await openAiWireAdapter.call(req, ctx());
  const toolUse = r.content.find((b) => b.type === 'tool_use')!;
  expect(toolUse).toMatchObject({
    type: 'tool_use',
    input: { __malformed_arguments__: '{path: a.ts' },
  });
});
```

原样带出去，让 zod schema 去拒绝它，模型收到一条能读懂的报错然后改正。
比悄悄换成 `{}` 强得多。

同一个思路还有一条：

```
残缺 tool_use（缺 id/name）被丢弃，不产生半个块
```

丢弃是对的 —— 但**不能产生半个块**。一个 `id` 是 `undefined` 的 tool_use 混进
conversation，下一轮就是孤儿，两家 wire 都会 400（这也是昨天那个 bug 的近亲）。

## 不许自作主张之三：finish_reason 不是权威

```
有 tool_call 时即使 finish_reason=stop 也判 TOOL_USE
```

OpenAI 兼容端点在这件事上很不一致，有些中转站会在带 `tool_calls` 的响应里
返回 `finish_reason: 'stop'`。信了它，Agent Loop 就以为模型说完了，
直接进入收尾 —— 而模型其实在等工具结果。

判据改成看**内容里有没有 tool_call**，而不是看厂商给的标签。

## 凭据不许进错误信息

两条测试，一半一半：

```ts
it('错误信息里绝不带 apiKey —— 即使 provider 把它回显进错误体', async () => {
  // 构造一个恶意/粗心的 provider：把整段请求（含 key）回显进错误体
  stubFetchJson({ error: { message: 'invalid key sk-secret-KEY-do-not-leak in header' } }, 400);
  // fetchJson 会把 provider 的错误摘要带出来 —— 这里断言的是：我们自己**不**主动
  // 拼接 apiKey。provider 回显自己那部分不受我们控制，但适配器的 header 里的 key
  // 不会出现在 error 中（下面的 anthropic 用例覆盖"我们不泄漏"这一半）。
  …
});

it('适配器抛错时不把 apiKey 带进错误信息', async () => { … });
```

第一条那段注释我改了三遍。因为一开始我想断言的是"错误信息里不含 key"，
但那**做不到** —— provider 把 key 回显进错误体是它的行为，我们没法阻止。
能保证的只有"我们自己不主动拼进去"。

把做不到的事写成断言，就是造一个会骗人的绿灯。所以最后拆成两条，
并且在注释里说清楚哪一半不在我们控制范围内。

## HTTP 错误分类

`fetchJson` 那一层把网络世界的混乱收敛成 `ModelCallError.kind`：

```
ok 但响应体不是 JSON → PARSE
fetch 抛 AbortError → CANCELLED
fetch 抛普通错误 → NETWORK
body 里带 error 字段 → BAD_REQUEST
没有 choices → PARSE
```

分类的意义在于上层能做不同的事：`CANCELLED` 不该记成失败、`NETWORK` 值得重试、
`BAD_REQUEST` 是我们自己拼错了请求（比如那条孤儿 `tool_use`）。全都糊成
"调用失败"的话，`MALFORMED_CONVERSATION` 那种自己造的错就永远查不出来。

## 还没做的

**没有一条测试真的联网。** 全部用 stub 掉的 `fetch`。所以这 30 条能证明
"我们的翻译逻辑符合我们对协议的理解"，不能证明"我们对协议的理解是对的"。

这个区别昨天刚被上了一课：`findOrphanToolUse` 完美地实现了我对 Anthropic 的
（不完整的）理解。**至少要有一条能打真实端点的冒烟测试**，哪怕只在本地手动跑 ——
这条还欠着。

**流式没有实现，也就没得测。** 仓库里根本没有 SSE 路径，PRD-MODEL-004 要求的
`ModelStreamAttempt` / `partialDisposition` / `usageSettlement` 整套是个更大的结构性缺口。

## 可以带走的

1. **翻译层的失败模式是"给你一个合理的错东西"，不是崩溃。** 所以它的测试要
   全押在"有没有自作主张"上。
2. **`0` 和"不知道"是两回事。** 让类型带上 `| null`，并且顺着这条链一路检查
   哪里被 `?? 0` 抹平了 —— 我这条链目前还断在账本那一层。
3. **畸形输入原样上报，别兜底。** 兜底出来的合法值会让上层做出错误决策；
   带着 `__malformed_arguments__` 抛给 schema，模型能收到能读懂的报错。
4. **别信厂商给的语义标签。** `finish_reason` 不一致，看内容更可靠。
5. **把做不到的事写成断言，就是造一个会骗人的绿灯。** 拆成"我们能保证的"和
   "不在我们控制范围内的"，并在注释里说清楚。
6. **stub 掉的协议测试证明的是"符合我的理解"，不是"符合协议"。** 这两者的差距
   需要一条真实冒烟测试来补。
