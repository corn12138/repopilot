# 审核契约和补丁交付必须可验证

审核提示词要求模型调用 `submit_review`，实际 HTTP 请求却没有声明它。
锁文件修改通过了 receipt 和 mutation，封存出的补丁却没有这个文件。
这两种问题都能藏在全绿测试背后：替身补出了协议能力，分类断言没有检查最终交付。

## 审核工具必须真的发给模型

审核阶段现在只声明四个 R0 文件读取工具与 `submit_review`。提交定义包含 verdict、findings、
可选的 resolvedFindingFingerprints，并约束严重度、置信度、证据和行号。提交仍由 Core 在审核
提取边界校验，不能通过通用工具分发接受，也不能凭 PASS 决定任务成功。

测试分别经过 Anthropic 和 OpenAI 的真实序列化与 SSE 解析，检查实际请求体，再返回正常、
畸形、截断和未知停止原因的响应。畸形结论必须要求重提；未完成响应的工具必须回填“未执行”。
另有 Authority → Gateway → OpenAI adapter 的完整离线请求链路，避免仅测工具对象本身。

这组对照还暴露了 OpenAI 的一个边界：内容里有完整 tool call，不等于响应的结束原因可靠。
当前仅对已知 `stop` 做工具内容兼容推断；`length` 保留 MAX_TOKENS，未知或缺失原因保留 OTHER。
两者均不能派发工具或提交审核结论，已解析的调用仍保留供回填。

## 折叠展示与交付排除分开判断

9/18 的分类扩展把锁文件和生成形状源码移出了补丁。列入排除清单虽然披露了省略，仍然不能
证明省略正确。展示层可以折叠噪声，交付层必须保留任务真正修改的文件。

工作区现在保留最初导入的路径集合，并按 generation 记录成功 mutation 的文件来源。只有
未导入、未显式 mutation 的约定输出目录文件才可排除；文件名像锁文件、压缩文件或生成代码，
本身不再是交付排除依据。导入层的既有排除政策未改变，“已导入”指实际进入快照的文件。
来源键规范为实际相对路径，`./dist/x.ts` 不会和 `dist/x.ts` 分家。

三个边界决定这份来源记录是否可信：

- 导入集合在基线构建前取得，不能把 gen-0 后来生成的输出误当原有源码。
- 来源随成功 CAS 提交；失败事务与失败 CAS 既不改变当前文件，也不登记来源。
- 恢复历史 generation 时同时恢复来源，已回滚的编辑不能让未来构建产物进入交付。

外部候选归一化与文件树沿用同一交付判据。候选删除仍整笔拒绝；新增的约定输出目录内容
没有已知来源时仍排除并报数，未增加 delete mutation 或放宽保护路径。

## 用最终字节验收

修复前的 7 个专项断言失败，覆盖审核工具缺失与补丁遗漏；两协议对照另外抓到未知结束原因
被提升为可执行的失败。修复后覆盖锁文件单改、源码与锁文件一起改、嵌套锁文件、生成源码、
显式输出目录编辑、构建输出删除报数、失败零写入、CAS 与回滚来源。补丁测试使用临时 Git
仓库，确认显式应用前宿主不变，`git apply` 后字节与工作区一致。

验证结果见下方最终记录。测试使用隔离数据根，协议响应来自本地替身；没有真实模型请求。

本批只关闭代码复审的 R01/R02 及相邻完整性问题。审核级计数、未结算恢复、整改即时计数、
迟到快照、启动中断、任务工作台旅程仍待后续批次；Stage 0 与真实双模型验收没有因此通过。

可复用的检查方法是：验证实际发送的请求，以及最终交付的字节。仅有提示词、内存对象或
分类函数的正确断言，不能证明协议和交付两端已经接通。
