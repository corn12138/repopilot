# 我加的二次确认，自己成了新的危险

> 开发记录 · 2026-08-13 · RepoPilot

设置页里有三个危险动作：删 API Key、删自定义 Provider、立即清理。
它们**一个确认都没有**——点一下就发请求，其中两个不可撤销，一个真的 `rmSync`
用户的 Run 证据。整个 Renderer 里只有一处二次确认，在补丁那边
（「应用到仓库…」→「确认写入仓库」），设置页一处都没抄过去。

这轮补上。做完之后我让四个独立视角对着自己的改动做对抗复审 ——
**15 条候选，7 条成立，其中两条 high 是我这一轮刚写进去的。**
这篇就写那两条，因为它们比功能本身更值得留档。

## 一、横幅说"已阻止执行"，底下的按钮是活的

先看组件的守卫：

```tsx
consequence: ReactNode | null;
...
<button
  className="danger"
  // 后果还没算出来就不许确认：那等于让用户在不知道结果的情况下按下去。
  disabled={busy || consequence === null}
>
```

注释是对的，逻辑看起来也对。再看调用点：

```tsx
consequence={
  previewFailed !== null ? (
    <strong>无法预演这次清理：{previewFailed} —— 已阻止在不知道后果的情况下执行。</strong>
  ) : preview === null ? null : (
    <SweepPreview summary={preview} />
  )
}
```

预演失败时，我传进去的是一个**非空的 React 元素**。
`consequence === null` 为假，守卫不触发，确认按钮**可点**。

也就是说：横幅上明明白白写着「已阻止在不知道后果的情况下执行」，
而它正下方那个会真的 `rmSync` 的按钮是活的。
复审用一个临时 jsdom 测试实测确认了这一点。

触发条件不刁钻：`retention.preview` 一旦被拒（Core 重启后的代次不匹配、
或者慢方法超时），就进这条路。

**根因不是我忘了写守卫，是我用错了类型。** `ReactNode | null` 只能表达
"有没有内容"，而我需要表达的是"能不能确认"——那是三种状态：

```tsx
export type ActionConsequence =
  | { readonly kind: 'pending' }                         // 还不知道后果
  | { readonly kind: 'ready'; readonly detail: ReactNode }   // 知道，可以确认
  | { readonly kind: 'blocked'; readonly reason: ReactNode }; // 知道自己算不出来
```

只有 `ready` 才**渲染**确认按钮——不是"渲染但禁用"。
`blocked` 状态下那个按钮根本不存在，只留一个「关闭」。

这条不变式在这个项目里其实早就有名字：**命令结果是判别联合，不是布尔**。
我在 Core 那边守了一年多，到了 Renderer 就把它写成了 `T | null`。

## 二、后果算完了，前提却变了

第二条 high：

> 保存新的保留策略时，已展开的确认不会失效。横幅还挂着旧策略算出的
> 「按当前策略，这次清理不会删除任何东西」，而确认键按下去执行的是新策略的清理。

复审同样跑了一遍复现：把保留期从 30 天改成 1 天并保存，横幅上那句
"不会删除任何东西"原地不动，确认按钮可点。

`armed` 是组件内部的 `useState`，而 `ConfirmAction` 在 `Card` 的 `right` 槽位上
位置固定，React 会跨重渲染保留它。加一个"依据的身份"：

```tsx
armKey={policy ? `${policy.evidenceDays}:${policy.workspaceGraceMinutes}` : 'no-policy'}
```

```tsx
// 依据变了就退回第一段，强制重新取一次后果。
useEffect(() => { setArmed(false); }, [armKey]);
```

两条 high 修完之后，它们从"记得写对守卫"变成了"结构上写不错"：
一个由判别联合保证，一个由 `armKey` 保证。

## 三、我自己读代码抓到的两条

等复审结果的时候我自己也在读。抓到两条，都是这一轮引入的。

**预演会覆盖上一次真实清理的记录。** `sweep()` 结尾无条件写 `last-purge.json`。
我给它加了 `dryRun` 却没管这里 —— 于是"预览一下会删什么"会把上一次真删的
记录覆盖成一份什么都没做的预演。既是预演的副作用，也销毁了真实证据。
一个号称无副作用的操作，唯一能被信任的方式就是它真的没有副作用。

**删内置 provider 会删掉你真实的 API Key。** 这条最险。原来：

```ts
export function removeCustomProvider(id: string): void {
  writeJsonAtomic(CUSTOM_PATH, loadCustomProviders().filter((c) => c.id !== id));
}
```

传 `'anthropic'` 会返回成功，实际什么也没删（它不在自定义表里）。
在此之前这是无害的——直到我这轮加了"删 provider 顺带删掉它的凭据"：

```ts
const res = await callCore('model.removeProvider', payload);
if (!res.ok) return res;
credentials.removeKey(providerId);      // ← Core 说成功了，那就删凭据
```

一次 `{providerId:'anthropic'}` 请求 → Core 静默返回成功 → Main 删掉用户
**真实的 Anthropic API Key**，而那个 provider 还好端端在列表里。

这是"静默通过"在删除路径上直接变成数据丢失的实例。给内置 provider 加了硬拒绝
（对不存在的 id 保持幂等——那条契约有测试钉着，是对的）。

## 四、复审的探针抓到的一条

复审过程中有个 agent 往我的源码树里写了个探针测试文件。文件本身要删掉，
但它构造的场景是对的：一个终态过期的 Run，加一个**只被它引用**的快照。
把那个场景收进正式测试后，退掉修复重跑，它红成这样：

```
× 预演算得出级联删除的快照，不会少报
  → expected 'KEPT_REFERENCED' to be 'WOULD_DELETE'
```

**预演少报了一项。** 删掉 Run 证据会让"只被它引用的快照"在同一轮里失去
最后一个引用者，第 3 步据此回收它。但那个扣减靠的是：

```ts
if (r.outcome === 'DELETED') purgedRuns.add(runId);
```

预演里那条是 `WOULD_DELETE`，进不了 `purgedRuns`，于是级联那一级算不出来。
预览说删 3 项，真跑删 4 项。

我自己的等价性测试没抓到，因为我造的数据里没有"只被待删 Run 引用的快照"这种组合。
探针精确地构造了它。

一个会**少报**的预览比没有预览更糟：用户是照着它按下确认的。

## 顺带说说预演本身

预演这个功能其实几乎是免费的。在此之前，想知道「立即清理」会删掉什么，
唯一的办法是**真的删一次**。而删除函数本来就长这样：

```ts
function remove(domain, target, path, reason) {
  const bytes = dirSize(path);          // ← 删之前已经量过体积了
  rmSync(path, { recursive: true, force: true });
  ...
}
```

体积已经算好了，每个分支本来就产出一条 `PurgeItemResult`。
加一个 `dryRun` 跳过 `rmSync` 就完事——判定路径完全相同，所以它给出的不是估算。

条目用独立取值 `WOULD_DELETE`、summary 带 `dryRun` 字段，
让"预演结果"在类型层面就不可能被下游当成"已经删完了"。

## 可以带走的

1. **给危险动作加确认，本身就是一个危险动作。** 它跑在用户与不可撤销操作之间，
   写错了不是"少了个提示"，是"提示说被拦住了，其实没拦"。
2. **`T | null` 表达不了"我知道自己算不出来"。** 三态就用三态。
   `pending` / `ready` / `blocked` 里，只有 `ready` 该有确认按钮 ——
   而且是**不渲染**，不是渲染成禁用。
3. **确认展开之后，依据可能会变。** 两段式确认必须绑定"依据的身份"，
   否则它会稳定地展示一段过期的后果，然后执行另一件事。
4. **静默成功在删除路径上会变成数据丢失。** `removeCustomProvider` 对内置 id
   返回成功本来无害，是我加的"顺带清理附属物"把它变成了删 key。
   改动的危险性来自它与既有静默行为的**组合**，不是它自己。
5. **少报的预览比没有预览更糟。** 它同样会被当成承诺，而且是用户按下确认的依据。
6. **让别人来审自己刚写的东西，而且要求默认驳回。** 15 条里 7 条成立、8 条被驳回；
   两条 high 我自己完全没看出来——我看的是"我想让它做什么"，
   复审看的是"它实际会做什么"。
