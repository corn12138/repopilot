# 把「谁在等你答话」做成一等状态

双工位能新建受管会话、能收发、能中断之后，用户还是得盯着每一栏猜：它是在跑、是跑完了、
还是卡在一个批准框前等我？`WorkbenchSessionStatus` 回答的是连接生命周期（READY/RUNNING/
DISCONNECTED），不是 agent 的注意力状态。设计文档 §5.1 自己就点了这个缺口——事件要能区分
「等待批准/输入」——但协议 v3 里既没有这个事件，也没有这个状态。

herdr 的招牌正是把 working/blocked/idle/done 做成一等属性、从 pane 汇到 workspace。这次照着补：
新增一条**独立于连接态**的 `WorkbenchAgentState`（IDLE/WORKING/BLOCKED_APPROVAL/BLOCKED_INPUT/
DONE/DISCONNECTED/ERROR），由 Main 从结构化引擎事件派生、随 `session.updated` 下发；加 `turn.waiting`
事件；加只读的跨项目 `workbench.summary`（herdr 侧栏的「哪个项目需要你处理」）；并把 UI 从
「每 vendor 只留一个会话」的硬编码双槽，放开成按 handle 渲染的 N 个 pane。

关键在于**blocked 感知被刻意隔离卡住，我没有伪造它**。Codex 受管会话固定 `approvalPolicy=never`
+ `sandbox=read-only`，app-server 因此根本不会发审批请求——Codex 永远不出现 BLOCKED_APPROVAL，
一条负向断言钉住这条隔离没被偷偷放宽。Claude 是 conversation-only（`tools=[]`），我把 SDK 权限/
控制请求映射成 `waiting/APPROVAL` 的分支接好了、也用确定性替身测了映射本身，但当前配置下真实
引擎不会触发它；真正「从 RepoPilot 代答批准」是控制动作，属另一个信任域决定，这轮不做。

其余红线照旧：状态只来自结构化引擎事件，不读屏、不 GUI 自动化；blocked 只呈现「谁在等」，
应答发生在会话自己的工具里，SDK 回调绝不绕过 Core 放行；人工交接与 authority/验证/2 审 1 改
一律没动——这不是 agent→agent 编排（那要先翻 ADR 010）。跨项目汇总只回计数、不回内容，
项目隔离不破。

证据：`workbenchService` 16 条（状态派生矩阵、blocked 期间拒发新轮、summary 计数、多会话独立），
两家 adapter 各 5 条（Claude 权限请求→waiting、Codex never-approve 不产出 blocked），
`Workbench.test.tsx` 9 条（jsdom 真实 DOM：N pane、状态徽标、汇总、turn.waiting 不代答、
外项目拒绝）。真实引擎下的 blocked 产出仍未验收——那要等 Claude 以可产出权限请求的模式跑起来。
