# 分叉能借，工作现场不能续用

> 开发记录 · 2026-08-19 · RepoPilot

用户丢给我一个链接：`tabtin.com`，说"借点灵感，改改我们的 PRD 和 TD"。
TabTin 的第一句话是"你、搭子、Agent 在同一工作区里碰头"；我们 PRD 的第四条产品决策是
**Single Local Operator**，第五条是**只交付 Patch、不写回宿主仓库**。前提相反的两个产品，到底能借什么？

这篇只写这一轮的两个决定：**怎么借**（先分四类，再动笔），以及借得最深的那一样 —— **分叉**——
它在 TD 里撞上了一条我差点忘了的不变式。

## 一、先分类，再动笔

TabTin 的公开页有 12 个卖点区块。我没有下载、没有登录、没有运行它，只抓了页面文字
（2026-08-18 23:13，2955 字符，原文和 sha256 存进 `docs/evidence/raw/alt-sources/`）。
所有"它能不能做到"一律标 `Unknown`——这不是竞品研究，是灵感来源，两者不能混。

然后逐条过一遍，只允许四种去向：

| 去向 | 例子 | 落点 |
|---|---|---|
| **Adopt**（只借叙事和原则，不新增对象） | "不用再解释一遍做到哪了"；"Agent 调的和你脚本里调的是同一套 API" | PRD §1 一段用户视角的话；§4.2 两条原则：**对等可见**、**同一 Gateway、同一账本** |
| **Adapt**（改成单人、本地、受治理版本，进 P1/Deferred） | 分叉、"谁烧得多一翻就知道"、Issue 进 Project、"第一件活今天就试" | `PRD-FORK-001` / `PRD-LEDGER-001` / `PRD-INTAKE-001` / `PRD-ONBOARD-001` |
| **Defer**（只登记问题） | 分层记忆"自己浮上来"、后台定时跑 | Q-020 / Q-021 |
| **Reject → 负向测试** | "登录状态也共用一份"、Webhook 回写、手机审批 | `THR-SHARED-SESSION-001` 等 5 条威胁 + ASM-023 |

最后一行是这轮最意外的收获：**前提相反的产品，最值钱的不是它有什么，而是它把我们的不变式
反着说了一遍**。"登录状态也共用一份"直接就是一条负向测试的标题：Sandbox/Connector/Skill 里
尝试读 `~/Library/Cookies`、Keychain、`SSH_AUTH_SOCK`，预期 typed deny。这种素材自己坐着想不出来。

`同一 Gateway、同一账本` 也不是凭空写的。08-17 那轮审计有一条 high：用户在 TaskForm 手填的命令
风险等级硬编码 `'R1'`，`runVerification` 直接调 `runCommand` 绕过 `dispatchTool`——
"用户命令免审、验证命令免记账"就是这条原则缺席的样子。TabTin 那句"Agent 调的和你脚本调的是同一套"
只是给了它一个名字。

## 二、分叉：借的是"主线不动"，撞上的是"新 Attempt 不能续用旧工作区"

TabTin 的原话：

> 从搭子 Agent 会话任意节点开新线，试方向不影响主线。

我们有 Checkpoint、有 Attempt、有 lineage，PRD/TD 里却**一个 fork 都没有**（grep 过，`分叉`/`fork`/`branch` 零命中）。
用户中途想换方向，现在只有一条路：取消，重新建 Task。所以这条值得借。

第一稿我写的是"从 Checkpoint 派生新 Attempt，继续用那时的工作区"。写到 TD 时翻到 §11.1 的一条规范：

> PatchAcceptance decision=`REQUEST_CHANGES` 时……新 Attempt 重新 plan/approve，**不能续用旧 workspace/lease**。

TabTin 那种"从任意节点开新线"隐含的是**同一份活着的工作现场**继续用；而我们的 Attempt 是
lease/预算/工作区三绑定的执行实例，工作区终态即销毁或 quarantine，lease 有 fencing。
让分叉去续用父 Attempt 的工作区，等于给"同一时刻只有一个 writer"开一个后门。

所以分叉的种子不能是工作区，只能是**摘要**：

```text
AttemptForkSeed {
  snapshotDigest,                 # 同一份只读快照
  generationTreeDigest@checkpoint,# 那个时刻已提交的 workspace generation 的内容寻址树
  conversationHighWatermark,      # 对话读到哪
  contextSelectionRefs[],
  checkpointFactsDigest,
  authorization_state = NONE      # 不带任何批准、consent、lease、终态
}
```

新 Attempt 拿着这个 seed 走完整个活动态：自己 provision 新 workspace/lease，
从 `generationTreeDigest` 重建 active generation，从 watermark 之前的持久消息重新物化上下文，
然后 `WAITING_DATA_CONSENT → PLANNING → WAITING_APPROVAL`——consent 要重新确认，Plan 要重新批。
父 Attempt 必须已经终态，或者被用户显式 supersede 成 `BLOCKED`（事实全部保留）；父还在 ACTIVE 就分叉，
一律 `FORK_REJECTED`。预算从 Task 聚合池扣，父的用量不回减。

这么定之后有个副产品：**状态图一笔没动**。分叉只是"创建新 Attempt"的第三种来源
（前两种是 retry 和 REQUEST_CHANGES），Approval 矩阵也不用加行——它压根不是 Approval，
是和 REQUEST_CHANGES 同类的用户手势。TD §12.19 整段流程写下来，没有一个新状态、一个新审批面。

对应的负向测试也是现成的：ACTIVE 父分叉、被 purge 的 checkpoint、seed 里夹带 lease/path/approval、
双 ACTIVE 竞争、预算回减、lineage 缺失——`THR-FORK-INHERIT-001` / `TEST-FORK-001`。

## 三、账本：把"谁烧得多"改成"哪一步烧得多"

TabTin：组织一个 Credits 池，按搭子记账，"谁烧得多，一翻就知道"。
我们没有组织、没有 Credits、也永远不做共享额度（PRD §5.4 明确非目标）。但"一翻就知道"这个体验是对的——
我们已经有三层 budget ledger 和每次出站的 `ModelEgressManifest`，却没有一个视图能回答
"这个 Run 的 token 都烧在 planning、execution 还是 compaction 上"。

所以 `PRD-LEDGER-001` 是一个**纯投影**：按 Project/Task/Attempt/Run/`ModelInvocationPurpose`/route 汇总，
数据只来自 ledger 和 manifest，不发一次新请求。唯一需要较真的规则是：
stream 中断、Provider 没回报 usage、pricing 未知的条目，**显示 `UNKNOWN`，不许是 0**，并且单列一个"未结算"计数。
这条也进了威胁矩阵（`THR-LEDGER-ZERO-001`）——一个把未知写成零的账本，比没有账本更糟。

## 四、踩了什么坑

**1. 叙事段落偷偷提前承诺。**
我给 PRD §1 加了一段"对用户说的话"，第一稿里有一句"中途想换方向可以从任意 Checkpoint 分叉，主线不动"——
写得像现在就有。分叉是 P1。回读时才发现，改成括号标注"（P1 合同，见 §7.14）"。
"文档写完不等于验证过"这条规矩，对叙事段落同样成立：**一段好读的话最容易把优先级抹平**。

**2. 想改 `PRD-CONV-006`，读完发现不用改。**
TabTin 的"交接"（光标停在哪、开着哪些标签、Agent 记了什么，一起传过去）让我打算给 Continuation
补一份"携带/不携带清单"。评审文档里都写上"§7.8 验收补充"了。真去读那条需求：携带项七种、不携带项九种、
`authorization_state=NONE`，比 TabTin 那句话严格得多。撤回。样本给的往往只是一个**名字**，
不一定给新内容；先读再改，不然就是为了对齐样本而制造噪音。

**3. 83 不是 §7 的数。**
我一直以为 §7 有 83 条需求，让 agent 逐条列出来才知道是 §7 的 72 条 + §10 的 11 条 NFR。
新增 4 条之后要同步 7 处（§7 表、§15.1 AC、§15.2 逐条追溯、尾句计数、§15.3 分组、§8 视图矩阵、修订记录），
TD 那边再同步 §13/§21/§23。这种事肉眼必错，所以最后是脚本说话：

```text
PASS: requirement defs=87 prd_trace=87 td_trace=87 expected=87
PASS: threats td=64/64 model=64/64 matrix=64/64 expected=64
PASS: matrix rows 14-col + applicability vocab issues=[]
```

顺带一个诚实问题：仓库里已有的 `verify-stage0.py` 钉着 r9 的冻结 hash 和 `len==83`/`59`，
对 r10 文件**必然失败**。改脚本里的旧 hash 最省事，但 evidence-index 明写"历史 hash 不删除、不偷换"。
所以另写了 `verify-r10-trace.py`（同一套规则、只换期望值），记成 RUN-016/017，状态 `COLLECTED` 而不是 `VERIFIED`——
它不在冻结包里。老脚本继续红着，红得有理由。

**4. 威胁矩阵是有机器字段的。**
把 5 条新威胁落到 `security/threat-control-test-matrix.md` 时才发现每行 14 列，最后四列是
`scopeClass / requiredForGate / featureState / applicabilityPredicate`，且 `P1_` 前缀的行 `requiredForGate`
必须含 `"G0:DISABLED"`、`featureState` 必须是 `P1_DEFERRED_DISABLED`——这些规则就写在验证脚本里。
新加的 fork/intake 也没有新增 `PlatformCapability` 枚举（C1..C10 是封闭的）：只读拉取复用 C2 的 CredentialLease 行，
分叉不是 Approval。**能不加新枚举就不加**，加了就要动 schema catalog。

**5. 日期跨了零点。**
采集是 08-18 23:13，改稿改到 08-19 凌晨，第一稿所有"修订日期"都写成 08-18。后来统一成"采集日 08-18 / 修订日 08-19"。
小事，但证据文件上的日期是要被复核的。

## 五、可复用的结论

- **前提相反的产品也能借**，但先分四类：叙事和原则可以直接借；机制要改成自己的前提；冲突的写成负向测试——
  后一类往往最值钱，因为它替你把不变式反着说了一遍。
- **借机制之前先找自己的不变式。** 分叉能借，工作现场不能续用；种子只能是内容寻址的摘要 +
  `authorization_state=NONE`，新 Attempt 自己 provision。做对了状态图不用动。
- **账本可以只是投影，但 `UNKNOWN` 永远不能显示成 0。**
- **叙事段落也要标优先级**，它比需求表更容易把 P1 写成现在时。
- **计数交给脚本，历史 hash 不偷换**：老校验红着，是因为它守的是历史；新校验绿着，只声明它检查的那个窄事实。

本轮改动全部是文档：PRD 1092 行、TD 2424 行、评审文档 207 行；需求 83 → 87、威胁 59 → 64，
新增全部 P1/Deferred，P0 一个字没动，Gate 仍是 `Not Ready`。`prototype/` 没碰。
