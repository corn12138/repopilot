# 交接点由 Core 决定

双工位的协作流程已细化为下一轮开发任务：一方计划与评审，另一方实施与修正，平台独立验证，用户确认计划并最终验收。计划、改动、验证和评审之间，每次交接都要说明当前工件、接收方、范围和剩余额度。

本轮是规划交付，没有修改产品运行代码，也没有启动真实模型任务。

## 手动与自动共用同一条链

默认逐步交接：计划批准后实施，平台验证自动执行，下一次模型阶段开始前等待用户决定。构建自修复、首审、审核整改和复审都属于这样的交接点。

有界自动模式在计划确认时批准范围内的推进，正常阶段不重复确认。Core 仍在每次派发前检查角色、出站同意、工件新鲜度和预算。最多两次评审、一次审核整改；构建自修复另按 Task 预算报数，不能藏在整改次数里。

两种模式使用同一套 Core 门禁和工件消费规则。Renderer 只展示当前允许的动作；观察 watcher 不增加自动转发职责。

## 四个动作必须分开

| 动作 | 规划语义 |
|---|---|
| 本步结束后暂停 | 当前阶段结束并对账后停在安全边界，同一活进程中可以继续 |
| 取消任务 | 阻断后续执行并清理；不能以「继续」恢复这个终态 |
| 要求修改补丁 | 复用现有 REQUEST_CHANGES，开新 Attempt，重新规划和批准 |
| 授权再审一轮 | 消费用户额外的循环授权，Task 累计次数与总预算不清零 |

计划修订则发生在批准前：产生新 revision，旧批准失效，继续使用原 Task 预算。进程重启后的中途任务仍为 INTERRUPTED，本轮规划不承诺可执行 checkpoint。

## 从源码确认的开发缺口

- 规划与实施仍默认共用 `AgentDeps.resolution`，需要真实分路由，并把独立计划方纳入出站披露。
- `PausableDeadline` 解决的是批准等待期间的计时；当前没有用户可用的通用暂停和交接继续接口。
- 外部 CLI 与模型 API 的写审同厂商处理不同。新协作模式将统一要求可证明异构；历史任务保持原语义。
- 会话名称仍使用 basename，双工位真实输入、流式输出与取消还待开发。协议握手不等于这些能力已经完成。

## 交付与验证边界

本地设计文档已形成完整流程规格和 gpt-5.6-sol 实施任务书，后者含 7 个工作包、20 条验收及直接交接提示词。它们是产品种子下一轮工作的规划，不调整正式 PRD/TD、ADR、Stage 0 或 M2 状态。

本轮运行 `pnpm typecheck` 通过；定向执行 `agent.crossreview`、`agent.phase`、`authority.egress.e2e`、`authority.attempt.e2e`、`observer.boundary` 五个测试文件，50 项通过。它们验证现有底座，没有覆盖尚未实现的新流程。

未重跑全量测试、Electron 自检、真实模型收发和 Desktop GUI。最终集成验收须分别记录这些层次，已有 Desktop 活跃会话接管也单列验证，不能用新建引擎会话代替。
