# 验证"通过"，证明不了一份被改过的验证

> 开发记录 · 2026-08-19 · RepoPilot

08-17 审计里全仓最短的一条 false-green 路径：给 `vitest.config.ts` 的 exclude 加一条，基线失败的命令在
修复后变绿 → 补丁绑上一次 passed 的验证 → 用户看到绿色「已修复」→ `SUCCEEDED`。
上一篇刚让外部 CLI 当作者 —— 一个黑盒，它完全可以这么干。所以这一刀紧跟着切。

## 一、不拦，降级

第一反应是把 tsconfig/vite/vitest/eslint 配置全加进受保护路径，让 mutation 引擎直接拒。
想了一下不对：修类型错误有时就是要改 tsconfig，修 bug 经常要改测试。一刀切成 hard deny 等于把一半合法修复也拦了。

TD 的原话其实已经给了答案："Patch 修改任一验证输入时……无法独立证明时只能 BLOCKED/UNVERIFIED"。
原型里没有"独立 task assertion"那一半，所以只做降级这一半：

- 封存时（`sealPatch`）把补丁里属于**验证输入**的路径记进 `PatchArtifact.verificationInputsTouched`，未验证清单第一条写
  `⚠ COVERAGE_WEAKENED`；
- 接受时（`decidePatch`）：`verified = 验证通过 && 没动验证输入`。动了 → `ACCEPTED_UNVERIFIED`，`terminalFacts.verificationRunId=null`，
  状态原因写明"验证虽通过，但补丁修改了验证输入（…）"；
- 导出文件头 `# verified: NO — verification … passed, but the patch modified verification inputs (…)`；
- 审查页"已修复"徽章旁紧挨着一条横幅点名文件。徽章照常显示 —— 事实不隐藏，只是旁边说清楚它证明不了什么。

放在 `sealPatch` 里而不是某个调用点，是让首次封存、整改后重封存、挽救封存三条路口径一致；不然重封存的补丁会"看起来更干净"。

## 二、什么算验证输入：模式猜得到的，和只能从命令推的

两类：

1. 按模式（`coverage.ts`）：`**/tsconfig*.json`、`**/vite.config.*`、`**/vitest.config.*`、eslint/babel 配置、`*.test.*`/`*.spec.*`、
   `__tests__/`、`__mocks__/`、`__snapshots__/`、`test/`、`tests/`、setup 文件。普通源码一个不报，`src/testing-utils.ts` 也不报。
2. 按命令：验证命令 argv 里**直接点名且真实存在**的仓库文件。`pnpm build` 推不出任何东西；`node check.mjs` 推出 `check.mjs`；
   flag、绝对路径、`..`、不存在的 token 都不算。这一类模式永远猜不到 —— e2e 夹具的验证就是 `node check.mjs`，
   作者把 `check.mjs` 改成 `console.log('ok')` 一行，源码还是 broken，验证照样绿。

e2e 就按这条路走了一遍：外部作者改 `check.mjs`、不碰 `src/app.js` → `VERIFICATION_FINISHED 验证通过` → 补丁
`verificationInputsTouched=['check.mjs']` → 接受 → `ACCEPTED_UNVERIFIED`，导出头 `verified: NO`。内部模型用 `workspace_mutate`
走同一条路，同样降级。对照组只改 `src/app.js` → `verificationInputsTouched=[]` → `SUCCEEDED`，规则没有误伤。

## 三、批准的不只是摘要

审计 G-3："用户不填限定路径时 `allowedPaths` 兜底为 `**`"—— 这件事只藏在 TaskForm 的占位符里。现在 Core 把"允许改动范围 /
受保护路径 / 实现方是谁"附在审批请求的 `detail` 里，审批卡把这几行显示在摘要下面。

## 四、踩了什么坑

**1. `approval.detail` 根本没被渲染。** 我把范围写进 detail，跑完测试全绿，去看 `ApprovalCard` —— 它渲染的是 `plan.summary` 和
`plan.steps`，`detail` 从没上过屏。绿测试证明不了用户看得见。加了 `approval-scope` 块并用测试钉住"摘要不重复出现、范围三行都在"。

**2. 旧快照没有新字段。** `verificationInputsTouched` 是可选字段：旧 patch 读出 `undefined` 按空处理，不追溯改写已落盘的终态；
UI 同样"缺字段不出横幅"，测试里专门 rerender 一个无字段的 patch。这是 08-08-02 那篇"增量字段跨重启往返"的同一条纪律。

**3. 给作者看的规则要同步。** 内部模型的执行规则和外部作者的简报都加了一句：不要为了让验证变绿去改配置/测试/验证脚本，
平台会标 COVERAGE_WEAKENED。规则不告诉作者，就只剩事后降级；告诉了，至少少走一轮。

## 五、数字

- 新增 `core/coverage.ts`；`patch.ts`/`authority.ts`/`agent.ts`/`RunDetail.tsx` 各一处；`PatchArtifact` 加可选字段。
- 测试 43 → 45 个文件、777 → 790 个：`coverage.test.ts` 7、`authority.coverage.e2e.test.ts` 3（黑盒作者 false-green、内部模型同路、对照组）、`RunDetail.test.tsx` +3。全绿，typecheck 过。

## 六、可复用的结论

- **被补丁改过的验证，通过了也不算数。** 这条不靠拦截实现，靠"记录 + 降级 + 在徽章旁边说清楚"。
- 验证输入有两类：**模式猜得到的**和**只能从实际命令推的**；后者才是夹具里最短的那条路。
- 绿测试 ≠ 用户看得见；写进 `detail` 的东西要确认有人渲染它。
- 新增字段一律可选，旧数据按旧语义，不追溯改写终态。
