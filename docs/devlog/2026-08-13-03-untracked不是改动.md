# untracked 不是"改动"，它是"根本没进来"

> 开发记录 · 2026-08-13 · RepoPilot

项目有条硬不变式，写在 `AGENTS.md` 第 8 条：

> **省略要报数。** 任何截断、过滤、排除都必须显示数量和原因 ——
> 静默过滤和静默通过是同一类问题。

之前每次都是发现一处补一处。这次换个做法：**系统性扫一遍**。
五个互相独立的视角同时看全仓——导入与快照、补丁与 mutation、
工具与命令输出、Renderer 视图、吞异常——共提出 53 条候选。

然后关键的一步：**换一批人去驳回它们**。给验证者的指令是"默认判不成立，
必须打开文件、grep 那个字段名、证明它在任何地方都没被披露，才允许判成立"。

结果 **30 条成立，23 条被驳回**。驳回的理由长这样：

> 这不是静默丢弃 —— 截断在三条独立路径上都有披露：patch.ts:66-68 的带内标记
> 携带了原因，`diffTruncated` 字段进了协议，RunDetail 也渲染了它。

43% 的驳回率让我对剩下那 30 条有信心。下面是其中最严重的一条。

## 一个新建的文件，被显示成"1 项改动"

```ts
const status = git(hostPath, ['status', '--porcelain']).trim();
dirtyLines = status ? status.split('\n') : [];
...
baseKind: !isGit ? 'NO_VCS' : dirtyLines.length > 0 ? 'DIRTY_WORKTREE' : 'CLEAN_COMMIT',
dirtyFileCount: dirtyLines.length,
```

`git status --porcelain` 的输出里包含 `??` 开头的 untracked 行。而快照的内容来自
`git ls-files` —— **只有 tracked 文件**。

于是一个只新建了一个文件的仓库：

- `baseKind` = `DIRTY_WORKTREE`
- `dirtyFileCount` = 1
- 界面显示「工作区基线 · 1 项改动」、「+ 未提交改动」
- 给模型的仓库信息写着「+ 1 项未提交改动」

而事实是：**快照内容与 HEAD 逐字节相同**，那个新文件一个字节都没进来。

这比漏报数更糟。漏报是"我没告诉你"，这是**分类撒谎**：把"完全没进来"
显示成了"进来了而且被改过了"。用户以为 Agent 正在修的那个文件，Agent 根本看不见。

按状态码拆开：

```ts
for (const line of status ? status.split('\n') : []) {
  if (line.startsWith('??')) untrackedCount += 1;
  else trackedDirtyCount += 1;
}
```

只有 tracked 改动才让基线偏离 commit —— 只有 untracked 时快照确实等同干净 commit，
谎称 `DIRTY_WORKTREE` 反而掩盖了真正的问题。`untrackedCount` 单独成一个字段，
在项目卡片、`RUN_CREATED` 事件、以及给模型的 brief 三处都报出来：

```
- 未跟踪文件: 2 个，**不在快照里**（快照只含 tracked 文件，它们对你不可见）
```

测试里那条负向断言是重点：

```ts
expect(snap.baseKind).toBe('CLEAN_COMMIT');
expect(snap.dirtyFileCount).toBe(0);   // 这个 1 绝不能出现在这里
expect(snap.untrackedCount).toBe(1);
// 快照内容确实与干净 commit 一致 —— 所以 CLEAN_COMMIT 是诚实的
expect(snap.treeDigest).toBe(clean.treeDigest);
```

## 顺带：三个裸 continue

同一个循环里还有别的。lstat 失败是这样处理的：

```ts
try {
  st = lstatSync(abs);
} catch {
  continue;          // ← git 说文件存在，我们读不到，然后它从两边同时消失
}
```

它既不进 `included` 也不进 `excluded`，`fileCount` 只是悄悄小了一个。
非普通文件则一律记成 `BINARY` —— 软链接不是二进制文件，那也是分类撒谎。

NO_VCS 路径更彻底：`walkPlainDirectory` 静默跳过 symlink、依赖/产物目录、
读不了的目录，还会在 8000 个文件处悄悄停下并返回一个**看起来完整的数组**。
于是界面上打印「排除文件 0 个」，而整棵 `node_modules` 都没进来。

`ExclusionEntry.reason` 加了三个取值（`SYMLINK` / `UNREADABLE` / `ENUMERATION_TRUNCATED`），
每条 `continue` 都留下一行。项目卡片那句写死的"依赖、产物、二进制、疑似 secret"
也换成按 reason 分组报数 —— 原来无论实际排除了什么都照念那一句。

## "尾部损坏只丢弃最后一条"

事件日志的读取长这样：

```ts
try {
  this.cache.push(JSON.parse(trimmed) as RunEvent);
} catch {
  // 尾部损坏只丢弃最后一条，不破坏已有 lineage
  break;
}
```

注释描述的是崩在写一半的情形，那时确实只坏最后一行。但 `break` 的语义是
**放弃它之后的全部**。中间坏一行，后面几百条完好的事件一起消失，而且一个数都不报——
时间线短了一截，界面上与"这个 Run 本来就只跑到这里"完全无法区分。

一份读不回来的日志不叫证据。改成继续读完、记录坏行数与首个坏行号，
由 authority 投影成 `evidence: 'DAMAGED'`（这条通道 `RunDetail` 早就会渲染，零新增 UI）。

改的时候发现二阶缺陷：

```ts
seq: this.cache.length + 1,
```

日志有坏行时 cache 比实际短，新事件会被写成一个**磁盘上已经用过的 seq**，
`after(afterSeq)` 的游标语义就此失效。改成从磁盘上见过的最大 seq 推。

## 读不出来的凭据，会被一次"保存"删光

`credentials.ts` 的 `load()` 对解密/解析失败一律返回 `{}`。两个后果，第二个严重得多：

1. 界面显示成"还没有任何连接"，而用户其实配过一堆 key；
2. `setKey` 会 `load()` → 得到 `{}` → 加一把新 key → 写回 `{ 新key }` ——
   **把那份仍在磁盘上的密文整个覆盖掉**，其余所有 provider 的凭据在一次"保存"里
   被永久删除，全程没有任何提示。

改成三态（`ABSENT` / `OK` / `UNREADABLE`），`UNREADABLE` 时拒绝一切写入。
测试里最关键的一行不是"抛错了"，是：

```ts
// 旧实现会把文件重写成只含 deepseek 的 store，另外两把 key 就此消失。
expect(readFileSync(file).equals(before)).toBe(true);
```

## 外部审核方：说要改，被判成了通过

最后一条来自交叉审核。`parseReviewOutput` 在 `findings` 畸形时一律归零：

```ts
const findings = Array.isArray(obj.findings) ? obj.findings.filter(...) : [];
return { verdict, findings };
```

而 `agent.ts` 判"审核通过"的条件是：

```ts
if (round1.verdict === 'PASS' || blocking1.length === 0) return done('REVIEWER_PASSED');
```

于是「`CHANGES_REQUESTED` + 读不出来的 findings」→ 零条阻断 → **判通过**。
审核方明说要改，平台当成没意见。

这里有个已有的测试挡了我第一版的修法：

```ts
it('findings 不是数组时归零，而不是把整个结论丢掉', () => {
  const r = parseReviewOutput('{"verdict":"PASS","findings":"none"}');
  expect(r?.verdict).toBe('PASS');
});
```

它是对的——`PASS` 时发现清单不驱动任何决定，归零是安全的。我一开始改得太宽，
把这条也弄红了。正确的修法是外科式的：归零只在 `verdict === 'PASS'` 时保留，
非 PASS 时整份判为不可解析。原测试保留并加注说明为什么两者不同。

## 可以带走的

1. **分类错误比漏报更糟。** 漏报是"我没说"，分类错是"我说了个反的"——
   用户的每一次确认都在强化一个错误结论。`untracked` 被算进 `dirtyFileCount`
   就是这一类：它把"完全没进来"说成了"进来了而且改过"。
2. **注释描述的是你想到的那个场景，不是代码的语义。**
   "尾部损坏只丢弃最后一条"和 `break` 之间差了一个"中间坏一行"。
3. **系统性扫 + 独立驳回，比逐个补洞有效。** 关键是驳回那一步要**换人**、
   要求默认不成立。43% 的驳回率是这批发现可信的理由。
4. **静默通过和静默过滤是同一类问题。** 这次两边各出现一次：枚举静默跳过
   （过滤），审核结论静默降级成通过（通过）。同一条不变式管住两者。
5. **修法要对准洞口，不要顺手扩大。** 已有的测试往往钉着一个你没想到的正确场景，
   把它弄红了先想想它为什么在那儿。
