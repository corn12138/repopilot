# 389 个测试全绿，而产品接上真实模型跑不通

> 开发记录 · 2026-08-09 · RepoPilot

昨天补完测试：389 个，全绿，15 个文件。今天开工前我让一组 agent 做了轮盘点，
第一条结论是这样的：

> 用户每一次点「批准计划」，都会在执行阶段的第一次模型请求上被 provider 以 400 拒绝。

也就是说，**这个产品接上真实 API 之后，一次都没法跑完。**

而 389 个测试全是绿的。

## 那条消息序列

`generatePlan` 里，模型调用 `submit_plan` 之后是这样处理的：

```ts
conversation.push({ role: 'assistant', content: response.content });
const results: ContentBlock[] = [];

for (const use of uses) {
  if (use.name === 'submit_plan') {
    const parsed = planSchema.safeParse(use.input);
    // …
    return {            // ← 直接 return，results 永远不会被写回 conversation
      planId: newId('plan'),
      // …
    };
  }
  const outcome = await dispatchTool(deps, use.name, use.input, 'PLANNING');
  results.push({ type: 'tool_result', toolUseId: use.id, /* … */ });
}

conversation.push({ role: 'user', content: results });   // ← 走不到这里
```

第 385 行把带 `tool_use` 的 assistant 消息推进了历史，第 414 行直接 `return`。
`results` 数组从来没被写回去。

关键在于 `conversation` 这个数组是**跨阶段复用**的：

```ts
const plan = await generatePlan(deps, conversation);   // 规划
// … 用户审批 …
const ended = await executionTurns(deps, conversation); // 执行，同一个数组
```

审批通过后又往后面追加了一条审批通知。最终发出去的是：

```
[0] user       任务描述
[1] assistant  [tool_use: submit_plan]     ← 没有对应的 tool_result
[2] user       "用户已批准以下计划，现在开始执行…"
```

Anthropic 返回 `tool_use ids were found without tool_result blocks immediately after`，
OpenAI 兼容端返回 `An assistant message with 'tool_calls' must be followed by tool messages
responding to each tool_call_id`。两家都是 400。

更糟的是这条坏消息**永久留在 conversation[1]**。就算某个宽松的中转端点放行了第一次，
此后每一轮执行、每一轮自修复都带着它。

## 为什么 389 个测试没抓到

因为测试用的是 `ScriptedModel` —— 一个按脚本回应的替身。

```ts
class ScriptedModel implements ModelInvoker {
  async invoke(input: Parameters<ModelInvoker['invoke']>[0]) {
    const response = this.script(input.purpose, input);
    return { invocationId: `inv_fake_${this.turn}`, response, manifest: { /* … */ } };
  }
}
```

它**不校验消息序列**，因为它根本不是 provider。它只看 `input.purpose` 和最后一条消息的
文本，然后返回预设的响应。

这就是脚本化替身的固有盲区：**它能测你的逻辑，测不了你和外部世界的契约。**
而契约违反同样会让产品完全不能用。

## 修法：先写回历史，再决定返回

第一反应是"return 之前补一条 tool_result"。但这不够 —— 模型完全可能在同一轮里
先调 `fs_read` 再调 `submit_plan`，那样后面那些 id 也会变成孤儿。

所以改成：拿到计划先存着，把本轮**全部** `tool_use` 回填完再返回。

```ts
/**
 * 本轮 submit_plan 解析出的计划。
 *
 * 拿到之后**不能立刻 return** —— 必须先把本轮全部 tool_use 的 tool_result 写回历史。
 * 这个 conversation 会被执行阶段继续复用，一条带 tool_use 却没有对应 tool_result 的
 * assistant 消息会让 Anthropic 与 OpenAI 兼容端都以 400 拒绝整个请求。
 */
let submitted: PlanRevision | null = null;

for (const use of uses) {
  if (submitted) {
    // 计划已在本轮提交，剩余工具不再执行 —— 但 id 仍要回填，否则它们就是孤儿
    results.push({
      type: 'tool_result',
      toolUseId: use.id,
      content: '本轮已提交计划，该工具调用未执行。请在计划获批后的执行阶段再调用。',
      isError: true,
    });
    continue;
  }
  // …
}

// 先写回历史，再决定是否返回 —— 顺序反了就是这个 bug 本身
pushUser(conversation, results);
if (submitted) return submitted;
```

## 顺带发现的第二处

`executionTurns` 里有同一类问题：

```ts
for (const use of uses) {
  throwIfCancelled(deps.signal);        // ← 抛出时 results 永远不会被 push
  const outcome = await dispatchTool(deps, use.name, use.input, 'EXECUTION');
  results.push({ /* … */ });
}
conversation.push({ role: 'user', content: results });
```

今天这条不会暴露 —— 被取消的 Run 直接结束，conversation 跟着丢掉。
但 PRD 要求的可续跑 Checkpoint 一落地它就是活的。用 `try/finally` 堵上：

```ts
} finally {
  // 正常跑完、被取消、或 dispatchTool 抛错，都必须把本轮**全部** tool_use 回填。
  // 半截的历史一旦被复用（重启续跑、交叉审核复读），两家 wire 都会返回 400。
  for (const use of uses.slice(results.length)) {
    results.push({
      type: 'tool_result',
      toolUseId: use.id,
      content: '该工具调用未完成（执行被中断）。',
      isError: true,
    });
  }
  pushUser(conversation, results);
}
```

## 把契约变成代码

改完 bug 只是恢复现状。真正的问题是：**这类缺陷凭什么下次能被抓到？**

于是把这条 wire 契约写成一个可执行的检查，放进领域层：

```ts
/**
 * 检查消息序列是否满足两家 wire 共同的硬性要求：
 * **每条含 tool_use 的 assistant 消息，下一条消息必须回填全部 toolUseId。**
 *
 * 所以这不是"发出去再看"的事情，得在出站前拦住：provider 的 400 只会被归类成
 * BAD_REQUEST 加一句供应商原文，定位不到是我们自己拼错了历史。
 */
export function findOrphanToolUse(messages: readonly ModelMessage[]): string | null {
  for (let i = 0; i < messages.length; i += 1) {
    const msg = messages[i]!;
    if (msg.role !== 'assistant') continue;
    const uses = toolUsesOf(msg.content);
    if (uses.length === 0) continue;

    const next = messages[i + 1];
    const answered = new Set(
      (next?.content ?? [])
        .filter((b) => b.type === 'tool_result')
        .map((b) => b.toolUseId),
    );
    const orphans = uses.filter((u) => !answered.has(u.id));
    if (orphans.length === 0) continue;

    const which = orphans.map((u) => `${u.name}(${u.id})`).join(', ');
    return next
      ? `messages[${i}] 的 tool_use 未被 messages[${i + 1}] 回填：${which}`
      : `messages[${i}] 的 tool_use 后没有任何消息：${which}`;
  }
  return null;
}
```

两处使用：

**生产侧** —— 网关出站前置检查里加一条，不满足就是 NOT_SENT：

```ts
if (current !== resolution.digest) return 'ROUTE_DRIFT';
if (!resolution.origin.startsWith('https://')) return 'INSECURE_ORIGIN';
// 我们自己拼错的历史，不要花一次真实请求去换供应商的一句 400。
const violation = findWireViolation(messages);
if (violation) return `MALFORMED_CONVERSATION: ${violation}`;
```

**测试侧** —— 4 个 `ScriptedModel` 替身统一调用同一个函数：

```ts
// 先快照再校验：抛在快照前的话，出问题的那一次调用反而查不到。
// 真实 provider 会对孤儿 tool_use 返回 400，测试替身不会 —— 所以这里
// 主动用与网关同一个校验器把关，否则这类回归在测试里是静默的。
const orphan = findWireViolation(input.request.messages);
if (orphan) {
  throw new Error(`第 ${this.calls.length} 次调用（${input.purpose}）收到非法消息序列：${orphan}`);
}
```

一份实现，两处生效。替身不再是"不校验"，而是"用和生产一样的校验器"。

## 断言必须真的会红

昨天那篇写过一条教训：**永远不会红的断言等于没有断言**。所以这次修完，
我把修复临时改回错误的顺序，跑一遍：

```
× 执行阶段超预算：发出 BUDGET_EXHAUSTED，且此后不再有任何模型调用
  → 第 2 次调用（EXECUTION）收到非法消息序列：messages[1] 的 tool_use 未被 messages[2] 回填：submit_plan(tu_submit_plan_fo1c8r)
× 未验证模式 > 跳过基线、跳过重验、不做自修复，直接产出 PATCH_READY
  → 第 2 次调用（EXECUTION）收到非法消息序列：messages[1] 的 tool_use 未被 messages[2] 回填：submit_plan(tu_submit_plan_1mppzb)
× 发给模型的消息序列必须合法 > 计划获批后的第一次执行调用，历史里不能有孤儿 tool_use
× 发给模型的消息序列必须合法 > submit_plan 与别的工具同轮出现时，两个 id 都要被回填
…
Tests  10 failed | 16 passed
```

10 条红，而且每条都直接点名是哪个 id 没被回填。恢复修复后全绿。

新增的断言里有一条专门用来防"检测器本身是假的"：

```ts
it('findOrphanToolUse 真的能抓到孤儿 —— 否则本组其余断言都是空的', () => {
  const orphan = [ /* assistant(tool_use) 后面直接跟 user text */ ];
  expect(findOrphanToolUse(orphan)).toContain('submit_plan(tu_1)');
  // 回填之后就合法
  expect(findOrphanToolUse(answered)).toBeNull();
  // 只回填了一半也算孤儿
  expect(findOrphanToolUse(half)).toContain('submit_plan(tu_2)');
});
```

还有一条前提检查，防止断言变空：

```ts
// 前提：确实发生了「规划提交 → 执行」的跨阶段历史复用，
// 否则下面那句断言什么都没验证。
const exec = gateway.calls.filter((c) => c.purpose === 'EXECUTION');
expect(exec.length).toBeGreaterThan(0);
expect(
  first.messages.some((m) => toolUsesOf(m.content).some((u) => u.name === 'submit_plan')),
).toBe(true);

expect(findOrphanToolUse(first.messages)).toBeNull();
```

## 一个没解决的尾巴

修完之后跑全量，有一次 `agent.e2e.test.ts` 红了：

```
AssertionError: expected 'BLOCKED' to be 'PATCH_READY'
```

之后连续 9 次（6 次单跑 + 3 次全量）都是绿的，复现不出来。

`BLOCKED` 在 `agent.ts` 里只有一处来源 —— 自修复循环里 `budgetExceeded()` 为真，
而这个 e2e 的 FakeHost 只判 `modelTurns > 30`。脚本模型正常只需 ~6 次调用，
31 次意味着进了循环。推测是并行负载下真实 `npm run build` 偶发失败，触发自修复，
而脚本模型的状态机只看"最后一条消息的文本"来决定下一步，改动已生效的情况下
会反复发出同一个 `REPLACE_EXACT_TEXT_SPAN` 拿到 `ZERO_MATCH`，形成活锁。

**这个推测我没有证实。** 能做的是让它下次红的时候能自证：

```ts
// 带上 detail 与模型轮次：这条断言曾经红过一次且复现不出来，
// 只说 "expected BLOCKED to be PATCH_READY" 是查不下去的。
expect(
  result.kind,
  `result.detail=${result.detail} · modelTurns=${recorder.ledger.modelTurns} · ` +
    `finalVerification=${result.finalVerification?.commands.map((c) => `${c.commandId}=${c.outcome}`).join(' ') ?? 'null'}`,
).toBe('PATCH_READY');
```

已经开了单独的任务去追。写在这里是因为：一次红过又复现不出来的测试，
如果不记下来，三个月后就变成"一直都这样，重跑一下就好了"。

## 可以带走的

1. **脚本化替身测不了你和外部世界的契约。** 它能证明逻辑对，不能证明产品能用。
2. **契约要写成可执行的检查，生产和测试共用同一份。** 替身不该是"不校验"，
   而该是"用和生产一样的校验器"。
3. **出站前拦住自己拼错的请求。** provider 的 400 只会给你一句 `BAD_REQUEST` 加供应商原文，
   定位不到是自己的问题。
4. **改完要反向验证断言真的会红。** 把修复临时撤掉跑一遍，是最便宜的"这条测试有没有用"检查。
5. **加一条"检测器本身有效"的测试。** 否则整组断言可能都建立在一个永远返回 null 的函数上。
6. **偶发的红要记下来并让它下次可自证**，不要因为复现不出来就当没发生。
