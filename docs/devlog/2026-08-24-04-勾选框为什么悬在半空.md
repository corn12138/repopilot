# 勾选框为什么悬在半空

用户在真机上圈了一张图：出站同意的勾选框孤零零悬在一大片空场正中，
披露文字在窗口右缘被挤成一字一行的竖排碎片，问"这个设计联动是不是很 low"。

答案分两层：**原则不 low，呈现确实 low —— 而且呈现里叠着一个真 bug。**

## 根因：全局规则咬了勾选框

```css
input, textarea, select { width: 100%; ... }
```

这条全局规则是给文本输入框写的，但它把 `<input type="checkbox">` 一起吃了：
勾选框的盒子被拉成整行宽（Chromium 把勾选图形画在盒子正中 —— 就是悬在行中央的
那个勾），旁边的披露 `<span>` 被挤出容器，在右缘以 1 字符宽度逐字换行 ——
顺带把整行撑得很高，形成那片空场。

`.composer-consent input` 早有人写过 `flex: none; margin-top: 2px`（说明当时就在
对抗什么），但没有覆盖 `width` —— 全局的 100% 一直赢着。这个 bug 从披露功能
上线（Slice H）起就在：jsdom 没有布局，105 条 renderer 测试一条都测不出它；
selftest 的渲染探针当时也没有量过这个元素。**第一个抓到它的是用户的眼睛。**

修复一行：`width: auto`。

## 布局 bug 之外：联动本身哪里 low

1. **同意作废是静默的。** 披露 digest 一变（换路由/加审核方/换快照），勾选自动
   归零 —— 机制是对的（你确认的是"这一份"披露），但界面上勾就是凭空没了，
   「开始」重新变灰，没有一个字解释。用户的体感：勾了又让我勾，抽风。
2. **禁用的「开始」不说原因。** 五个条件任一不满足按钮就灰着，用户只能挨个猜。
3. **披露块没有边界。** 一行裸勾选框 + 一句长文，视觉上不像"一个需要你读的东西"。

改法（原则一字不动，全是呈现层）：

- 披露收进带边框的卡片（与输入框同圆角），长 URL `overflow-wrap: anywhere`；
- 勾选作废时显式解释："披露内容已变化 —— 你此前的确认针对的是旧披露，请重新
  阅读并再次勾选"；
- 「开始」灰着时，旁边按 canSubmit 的判定顺序给出**第一条**拦住它的原因
  （先写目标 / 先配模型 / 审核方填错 / 先确认披露 / 命令待批准），按钮 title 同步。

**没有改的**：同意仍然每任务一次、digest 一变即作废。这不是交互债，是这个产品
的命根（先披露、后同意、再出站，P0 无"仍然发送"）。要动它只有一个正当方向 ——
同 digest 的会话内沿用 + 变化时高亮 delta —— 那是一次治理语义变更，得单独议。

## 让这类 bug 以后有地方能红

jsdom 测不出布局，就把断言放进唯一有真实布局的地方：selftest 的渲染探针。
注入一个同 class 的哨兵 `<label class="composer-consent"><input type="checkbox">`，
量勾选框的 `getBoundingClientRect().width`，超过 40px 即 FAIL 并点名根因。

负向验证做了：把 `width: auto` 临时拿掉，探针立刻红 ——
`同意勾选框实测宽度 800.0px —— 全局 input { width:100% } 又咬到它了`。

## 可复用的结论

- **全局元素选择器是长牙的。** `input { width:100% }` 写下的那天就注定咬到
  checkbox/radio；给全局规则挑元素类型时，想清楚它的所有子类型。
- **"有人对抗过它"是气味。** `flex:none` 已经站在那里对抗全局规则了，
  说明冲突早被感知过 —— 对抗到一半的规则比没有规则更能说明问题。
- **状态凭空变化必须带解释。** 勾选被机制取消是对的，取消得无声是错的；
  同一条原则此前落在 INCONCLUSIVE、降级、截断上，这次落在勾选框上。
- **布局断言放在有布局的地方。** jsdom 之外，selftest 的真实引擎探针
  就是这个仓库的"视觉回归最小单元"；新增探针先做负向验证再入库。
