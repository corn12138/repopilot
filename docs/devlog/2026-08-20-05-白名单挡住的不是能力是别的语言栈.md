# 白名单挡住的不是能力，是用别的语言栈的人

前天我把用户手填的验证命令改成"先分级、非 R1 一律拒绝"，
理由很正当：此前它一律硬编码 R1，等于"填一次即永久授权"。
今天我拿一个 Makefile 项目试用自己的产品，第一步就被自己挡在门外。

## 问题是什么

分级规则是白名单：

```ts
const R1_BINARIES = new Set([
  'node', 'npx', 'tsx', 'deno', 'bun',
  'tsc', 'vitest', 'jest', 'eslint', 'vite', 'turbo',
  'npm', 'pnpm', 'yarn',
  'make', 'cargo', 'go', 'python', 'pytest',
  ...
]);
// 认不出的一律 R2，fail-closed
return { risk: 'R2', reason: `未知可执行名 ${bin}：不在已知本地工具白名单内` };
```

未知即 R2、R2 即拒绝。于是这些命令一条都填不进去：

```
bash scripts/test.sh      just ci        bazel test //...
./run-tests.sh            gradle check   dotnet test
mix test                  rake spec      swift test
```

`R2` 那一档当时的拒绝语是"原型不开放"。**它撒了一半的谎** —— 听上去像是
"这个能力我们还没做"，实际上是"我们不认识这个可执行名"。

而真正让我改主意的是这一行，它一直是 R1：

```
node -e "require('child_process').execSync('rm -rf /tmp/whatever')"
```

`node -e` 能执行任意代码。所以白名单**根本不是一堵墙** ——
它拦不住有意为之的人，只拦住了用 Ruby、用 Bazel、用一个 shell 脚本跑测试的人。
挡住的不是能力，是**别的语言栈**。

PRD 早就写了这一档该怎么办："R2 需要一次性精确审批 + TTL + max uses"。
我当时跳过了它，用一句"原型不开放"糊了过去。

## 怎么解决的

把 R2 劈成两半。关键是给判级结果加一个**成因**，而不只是等级：

```ts
export type CommandRiskCause =
  | 'UNKNOWN_BINARY'    // 我们不认识它 —— 唯一可以批准的一类
  | 'NETWORK_OR_DEPS'   // 联网 / 装依赖 / 容器
  | 'GIT_UNKNOWN' | 'DESTRUCTIVE' | 'PRIVILEGED' | 'PUBLISH' | 'GIT_WRITE'
  | 'KNOWN_LOCAL';

/** 只有这一类 R2 能被一次性精确批准 —— 其余的批准了也不执行 */
export function isApprovableCause(v: CommandRiskVerdict): boolean {
  return v.risk === 'R2' && v.cause === 'UNKNOWN_BINARY';
}
```

**等级决定"能不能直接跑"，成因决定"能不能被批准"。** 这两件事此前挤在一个字段里。

`NETWORK_OR_DEPS` 为什么连批准通道都不给？不是保守，是物理上做不到 ——
看一眼工作区是怎么拿到依赖的：

```ts
// workspace.ts: 把宿主已安装的 node_modules 以 symlink 形式挂进工作区
symlinkSync(join(this.hostRepoPath, 'node_modules'), join(genPath, 'node_modules'), 'dir');
```

在工作区里跑 `pnpm install`，写的是你**真实仓库**的依赖树。
"宿主仓库只读"这条不变式在那一刻就破了。这不是一次点击能授权的东西，
所以界面在这里给的是别的走法，不是复选框：

> 请先在你自己的仓库里装好依赖，RepoPilot 会只读复用它 ——
> 工作区的 node_modules 是指向你仓库的 symlink，在这里装依赖会写进你真实的依赖树。

批准本身是一张票：

```ts
const approval: CommandApproval = {
  approvalId: newId('capp'),
  argv: clean,                                   // 原样留存：事后要能复核"我当时批的是什么"
  argvDigest: commandArgvDigest(clean),          // 绑整条 argv
  reason: verdict.reason,                        // 它为什么需要批准，不是用户填的备注
  expiresAt: new Date(Date.now() + 15 * 60_000).toISOString(),
  maxBindings: 1,                                // 一张票只能进一个 Run
  bindings: 0, boundRunIds: [], executions: 0,
};
this.commandApprovals.set(approval.approvalId, approval);   // 只在内存里
```

六条约束，每条都对应一种"授权会怎么扩散"：

| 维度 | 约束 | 挡的是 |
|---|---|---|
| 精确 | 绑整条 argv digest | `bash test.sh` 的批准覆盖 `bash test.sh -u` |
| 一次性 | `maxBindings = 1` | 一张票喂给第二个任务 |
| 不落盘 | 进程重启即作废 | "上个月批的今天还在生效" |
| 时效 | 15 分钟 | 批了忘了，半天后被别的操作用掉 |
| 身份 | 只对 BASELINE / VERIFICATION | 模型借用户的票去跑自己的命令 |
| 每次现问 | 执行期闸门逐次校验 | 登记时查过就一路放行 |

最后一条落在 `runVerification` 里 —— 它原本是硬编码的 `if (def.risk !== 'R1') 拒绝`：

```ts
if (def.risk !== 'R1') {
  const verdict = approvals?.consume(def, role) ?? { ok: false, reason: '本次运行没有命令批准通道' };
  if (!verdict.ok) {
    outcomes.push(await record(def, async () => ({ ...spawnError(verdict.reason) })));
    continue;   // 不跑 ≠ 通过：SPAWN_ERROR 会让 passed=false
  }
}
```

`?? { ok: false }` 那半行是刻意的：**缺省是关的**。不传 checker 就等于没有批准通道，
而不是"忘了传就放行"。

还有一条我特意写进测试标题：

```ts
it('批准过的命令登记成功，但风险等级如实留在 profile 里 —— 不被洗白成 R1', ...)
expect(profile.commands.user1!.risk, '批准是"允许它跑"，不是"把它变成 R1"').toBe('R2');
expect(verifyCalls[0]!.risk, '账本里记的是它真实的等级 R2').toBe('R2');
```

批准改变的是"能不能跑"，不改变"它是什么"。把 risk 改写成 R1 会让账本、
时间线、日后的审计全部看不出这里发生过一次人为放行。

## 踩了什么坑

### 一、我差点给"执行次数"设上限

PRD 的措辞是 "TTL + max uses"，我第一版真的写了 `maxUses` 并在每次执行时递减。
写完算了一下一个 Run 里这条命令要跑几次：

```
基线 1 + 终验 1 + 每轮自修复重验 1×N + 交叉审核整改后重验 1×M
```

而 N 是用户配的 `maxSelfFixRounds`，M 在用户点"继续交叉审核"之后还能接着涨。
任何我猜的上限都会在某个真实任务里被用尽 —— 用尽之后会发生什么？
那条验证命令记 `SPAWN_ERROR`，验证不通过，**Run 以失败收场**。

这是**假红**。而这个产品所有的设计都在防假绿，防假红同样重要：
一次合法的重验被基础设施掐掉，用户看到的是"我的测试挂了"。

想清楚之后，`maxUses` 改成了 `maxBindings`：

> 要限的是"这次授权能扩散多远"，不是"这条命令跑了几遍"，所以次数照记不照拦。

`executions` 照样计数、照样进事件流，只是不作为闸门。
这是与 PRD 措辞的一处**显式偏离**，写进了 README 和类型注释里 ——
偏离本身不丢人，偷偷偏离才是。

### 二、判级和签发合在一个接口里

界面要在用户打字时就告诉他"这条命令需要批准"，所以判级得随打字跑。
第一版我只做了 `command.requestApproval`，界面 debounce 之后去调它 ——
于是每敲几个字就在 Core 里堆一张票。**"一次性"就只剩名义上的了。**

拆成两个方法：

```ts
'command.classify':        // 只判级，不留任何东西，问一万次都行
'command.requestApproval': // 签发。这是一个手势，不是一次查询
```

对应的用例标题是：`classify 只判级不签发：问一万次也不会在 Core 里留下一张票`。

### 三、想在测试里跟后台 Run 抢时序

有一条我想验的是"票被撤走之后，执行期闸门会自己再查一次"。第一版这么写：

```ts
const { run } = await harness.createTask(...);
harness.authority.commandApprovals.clear();     // 抢在基线跑之前清掉
await harness.waitForStatus(run.runId, [...]);
expect(v.commands[0]!.outcome).toBe('SPAWN_ERROR');
```

红了：`expected 'EXIT_NONZERO' to be 'SPAWN_ERROR'`。基线已经跑完了。

我可以加个 sleep 反过来赌，但那只是把偶发红换个方向。真正的问题是
**我在用一个异步的整体流程去验证一个同步的判定**。改成直接问闸门：

```ts
const checker = authority.approvalCheckerFor(record);
authority.commandApprovals.clear();
const verdict = checker.consume({ ...def, approvalId }, 'VERIFICATION');
expect(verdict.ok).toBe(false);
expect(verdict.reason).toContain('批准记录已不存在');
```

而「不跑 ≠ 通过」那半句，交给 `verify.test.ts` 直接对 `runVerification` 断言，
连 Run 都不用起。**要验的是哪一层，就在哪一层验。**

顺带补了对照组 —— 否则"R2 被拒"这条断言在"R2 永远跑不了"的实现下也是绿的：

```ts
it('对照组：闸门放行时 R2 命令真的执行 —— 证明上面两条不是"R2 永远跑不了"', ...)
it('R1 命令不打扰闸门：批准通道只对高于 R1 的命令生效', ...)  // asked === 0
```

### 四、fixture 里的 `git worktree list` 不是我以为的那一档

写"不可批准"的表驱动用例时，我拿 `git worktree list` 当"未列出的 git 子命令"。红了：

```
git worktree list: expected 'GIT_WRITE' to be 'GIT_UNKNOWN'
```

`worktree` 在 `GIT_R4` 里 —— 它能建、能删工作树。换成 `git bisect start` 才是
真正没被列出来的那一档。**测试 fixture 也会说谎**，尤其是"我以为这个例子代表 X"。

## 可复用的结论

- **"未知"和"已知危险"要分开记。** 挤进同一个等级，你就只能一起拒绝或一起放行，
  而它们的正确出路完全相反：一个该交给人判断，一个该连按钮都不给。
- **白名单的作用是防误操作，不是防人。** 当白名单里已经有 `node -e` 时，
  拒绝 `bash test.sh` 挡不住任何攻击者，只挡住了正常用户。要么两个都拦，要么承认这一点。
- **给权限设上限之前，先算一遍正常用法会用到多少次。** 算不出确定的数，
  说明这个维度不该设闸门 —— 设了就是在制造假红。
- **判级要能随便问，签发必须是一个手势。** 合在一起的接口会让"一次性"名存实亡。
- **偏离 PRD 要写下来。** 写在类型注释和 README 里，附上算式和理由，
  比悄悄实现成另一个样子好得多。
- **要验哪一层就在哪一层验。** 用异步流程去验同步判定，得到的不是覆盖率，是偶发红。
