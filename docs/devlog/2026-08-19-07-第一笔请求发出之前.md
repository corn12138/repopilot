# 第一笔请求发出之前

> 开发记录 · 2026-08-19 · RepoPilot

08-17 审计里有一行我一直绕着走：`grep -rn 'consent\|Consent\|Disclosure\|DLP' prototype/src` **零命中**。
第一笔请求把源码发往第三方中转站之前，没有披露、没有确认、没有内容扫描。它是 PRD 里唯一"P0 且零落点"的整面。
这一轮把它补上 —— 披露、精确同意、最小 DLP、运行页逐笔出站视图。三个决定值得写，两个坑值得留。

## 一、同意的不是"出站"，是一份 digest

第一稿想做一个新的 Run 状态 `WAITING_DATA_CONSENT`（TD 里有）。想了想那要改状态机、审批卡、恢复路径，而第一笔出站其实就在任务创建之后 —— 披露完全可以在 `task.create` 之前给。于是：

- `egress.disclosure`（新 IPC）：给定快照 + 实现方 profile + 审核方/作者，Core 算出 `DataEgressDisclosure`：送给谁（角色/通道/官方还是中转/精确 origin/模型）、送什么类别（任务文本、被读取的片段、命令输出、补丁 diff、审核发现，外部 CLI 作者额外一条"整仓一次性副本"）、以及 `policy: {retention: UNKNOWN, training: UNKNOWN, region: UNKNOWN}` —— 我们**不知道**对方政策，就写不知道，不编。digest 盖住全部字段。
- `task.create` 必须带回 `egressConsentDigest`。Core 用**同一个函数、同一套输入**重算再比对：缺 → `CONSENT_REQUIRED`；对不上 → `CONSENT_STALE`。用户同意的是这一份，不是"同意出站"这个动作 —— 加了审核方、换了作者、换了模型，digest 就变，旧同意自动作废。e2e 钉了这条：用"只有实现方"的 digest 去建"有审核方 + 作者"的任务，拒。
- `ModelGateway.preflight`：除 `CONNECTIVITY_TEST` 外每次调用都必须带 consent，且 consent 覆盖的冻结路由 digest 里要有这一条 —— 否则 `CONSENT_MISSING` / `CONSENT_STALE`，NOT_SENT，fetch 一次都不调。Loop 拿到的 gateway 是 authority 包过一层的 `consentBoundGateway`，忘带就是缺。

界面上披露常驻输入框上方，不进高级抽屉：一句话 + checkbox + 可展开的"会送出哪些数据"。不勾不能发；披露取不到也不能发（fail-closed，原因显示出来）。

## 二、DLP 放在哪一层：三道，不是一道

只做高置信度模式（AKIA/ASIA、私钥块、`Authorization: Bearer …`、sk-…、ghp_…、xox…、AIza…）。P0 没有 override，所以宁可漏低置信度的，也不让一条假警报把人锁在门外 —— `password = process.env.PASSWORD`、`"sk-test"`、`AKIA...` 占位符都不报，测试里钉着。

放在哪一层，我改了一次主意：

1. 一开始只在网关 preflight 拦。e2e 一跑，请求确实被拦了（NOT_SENT，原因只有种类和位置），但 `VERIFICATION_FINISHED` 事件的 `stderrPreview` 里**原文还在** —— 它已经落盘了。网关那一道拦的是出站，拦不住持久化。
2. 所以第二道在**命令输出投影层**（`command.ts` 的 `outcome()`）和工具投影层（`tools.ts` 的 `project()`）：高置信度 span 换成 `[REDACTED:<KIND>]`。预览进事件、进模型、进界面都只有占位符；私钥块从 BEGIN 到 END 整段拿掉（只脱头部等于把密钥正文留在后面）。这样基线 stderr 里的 key 在命令层就没了，规划照常进行 —— e2e 断言事件流、发出去的请求体、外部作者的简报三处都只见占位符。
3. 文件里有 key 呢？`fs_read` **拒读**而不是脱敏后给出去：脱敏后的内容一旦被模型 `REPLACE_WHOLE_FILE` 写回，占位符会覆盖真实值，补丁 diff 还会把原值带进 `-` 行。读不到，就没有这条路；界面上能看到原因。
4. 任务描述里粘了一把 key：`task.create` 直接拒 —— 那段文本会原样进 `RUN_CREATED` 落盘，先落盘再靠网关拦就晚了。
5. 外部 CLI 的 prompt（审核简报、作者简报）同样扫一遍：不因为"不经网关"就少一道。

网关那一道仍在，是最后防线，不是唯一防线。

## 三、对等可见：运行页多一张「数据出站」卡

用户随时能看到 Agent 把什么送给了谁：同意摘要（digest、目的地、通道、中转、数据类别、政策 UNKNOWN）+ 每次模型 / CLI 出站一行。被拦下的（NOT_SENT）与发出去的并列，拦下的原因写在那一行；token 未知写"未知"不填 0。事实全部来自持久化事件，没有第二份状态。

## 四、踩了什么坑

**1. 网关拦住了，日志里还有。** 就是上面第二道的来历。"请求没发出去"和"没有持久化"是两件事，测试要分开断言。

**2. 一个 `origin` 带不带 `/v1`。** 我在 e2e 里写 `origin: 'https://api.deepseek.com'`，实际 `https://api.deepseek.com/v1`。披露里的 origin 就该是**精确**的那一串 —— 这正是它要披露的东西；测试改成精确值。

**3. `run.list` 不是空的。** 同一文件里的用例共用一个受管数据根，前面用例的 Run 会被后面的新 Authority 恢复出来。断言"没建 Run"要用前后计数，不能 `toEqual([])`。

## 六、可复用的结论

- **同意要绑 digest，不绑动作。** 目的地一变旧同意自动失效，这比"记住用户同意过"诚实得多。
- **出站网关不是 DLP 的唯一位置**：落盘之前、给模型之前、给外部进程之前，各一道；脱敏用于流经，拒读用于文件，拒绝用于用户输入。
- **不知道的政策写 UNKNOWN**，不写"默认不训练"。
- "请求没发出去"≠"没有持久化"，测试分开断。
