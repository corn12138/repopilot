# 哪些失败可以重发

> 开发记录 · 2026-08-10 · RepoPilot

给模型网关加重试，写第一版判断时手停了一下：`ECONNRESET` 算网络错误，
网络错误当然该重试 —— 等等。连接被重置的时候，请求可能已经完整送到了
provider，它可能正在推理，可能已经计费。重发一次，就是两次执行、两次账单。

这一停，把"重试"从一个 while 循环变成了一个分类问题。

## 背景：零重试的代价

原型网关此前一次都不重试，也没有单次调用超时。真实后果两条：

- 一次网络抖动翻掉整个 Run —— 前面二十轮工具调用、几万 token 的上下文全部作废。
  当天打 x64 安装包时连挂两次的 `The server aborted pending request`，就是这类故障。
- 挂死的连接要等到 Run 的墙钟预算耗尽才结束，用户看到的是"卡住了"。

TD（`model-invocation-stream-and-egress` §4）对重试有整段硬合同，核心一句：
`BEFORE_BYTES` 可按幂等安全矩阵重试，`AFTER_BYTES_UNKNOWN` 默认禁止重发。
翻译过来：**没发出去的可以再发，发出去了但不知道结果的不可以**。

## 判据：(kind, sendState)，不是"网络错误就重试"

失败按请求生命周期分三段，`fetchJson` 在抛错时标注 `sendState`：

| sendState | 含义 | 例子 | 能否重发 |
|---|---|---|---|
| `NOT_SENT` | 连接根本没建立，请求没离开本机 | `ECONNREFUSED` / `ENOTFOUND` / TLS 握手失败 | ✓ |
| `RESPONDED` | 对端明确回了话 | 429 / 5xx（HTTP 状态码本身就是回执） | ✓（仅 429/5xx） |
| `SENT_OUTCOME_UNKNOWN` | 发出去了，结局不明 | `ECONNRESET`、正文读断、单次超时 | ✗ |

分类靠 undici 错误的 `cause.code`。关键的一条规则是**没有 code 的网络错误
一律保守判为结局不明** —— 因为分错方向的代价不对称：

- 把"发出去了"错标成 `NOT_SENT` → 重发 → 可能重复执行、重复计费；
- 把"没发出去"错标成结局不明 → 只是少一次重试。

一边是错账，一边是少一次便利。宁可少便利。

429 的 `Retry-After` 优先于指数退避，但封顶 20s —— 交互式应用不能陪 provider
挂半天；只认秒数形式，HTTP-date 形式时钟相关，解析错比不解析更糟，直接交给
退避。退避本身是指数 + 只向下的抖动（0.5x–1x），上限 8s。

## 超时是"防挂死"，不是延迟 SLA

单次尝试 240s 超时。给这么宽是因为它防的是挂死的连接，不是慢 ——
大上下文 + 长输出的真实调用就是可以很慢。超时用 `AbortSignal` 实现，
和用户取消共用一条信号线，靠 reason 的 `name === 'TimeoutError'` 区分：
超时的 sendState 是结局不明（请求早已发出），**不重试**；取消是用户意志，
优先于一切可重试判断 —— 退避睡到一半被取消，下一次尝试根本不发起，
manifest 如实记 `NOT_SENT`。

## 每次尝试独立落账

重试不是"把失败藏起来再试一次"。egress manifest 加了 `sendAttempt`，
中间失败的尝试独立追加进 egress 日志，最后一次随结果返回 —— 三次尝试
就是三条记录，不覆盖。顺带修了一个旧的不实记账：以前 catch 里统一写
`sent: true`（注释是"请求确实发出去了"），但 `ECONNREFUSED` 时请求
从没离开过本机 —— 现在 `sent = sendState !== 'NOT_SENT'`。

两条不变式在重试层原样成立：

- **永远只在冻结的那条路由上重试。** 不换 provider、不换模型、不换 origin。
  429 触发换供应商是别的产品的行为，这里 `automaticFallback=DENY`。
- **探针不重试。** 设置页「测试连接」单次 30s —— 它的职责是报告"现在通不通"，
  重试会把链路抖动藏起来，恰好与职责相反。

## 与 TD 的差距（如实）

TD 要求 max attempts、Retry-After 上限、jitter 全部来自**签名的 adapter
policy**；原型没有签名机制，用一份写死并有文档的保守默认顶位，差距记在
`retry.ts` 头注释里。语义三条底线（同路由、结局不明不重发、独立落账）没打折。

## 反向验证

+26 条测试（8 条 sendState 分类、7 条 invoke 重试语义、11 条纯函数矩阵），
全量 519 通过。把最贵的那条守卫 —— "结局不明不重发" —— 临时放开
（`NETWORK` 一律可重试），确认它真的在管事：

```
❯ src/core/model/gateway.test.ts (24 tests | 2 failed)
  × invoke: 有界同 route 重试 + 单次尝试超时
    > 发出去后连接被重置（结局不明）不重试 —— 重发可能重复执行、重复计费
  × retry 策略纯函数：什么能重试、等多久
    > NETWORK + sendState=SENT_OUTCOME_UNKNOWN → 可重试=false
```

## 可以带走的

1. **重试首先是分类问题，然后才是循环问题。** "什么错误"不够，
   要知道"错误发生在生命周期哪一段"。
2. **分类错误的代价不对称时，把默认值放在便宜的那一侧。**
   少一次重试是便利损失，重复执行是错账。
3. **重试不能覆盖失败记录。** 每次尝试独立落账，否则"试了三次才成"
   和"一次就成"在审计里长得一样 —— 链路质量的证据就没了。
