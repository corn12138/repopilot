# 让 LLM 改代码，但不让它模糊匹配

> 开发记录 · 2026-08-07 · RepoPilot

几乎所有 coding agent 的 edit 工具都长这样：给一段 `old_string`、一段 `new_string`，
在文件里找到就替换。听起来很简单，但**「找到」这两个字里藏着整个可靠性问题**。

## 先看模糊匹配会出什么事

参考的开源 CLI 里，apply 逻辑有多层降级策略：

```
src/utils/applyEdit.ts:349-447
  精确匹配 → 失败
  → 去掉首尾空白再匹配 → 失败
  → 忽略缩进匹配 → 失败
  → 更宽松的策略...
```

用户体验很好：模型少写了个空格也能改对。但代价是：

**你永远不知道它到底改了哪一行。**

更要命的是 write 工具：

```ts
// src/tools/edit.ts:44-75  —— 接受绝对路径，直接写
// src/tools/write.ts:25-46 —— 隐式覆盖 / 隐式创建
```

绝对路径 + 隐式覆盖 + 模糊匹配，三个凑在一起，一次跑飞就能把仓库改成没人看得懂的样子。

我的选择是反过来：**宁可失败，也不猜。**

## 三条硬规则

### 1. 命中必须唯一

`oldText` 在文件中出现 0 次或 2 次以上，整笔事务失败：

```ts
const first = content.indexOf(oldText);
if (first < 0) {
  throw new Blocked('ZERO_MATCH',
    `${op.path} 中找不到 oldText —— 不做模糊匹配，请重新读取文件再改`);
}
if (content.indexOf(oldText, first + oldText.length) >= 0) {
  throw new Blocked('MULTIPLE_MATCH',
    `${op.path} 中 oldText 命中多次 —— 请扩大上下文使其唯一`);
}
```

失败信息里直接告诉模型该怎么办。实际跑下来，模型收到 `MULTIPLE_MATCH`
之后会自己带更多上下文重试，不需要额外的 prompt 工程。

### 2. 改之前必须先读，而且要能证明

这是我觉得最有价值的一个设计。读文件时签发一张**回执**：

```ts
export interface MutationReadReceipt {
  readonly receiptId: string;
  readonly generation: number;   // 绑定到工作区的哪一代
  readonly path: string;
  readonly fileDigest: Digest;   // 读到的内容摘要
  readonly byteLength: number;
  readonly readAt: Iso8601;
  readonly expiresAt: Iso8601;
}
```

修改现有文件时必须带上 `receiptId`。关键在于这句注释：

> Receipt 只证明「在 generation N 读到了 digest D 的这个文件」。
> 它**不是**写权限凭据 —— apply 时会重新计算 digest 再比对一次。

区别在哪？如果只是「必须先调 read」，那模型可以读 A 文件、改 B 文件。
绑定 digest 之后，「你以为的文件内容」和「实际文件内容」不一致就直接拒绝 ——
这堵住的是并发修改和陈旧上下文，而不只是流程合规。

### 3. 事务是原子的

多个 operation 要么全成，要么全不成。实现方式是**先在内存里完整模拟一遍**：

```ts
export function applyMutationPlan(ws, plan, policy): MutationResult {
  const expectedActive = ws.activeGeneration;

  // ---- 阶段 1：内存中完整模拟。任何失败 = 零写入 ----
  let sim: Map<string, SimFile>;
  try {
    sim = simulate(ws, plan, policy);
  } catch (err) {
    return blocked(err.reason, err.detail, expectedActive);
  }

  // ---- 阶段 2：把模拟结果写进 staged generation ----
  const staged = ws.stage();
  try {
    for (const file of sim.values()) { /* 写盘 */ }
  } catch (err) {
    ws.discard(staged.generation);   // 整个丢弃，active 不动
    return blocked(/* ... */);
  }

  // ---- 阶段 3：CAS 提交 ----
  if (!ws.commit(staged.generation, expectedActive)) {
    ws.discard(staged.generation);
    return blocked('STALE_GENERATION', 'CAS 失败', ws.activeGeneration);
  }
  return { ok: true, outputGeneration: ws.activeGeneration, /* ... */ };
}
```

工作区用「代」组织：`gen-0` 是导入时的原貌，每次事务克隆出 `gen-N+1`，
校验通过才 CAS 切换 active 指针。macOS 上用 APFS clonefile（`cp -Rc`），
整目录克隆的实际成本接近元数据操作。

失败时工作区与调用前**逐字节相同** —— 没有「部分提交」这个中间态。

## 一个我自己踩的坑：同文件多次编辑

第一版写完，测试跑出来一个问题：同一个文件连续改两处，第二处必然失败。

原因是我在写盘阶段又校验了一次 receipt digest：

```ts
// 第一版（有 bug）
const actual = sha256(before);
if (actual !== receipt.fileDigest) {
  throw new Blocked('STALE_FILE_DIGEST', '...');
}
```

第一个 operation 已经把 staged 文件改了，第二个 operation 读到的自然对不上 receipt。
逻辑上「文件确实变了」，但这个变化是**本次事务自己造成的**，不该算冲突。

修法就是前面那个「先模拟」的设计：receipt 只在**首次触碰某个路径**时校验一次，
之后的 operation 作用在演化后的内存内容上：

```ts
let file = sim.get(op.path);

if (!file) {
  // 首次触碰这个路径：在此校验 receipt / 存在性
  verifyReceipt(ws, op, currentDigest);
  file = { path: op.path, originalDigest: currentDigest, content: readFileSync(...), touched: false };
  sim.set(op.path, file);
}

// 对**演化后的内容**应用 operation，允许同文件多次顺序编辑
file.content = applyToContent(op, file.content);
file.touched = true;
```

顺带的好处是：预检变成了完整模拟，所有失败模式都在零写入阶段暴露，
不用再依赖「阶段 2 出错就回滚」这条后路。

## 完整的阻断原因清单

```ts
export type MutationBlockReason =
  | 'STALE_GENERATION'    // plan 基于旧的一代
  | 'STALE_FILE_DIGEST'   // 文件在读取后被改过
  | 'RECEIPT_MISSING'     // 没先读就想改
  | 'RECEIPT_EXPIRED'
  | 'ZERO_MATCH'          // 找不到 —— 不模糊匹配
  | 'MULTIPLE_MATCH'      // 不唯一 —— 不改第一个
  | 'PATH_ESCAPE'         // 绝对路径 / ..
  | 'PATH_NOT_ALLOWED'    // 不在 TaskSpec 允许范围
  | 'PROTECTED_PATH'      // 命中受保护路径
  | 'TARGET_EXISTS'       // create 撞到已有文件，不隐式覆盖
  | 'TARGET_ABSENT'
  | 'BUDGET_EXCEEDED'
  | 'SYMLINK_REJECTED';
```

每一条都是**具体的、可以写测试的**失败模式。这比一个笼统的 `EDIT_FAILED` 有用得多 ——
模型能据此调整行为，用户能据此判断是自己的问题还是 Agent 的问题。

## 测试怎么写

核心断言只有一句：**失败时工作区必须逐字节不变。**

```ts
/** 整棵树的指纹 —— 用来断言"失败后什么都没变" */
function fingerprint(): string {
  return JSON.stringify(listTree(workspace.activePath));
}

it('0 次命中 → ZERO_MATCH，且不做模糊匹配', () => {
  const { receipt } = workspace.issueReceipt('src/app.ts');
  const snapshotBefore = fingerprint();

  const result = applyMutationPlan(workspace, {
    operations: [{
      kind: 'REPLACE_EXACT_TEXT_SPAN',
      path: 'src/app.ts',
      receiptId: receipt.receiptId,
      // 只差一个空格 —— fuzzy apply 会"帮忙"改掉，这里必须拒绝
      oldText: 'const b  = 2;',
      newText: 'const b = 42;',
    }],
  });

  expect(result.ok).toBe(false);
  if (!result.ok) expect(result.reason).toBe('ZERO_MATCH');
  expect(fingerprint()).toBe(snapshotBefore);
});
```

「只差一个空格」这个用例特别值：它精确地卡在 fuzzy apply 会「帮忙」的地方。

另一个必测的是批次原子性：

```ts
it('批次中任一 operation 失败 → 整批零写入', () => {
  const snapshotBefore = fingerprint();
  const result = applyMutationPlan(workspace, {
    operations: [
      { /* 第一个合法 */ },
      { kind: 'CREATE_FILE', path: 'src/dup.ts', newText: 'collision' },  // 第二个非法
    ],
  });
  expect(result.ok).toBe(false);
  expect(fingerprint()).toBe(snapshotBefore);          // 整批没生效
  expect(workspace.readText('src/app.ts')).toContain('const a = 1;');
});
```

26 个测试，全是这类负向用例（写这篇时的数字；后来补到 27）。正向路径只有几个 —— 因为**正向很难写错，
错都错在边界上**。

## 模型那边要怎么配合

系统 prompt 里把规则说死，不留解释空间：

```
- 你没有 shell，没有文件系统写接口。所有改动只能通过 workspace_mutate。
- 修改现有文件前，必须先 fs_read 拿到 receiptId，并在 mutate 时传回去。
- REPLACE_EXACT_TEXT_SPAN 的 oldText 必须在文件中**恰好出现一次**。
  命中 0 次或多次都会整笔失败，不会做模糊匹配。所以要带足够多的上下文让它唯一。
- CREATE_FILE 的目标必须不存在。不存在"隐式覆盖"。
- 一次 workspace_mutate 是原子的：任何一个 operation 不合法，整笔都不生效。
```

实际效果：模型第一次撞上 `MULTIPLE_MATCH` 之后，后续调用会主动带更多上下文。
**清晰的失败信息比冗长的 prompt 有效。**

## 可以带走的

1. **模糊匹配是在用「不知道改了哪」换「少失败几次」。** 交互式 CLI 里这笔账划算，
   要审计的产品里不划算。
2. **「先读后写」不够，要绑 digest。** 否则挡不住并发修改和陈旧上下文。
3. **原子性最简单的实现是「先在内存里跑一遍」。** 比「出错回滚」好写，也好测。
4. **失败原因要枚举成类型。** 一个 `EDIT_FAILED` 等于什么都没说。
5. **负向测试才是主体。** 正向路径不容易错。
